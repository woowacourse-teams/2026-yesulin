## 1 결정된 제품 방향

| 항목 | 결정 |
| --- | --- |
| 공개 범위 | 비회원·배우·제작사 구분 없이 누구나 목록·글·댓글 열람 |
| 작성 자격 | 회원가입·로그인·배우 인증 없이 글과 댓글 작성 |
| 정체성 | 익명. 닉네임 설정이나 실명 입력을 참여 조건으로 두지 않음 |
| 게시 주제 | 자유. 오디션 질문·경험 공유 등으로 주제를 제한하지 않음 |
| 운영 권한 | 첫 출시에서 방장·강퇴·쓰기 제한·운영자 숨김·복구 기능을 만들지 않음 |
| 신고 | 신고 1회부터 팀에 알림. 신고만으로 자동 숨김·삭제·제재하지 않음 |
| 남용 대응 | 도배·부적절한 글이 실제 문제가 되면 대응 방식을 추가 검토 |
| 검증 | 중요하지만 팀원 제외·고유 사용자 집계·리텐션 자동화는 구상만 하고 후순위로 둠 |

익명은 다른 이용자에게 계정·실명·프로필이 표시되지 않는다는 뜻이다.
운영 데이터나 서버 기록까지 전혀 남지 않는다는 의미로 안내하지 않는다.
게시물 관리용 비밀값과 통계용 식별자는 별도 목적이며, 하나를 도입했다고 다른 용도로 자동 사용하지 않는다.

## 2 첫 출시와 후속 범위

첫 출시는 **공개 목록 → 익명 글쓰기 → 글 상세 → 익명 댓글 → 신고 접수와 팀 알림**을 완성한다.
작성자 자신의 수정·삭제는 추가 입력 없이 작성한 브라우저의 비밀값으로 확인한다.

이전 초안의 로그인 유도, 계정 기반 고정 닉네임, 질문·경험 공유 선택, 도움 확인, 사용자 댓글 알림,
공고 연결, 운영 대시보드, 자동 집계는 첫 출시 필수에서 제외한다.
자유로운 글에 본문으로 공고 주소를 적는 것은 가능하다.

최신순 단일 게시판과 텍스트 입력을 기본안으로 둔다. 이미지·파일 업로드, 대댓글, 검색, 좋아요,
실시간 채팅, 개인 메시지, 여러 게시판은 별도 후속 항목으로 관리한다.

## 3 개발 순서와 완료 처리

C01부터 시작하되 C02 이후에는 관련 데이터와 화면을 함께 완성한다.
C06 결정 대기 중에도 목록·작성·댓글·신고 개발은 진행할 수 있다.
C08은 C07 신고 접수 이후에 진행한다. 알림 채널은 C08 구현 전에 확정한다.

각 체크박스는 기능을 만들었다는 이유만으로 체크하지 않는다.
해당 요구사항의 테스트와 필요한 화면·실제 요청 확인을 통과한 뒤 체크하고, 같은 논리적 변경의 커밋에 포함한다.
코드와 테스트가 실패하는 상태에서는 완료 표시나 성공 커밋을 만들지 않는다.

한 C 항목이 크면 하위 체크박스별로 더 작은 TDD 사이클과 커밋으로 나눠도 된다.
각 커밋은 독립적으로 검증 가능해야 하며, 관련 없는 리팩터링이나 다른 작업자의 변경을 섞지 않는다.

### 항목마다 반복할 TDD 사이클

- [ ] Red: 아래 검증 기준에서 사용자 행동 또는 실패 조건 하나를 골라 실패하는 테스트를 먼저 작성하고, 예상한 이유로 실패하는지 확인한다.
- [ ] Green: 그 테스트를 통과시키는 최소 구현을 한다.
- [ ] Refactor: 테스트를 유지하면서 중복과 책임을 정리한다. 정리할 것이 없으면 불필요한 변경을 만들지 않는다.
- [ ] Verify: 관련 테스트와 변경 영역의 필수 검사를 통과시키고, 자동 테스트로 확인하지 못한 화면·연동은 직접 확인한다.
- [ ] Sync: API·타입·호출·MSW와 구현된 규칙의 문서를 필요한 범위에서 맞춘다.
- [ ] Commit: 완료한 요구사항을 체크하고 변경과 검증 결과를 하나의 논리적 커밋으로 남긴다.

이 사이클 목록은 진행 방법이다. 전체 작업이 한 번에 완료됐다는 표시로 사용하지 않고,
실제 진행 상태는 아래 기능별 체크박스로 관리한다.

- [x] 실패하면 입력 내용을 유지하고 재시도를 제공한다. 성공하면 생성된 글 상세로 이동한다.

같은 등록 요청을 다시 보내도 글은 하나다. 회원의 글도 비회원의 글과 같은 익명 형태로 공개된다.

### C06 본인이 쓴 글과 댓글 관리

2026년 10월 27일 사용자 결정: **작성한 브라우저에서만 수정·삭제하며 추가 입력은 받지 않는다.**
첫 쓰기에 브라우저 비밀값을 생성하고 서버는 해시로 확인한다. 로그인 계정이나 공개 작성자 표시와 연결하지 않는다.
브라우저 데이터를 지우거나 시크릿 창을 닫아 비밀값을 잃으면 관리 권한을 복구하지 못함을 작성 화면에서 안내한다.

- [x] 확정한 방식으로 본인 확인이 될 때만 본인의 글·댓글 수정과 삭제를 제공한다.
- [x] 본인 확인 수단이 없거나 잘못되면 직접 요청을 보내도 수정·삭제할 수 없다.
- [x] 글 수정 시 수정 표시를 남기고, 삭제는 사용자에게 확인받는다.
- [x] 글 삭제 후 목록에서 제외하고 직접 주소에는 삭제 안내를 보여 준다. 그 글의 댓글도 함께 공개하지 않는다.
- [x] 댓글 삭제 후 목록과 댓글 수에서 제외한다.
- [x] 비밀값은 공개 응답·URL·분석 이벤트·로그에 노출하지 않는다.
- [x] 관리 권한의 유지 범위와 잃었을 때 가능한 행동을 사용자에게 안내한다.
- [x] 삭제된 글에는 새 댓글·신고를 받지 않는다. 동시에 작성·삭제한 경우도 일관되게 처리한다.

검증 기준: 본인만 수정·삭제할 수 있고 다른 비회원·로그인 회원·관리자 계정이라는 이유로 권한이 생기지 않는다.
삭제 후에는 상세·목록·댓글 어디에서도 원문이 다시 공개되지 않는다.
데이터의 실제 파기와 보관 기간은 별도 미결정 항목이다.

권장 커밋: `feat: 익명 작성물 본인 관리 추가`

### C07 비회원 신고 접수

- [x] 로그인 없이 글과 댓글을 신고할 수 있다.
- [x] 신고 버튼을 누르면 짧은 사유 선택과 제출 화면을 보여 준다. 신고자 이름·연락처는 요구하지 않는다.
- [x] 사유의 초기 기본안은 광고·도배, 욕설·괴롭힘, 개인정보 노출, 기타다. 자유 설명은 선택이다.
- [x] 신고 대상·사유·접수 시각을 저장하고 접수 완료를 안내한다.
- [x] 존재하지 않거나 이미 삭제된 대상은 신고할 수 없다.
- [x] 동일 신고 요청의 재전송은 한 건으로 처리한다. 비회원 환경에서 같은 실제 사람의 재신고를 완벽히 판별한다고 가정하지 않는다.
- [x] 신고자 정보와 신고 사유는 게시판의 다른 사용자에게 공개하지 않는다.
- [x] 신고 1회 또는 여러 회가 접수돼도 글을 자동 숨김·삭제하거나 작성을 제한하지 않는다.

검증 기준: 비회원 신고가 접수되고, 재시도로 중복 신고가 쌓이지 않는다.
신고 후에도 기존 글·댓글이 공개 상태를 유지하며 누구나 계속 작성할 수 있다.

권장 커밋: `feat: 비회원 커뮤니티 신고 접수 추가`

### C08 첫 신고의 팀 알림

신고 1회부터 알림을 보낸다는 요구는 **대상 게시글 또는 댓글에 첫 신고가 접수되는 즉시 알림을 예약**하는
방식으로 구현했다. 두 번째 이후의 별도 신고는 저장하되 같은 대상의 최초 신고 알림을 추가 생성하지 않는다.
기존 워크스페이스의 전용 신고 채널을 권장하며 `YESULIN_COMMUNITY_SLACK_WEBHOOK_URL`로 연결한다.
실제 웹훅과 같은 환경의 `YESULIN_COMMUNITY_LINK_BASE_URL` 설정·수신 확인은 아직 하지 않았다.
2026년 10월 27일 사용자 요청에 따라 실제 Slack 연결은 후속 작업으로 남긴다.

- [x] 대상에 첫 신고가 저장되면 팀 알림 작업을 함께 기록한다. 여러 신고를 기다리거나 신고 수 임계치를 두지 않는다.
- [x] 알림에는 게시글·댓글 구분, 확인할 공개 링크, 사유 분류, 접수 시각, 실행 환경을 포함한다.
- [x] 댓글 신고 링크는 해당 글에서 신고된 댓글을 찾을 수 있도록 한다.
- [x] 신고자의 계정·IP·기기 정보나 관리용 비밀값은 알림에 넣지 않는다. 본문·자유 설명 전문도 복사하지 않는다.
- [x] 신고 접수 성공과 외부 알림 전송 성공을 구분한다. 알림 장애 때문에 접수한 신고가 사라지지 않는다.
- [x] 첫 알림이 실패하면 전송 상태를 남기고 재시도할 수 있다. 뒤이은 신고가 없더라도 실패한 알림을 다시 보낼 수 있다.
- [x] 동시에 첫 신고가 들어오거나 같은 요청을 다시 보내도 대상별 최초 알림 작업은 하나만 생성된다.
- [x] 외부 전송 결과가 불확실한 재시도에서는 중복 수신 가능성을 구분하고, 같은 알림 식별값으로 중복을 알아볼 수 있게 한다.
- [x] 테스트·개발 환경의 알림이 운영 신고로 오인되지 않게 하며, 단위 테스트는 실제 채널로 보내지 않는다.

검증 기준: 첫 신고는 알림 작업 1개, 후속 신고·중복 요청·동시 요청은 추가 최초 알림 작업 0개다.
외부 전송 실패에도 신고가 남고 재시도하면 전송 상태가 갱신된다. 전송 불확실성을 무조건 성공으로 기록하지 않는다.

권장 커밋: `feat: 커뮤니티 첫 신고 팀 알림 추가`

- [ ] 전용 Slack 웹훅·환경별 링크 주소를 설정하고 실제 채널에서 첫 신고·실패 후 재시도 수신을 확인한다.

### C09 실제 사용 흐름과 출시 점검

- [x] 모바일·데스크톱에서 비회원의 목록 → 글쓰기 → 상세 → 댓글 → 신고가 막힘없이 이어진다.
- [x] 로딩·빈 상태·실패·재시도 화면이 있고, 실패했는데 성공 안내를 보여 주지 않는다.
- [x] 긴 제목·본문·주소가 화면을 넘치지 않고, 버튼과 입력을 키보드로 사용할 수 있다.

- [x] 글·댓글에는 식별자와 작성·수정 시각을, 신고에는 대상·접수 시각·알림 상태를 남긴다. 별도 사용자 추적은 추가하지 않는다.
- [x] 실제 HTTP 계약과 프론트 타입·호출·MSW가 일치한다.
- [x] 구현된 동작을 공통 도메인 문서와 관련 책임 문서에 반영한다.

검증 기준: 새 브라우저의 비로그인 흐름과 로그인한 배우·제작사 흐름을 실제 화면에서 확인한다.
확정된 신고 채널의 수신 여부도 별도로 확인하며, 자동 테스트 통과만으로 외부 수신을 검증했다고 하지 않는다.

## 5 후순위 체크리스트

아래는 첫 출시를 막지 않는 구상 목록이다. 실제로 착수하기 전 우선순위를 다시 정한다.

### L01 팀원과 테스트 사용 제외

- [ ] 팀원이 작성한 테스트 글·댓글 ID를 직접 표시하는 방식과 브라우저의 내부 테스트 표시 방식을 비교한다.
- [ ] 로그인한 팀원이 쓴 글만 별도로 식별하는 보조 방법을 검토한다. 로그인하지 않은 팀원 활동까지 제외된다고 가정하지 않는다.
- [ ] 팀원 표시와 실제 작성물 연결, 표시 누락 시 보정 방법, 기존 기록 소급 가능 범위를 정한다.
- [ ] 글 작성 권한의 비밀값이나 IP를 실제 사람의 신원으로 취급하지 않는다.
- [ ] 방식을 확정한 뒤 제외 기능을 구현하고 검증한다.

현재는 글·댓글의 건수와 시각을 확인할 수 있게 하는 정도로 둔다.
후속 제외 기능을 만들더라도, 지금 기록하지 않은 팀원 활동과 고유 방문자를 과거로 돌아가 정확하게 복원할 수는 없다.

### L02 가설과 지표 재정의

- [ ] 자유 주제·비회원 익명 참여에 맞게 활성 행동과 핵심 지표를 다시 정한다.
- [ ] 기존 가설 기록의 회원 계정 기반 고유 작성자·방문자·팀원 제외 전제를 수정한다.
- [ ] 사람 수와 글 수를 구분한다. 익명 글 5개를 작성자 5명으로 보고하지 않는다.
- [ ] 브라우저 식별을 도입한다면 사람 수가 아닌 브라우저 단위 추정임을 표시하고, 여러 기기·데이터 삭제에 따른 한계를 기록한다.
- [ ] WAU·W+4 리텐션의 측정 단위, 관측 시작일, 분석 거부·보관 기준을 정한 뒤 수집과 집계를 구현한다.
- [ ] 관측하지 않은 값은 미측정으로 남긴다. 팀원이 섞인 초기 글 수를 외부 사용자 성과로 표시하지 않는다.
- [ ] 도움 확인 기능이 없는 동안 이전 가설의 도움 확인 3건을 자동 검증할 수 있다고 보고하지 않는다.

이전 가설 검증 문서는 당시 계획으로 보존한다. 새로운 공개·익명 정책에 맞춘 실험 기준을 정하기 전까지
기존 20명·작성자 3명·글 5개·도움 확인 3건을 이번 출시의 필수 성공 조건으로 사용하지 않는다.

### L03 재방문과 탐색 확장

- [ ] 제목·본문 검색과 필터를 검토한다.
- [ ] 공고 연결과 공고별 대화 모아보기를 검토한다.
- [ ] 익명 상태에서 내 글·새 댓글 알림을 제공할 방법을 검토한다.
- [ ] 좋아요·도움 표시·대댓글·이미지 첨부의 우선순위를 실제 사용을 보고 정한다.

### L04 운영 확장

- [ ] 부적절한 글·도배·반복 신고의 발생 양상을 보고 대응 필요성을 판단한다.
- [ ] 필요할 때 등록 빈도 제한, 자동 탐지, 운영자 숨김·삭제·제재 등 대응안을 비교한다.
- [ ] 도입할 권한과 기준을 사용자가 결정한 뒤 별도 요구사항과 테스트를 작성한다.

## 7 저장소의 TDD와 커밋 규칙 적용

- 백엔드는 현재 `backend/AGENTS.md`에 따라 domain·application에서 규칙과 유스케이스를 TDD로 검증한다.
  Controller·외부 연동에 새 자동 테스트를 추가하지 않고 실제 요청·연동으로 확인한다. 기존 테스트는 유지한다.
- 프론트는 현재 `frontend/package.json`의 `npm test`가 Vitest를 실행한다.
  입력 검증·상태 전환·응답 처리 등 의미 있는 로직을 우선 검증하고 순수 문구·간격에 형식적인 테스트를 만들지 않는다.
- 변경 영역에 맞춰 백엔드 `./gradlew test`·`./gradlew build`, 프론트 `npm test`·`npm run lint`·`npm run build`를 실행한다.
  명령은 각각 backend·frontend 디렉터리에서 실행한다. UI만 바꾸는 경우 등 세부 범위는 각 AGENTS 지침을 따른다.
- 프론트 지침의 테스트 러너 미도입 설명과 현재 실행 스크립트가 다르므로, 실제 구현 착수 시 현재 코드·테스트를 우선 확인한다.
- 개발 시작 전 이슈·브랜치 절차와 커밋 형식은 [Git 작업 방식](./git-workflow.md)을 따른다.
- 커밋은 `{type}: {summary}`로 하나의 논리적 변경만 담고, 제목은 50자 이내로 쓴다.
- 루트 `node_modules/`가 없으면 `npm install`로 hook을 준비한다. hook 우회는 하지 않는다.
- 요구사항 문서 작성 완료는 기능 구현 완료가 아니다. 이번 문서의 기능 체크박스는 모두 미완료로 시작한다.
- 커밋 성공은 push·PR 병합·배포 성공을 뜻하지 않는다. 해당 단계는 별도 작업으로 진행한다.

## 9 디자인 방향

사용자 요청에 따라 스레드의 대화 중심 피드 구성을 참고하고, 색상은 기존 예술in 공개 화면의 밝은 배경·흰 카드·푸른 강조색을 공유한다.
좁은 중앙 피드, 익명 아바타, 본문 미리보기, 댓글·공유 동작을 배치하고 데스크톱은 왼쪽 메뉴, 모바일은 하단 메뉴를 쓴다.
좋아요·팔로우·리포스트처럼 구현되지 않은 동작이나 가짜 활동 수치는 표시하지 않는다.

## 10 이번 구현 검증 기록

- 도메인·애플리케이션 테스트를 먼저 추가해 실패를 확인한 뒤 구현했다. 생성·재시도·소유 확인·댓글 수·삭제·신고·알림 실패를 검증한다.
- 백엔드 전체 테스트: 1,005개 중 실패 0, 오류 0, 기존 제외 2. `./gradlew build` 통과.
- 프론트 전체 테스트: 348개 통과. `npm run lint`, `npm run build` 통과.
- 실제 로컬 HTTP 요청: CSRF 없는 쓰기 거절, 비회원 읽기/쓰기, 다른 작성자의 수정 거절, 재시도/충돌,
  글·댓글 수정/삭제, 댓글 수, 신고 및 삭제 대상 접근을 확인했다. 공개 응답의 필드와 no-store도 확인했다.
- 실제 API를 연결한 브라우저에서 익명 글쓰기·댓글·신고·수정·링크 복사를 확인했다. 데스크톱 1440×1000,
  모바일 390×844로 화면을 확인했다. 실제 Slack 전송과 배포 환경 부하 테스트는 하지 않았다.
- 팀원 제외·활성 사용자 집계·부하 지점 분석·장애 알림·부하 테스트는 후속 학습 범위로 유지한다.

### 작성 중 브라우저 이동 보호 보완

- 방문 기록의 기존 라우터 상태를 유지하며 뒤로·앞으로 이동을 확인하고, 취소 시 원래 기록으로 돌아온다.
- 여러 작성·수정 폼이 열려 있어도 이탈 확인은 한 번만 표시한다. 새 탭 열기·다운로드·같은 화면의 해시 링크 클릭은 막지 않는다.
- 회귀 테스트 7개로 뒤로/앞으로 취소, 여러 단계 이동, replace, 해시 방문 기록과 라우터 상태 보존을 검증했다.
- 실제 브라우저에서 글 초안의 뒤로/앞으로 취소, 정상 이동, 새 댓글·댓글 수정 초안 동시 보존과 단일 확인을 검증했다.
- 보완 후 프론트 전체 348개 테스트, lint, production build가 통과했다.
