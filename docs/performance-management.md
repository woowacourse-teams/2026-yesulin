# 공연 관리 — 공연·공고 생성과 지원자 심사 MVP

## 생성 기능 추가 (2026-08-05)

공연 선택 화면 우측 상단에 `공연 추가`, 공연별 공고 선택 화면 우측 상단에 `공고 추가`를 추가했다.

- 공연 추가: 최대 30MB의 공연 포스터 이미지, 제목·장소와 이후 공고에서 재사용할 배역·성별·나이 조건을 등록한다.
- 공고 추가: 모집 기간, 배역별/배역 구분 없음 모집 방식, 모집 배역과 인원, 전형 일정, 지원서 수집 항목과 지원 안내를 설정한다. `isOpenCall`이면 모집 분야를 하나만 선택한다.
- 전형은 2개로 시작하고 필요하면 3차를 추가한다. 각 전형의 이름·진행일·안내 메모를 바꿀 수 있다.
- 지원서 항목은 각각 사용 여부와 `필수`/`선택`을 정한다. 기본 목록에 없는 항목도 직접 추가할 수 있다.
- 장식용 이모지는 사용하지 않는다. 공연은 포스터 이미지로 구분하고 공고·상태는 텍스트와 상태 태그로 구분한다.
- 공연과 공고는 별도 개념이다. 공연을 만들었다고 모집이 시작되지 않으며, 해당 공연에 공고를 추가해야 지원자를 받을 수 있다.
- 새로 만든 공연과 공고는 MSW 인메모리 카탈로그에 반영되어 목록과 사이드바에 즉시 나타난다. 새로고침하면 초기화된다.

## 범위 변경 (2026-08-04)

공연사 관리자의 `공연 관리` 메뉴를 **공연 등록·수정 화면**에서 **지원자 심사 흐름**으로 교체했다.

- 교체 이유: 공연사가 가장 먼저 겪는 병목이 공연 등록이 아니라 **접수된 지원자를 차수별로 걸러내는 일**이었다. 프로토타입(`docs/index.html`)에서 확인한 흐름을 그대로 옮겼다.
- 당시 제거한 공연 등록·수정 폼 중 **등록 흐름만 현재 심사 구조에 맞춰 다시 추가**했다. 공연 수정, 전시 상태 토글, 포스터 교체, `/api/performance/**` 계약은 여전히 후순위다.
- 사이드 메뉴에서 `대시보드`, `지원 공고 관리`, `지원자 관리`, `모집 공고 만들기` 항목(모두 `준비 중`)을 제거했다. 남은 진입점은 `공연 관리` 하나다.

현재 저장소에는 과거 문서가 언급한 원본 프로토타입 `docs/index.html`이 없다. 화면 의도는 이 문서와 현재 프런트엔드 구현을 우선하며, 둘로 결정할 수 없는 내용은 팀에 확인한다.

## 도메인 계층

```text
Performance  공연(작품)
  ├ RoleTemplate  공연이 보유한 재사용 가능한 배역·조건
  └ Posting      공고 — 실제 게시하는 모집 공고 한 건
      └ Role          배역 — 한 공고 안에 여러 개
          └ Application   지원서
```

핵심 설계 결정 두 가지는 백엔드 테이블에도 그대로 반영해야 한다.

1. **전형은 배역 단위로 독립 진행된다.** 차수 마감 상태는 `(배역, 차수)`에 붙는다. 같은 공고라도 배역마다 1차/2차/3차 진행 속도가 다르다.
2. **심사 결과는 `(지원서, 차수)`에 붙는다.** 지원서에 상태 컬럼을 직접 두면 2차 결과가 1차 기록을 덮어써 이력이 사라진다.

공연의 `RoleTemplate`은 배역 이름과 성별·나이 조건을 재사용하기 위한 원본이다. 공고를 만들 때 템플릿을 선택하고 모집 인원을 정하면 공고 아래에 실제 `Role`이 생성된다. 따라서 같은 공연이라도 공고마다 모집하는 배역과 인원이 다를 수 있다.

### 전형 차수

| 차수 | 이름 | 선택 가능한 결과 |
| --- | --- | --- |
| 1 | 기본값 `서류 심사`, 수정 가능 | 합격 · 불합격 · 기타 |
| 2 | 기본값 `대면 오디션`, 수정 가능 | 합격 · 불합격 · 불참 · 기타 |
| 3 | 필요할 때 추가, 이름 수정 가능 | 합격 · 불합격 · 불참 · 기타 |

- 1차는 현장에 오지 않으므로 `불참`을 고를 수 없다.
- `기타`는 사유(memo)를 함께 받고, 목록 배지에 상태 라벨 대신 그 사유를 노출한다.
- 2차 이상의 심사 대상은 **직전 차수를 마감했을 때만** 넘어온다. 마감 전에는 비어 있다.
- 마감된 차수는 결과를 변경할 수 없다. 서버에서도 막는다(400).
- 검토 대기가 0명이 되어야 마감할 수 있다.

### 공고 진행 단계

접수 상태와 전형 마감 여부를 합쳐 4단계로 파생한다. **접수 마감과 전형 마감은 다른 상태다** — 접수는 끝났지만 심사가 안 끝났을 수 있다.

| 단계 | 조건 |
| --- | --- |
| `UPCOMING` 예정 | 접수 시작 전 |
| `OPEN` 진행중 | 접수 중 |
| `RECRUIT_CLOSED` 접수마감 | 접수 종료, 아직 전 배역 전형이 안 끝남 |
| `FINISHED` 전형마감 | 접수 종료 + 모든 배역의 모든 차수 마감 |

`UPCOMING` 공고는 지원자가 없으므로 열람할 수 없고, 눌러도 토스트만 띄운다.

### 조건 불일치

배역이 명시한 성별·나이 범위를 벗어난 지원자를 서버가 표시해 내려준다(`mismatchReasons`). 기존 접수 방식에서는 이런 지원자가 걸러지지 않고 그대로 들어오기 때문에, **막지 않고 눈에 띄게만** 한다. 목록·상세에 경고 배지가 붙고 `조건 불일치만` 필터로 모아 볼 수 있다.

## 화면 경로

| 화면 | 경로 |
| --- | --- |
| 공연 선택 | `/producers/performances` |
| 공고 선택 | `/producers/performances/{performanceId}` |
| 배역 선택 | `/producers/postings/{postingId}` |
| 지원자 심사 | `/producers/roles/{roleId}` |
| 공개 공고 상세 | `/apply/{postingId}` |

식별자가 전역 유일하므로 계층을 URL에 중첩하지 않는다. 상위 정보(공연·공고)는 각 응답이 함께 내려줘 브레드크럼으로 복원한다.

건너뛰기 규칙: **배역 구분이 없는 공고(`isOpenCall`)이거나 배역이 하나뿐이면** 배역 선택 화면을 건너뛰고 바로 심사 화면으로 들어간다. 서버가 `soleRoleId`로 알려준다.

공연사 관리자 화면은 검색 엔진에 노출하지 않는다. `/producers` 레이아웃에 `noindex`, `nofollow`를 적용한다.

### 공개 공고 상세 (프론트엔드 목)

- `/apply/{postingId}`는 로그인 없이 공고 정보, 공연사 정보, 모집 배역, 전형 일정, 제출 자료를 보여준다. 제출 자료는 `applicationFields`의 활성 필드를 지원서와 같은 섹션·`order` 순서로 파생하며, `required` 상태도 같은 값을 사용한다.
- 공개 공고 상세는 공고·공연사 제목, 모집 상태와 지원 시작·마감 시점, 모집 배역, 주요 전형 일정·제출 자료, 공연 상세·공고 안내 순서로 보여준다. 진행 중 공고만 모바일·태블릿 하단 CTA를 사용하고, 1200px 이상에서는 320px 요약 패널 CTA를 사용한다.
- 진행 중인 여러 배역 공고는 네이티브 radio 카드에서 하나를 고른 뒤 `지원서 작성` CTA를 사용할 수 있다. 선택 전 CTA는 `배역 선택하기`로 표시한다. 배역 구분이 없거나 하나뿐인 공고는 배역을 미리 선택해 별도 선택을 건너뛴다. 현재 지원서는 배역 하나에 속하며 중복 배역 지원은 지원하지 않는다. 향후 중복 지원을 허용하려면 배역별 심사 기록이 섞이지 않도록 공통 제출 묶음 아래에 배역별 지원서를 각각 생성하는 계약을 우선 검토한다.
- `UPCOMING`은 지원 시작일과 지원 불가 이유를, `CLOSED`는 마감 시각과 열람 가능 안내를 표시한다. 두 상태에서는 모바일 고정 CTA를 렌더링하지 않으며 공고와 배역만 열람할 수 있다. 존재하지 않는 식별자는 링크 원인과 `예술in 홈에서 공고 찾기` 행동을 보여주며 검색 노출하지 않는다.
- `지원서 작성`은 공고의 `applicationFields`에서 파생한 지원서로 이동한다. 현재는 `BASIC`(기본 정보), `INTRODUCTION`(자기소개), `MATERIALS`(사진·영상), `CAREER`(경력), `CUSTOM`(공고별 추가 질문) 섹션을 렌더링하며, 활성 필드가 없는 섹션은 단계와 본문에서 모두 제외한다. 서술형 항목의 `minLength`, 사진·영상의 필수 여부도 같은 설정으로 검증한다.
- 사진은 JPG·PNG·WEBP와 파일당 10MB만 허용하며, 추가 직후 `파일 확인 중`에서 `첨부 완료`로 목 상태가 전환된다. 잘못된 파일은 원인과 `첨부 실패`·재선택 동작을 같은 카드에 표시한다. 최대 4장을 등록하고, 첫 사진 또는 사용자가 지정한 사진이 대표 사진이다. 삭제는 브라우저 메모리의 미리보기만 제거한다.
- 영상은 URL 파싱 후 실제 호스트가 `youtube.com`, `www.youtube.com`, `m.youtube.com`, `youtu.be`인 일반·단축·Shorts·embed URL만 인정한다. 유효한 링크에는 연결 상태와 삭제 동작을 표시한다. 경력은 최대 10개까지 작품명·맡은 배역·연도를 반복 입력하거나 `경력 없음`을 선택할 수 있다.
- 공고 본문에는 공연사 소개만 간결하게 노출한다. 검토 화면은 영역별 수정, 누락 항목으로 이동하는 오류 요약, 개인정보 안내 동의, 전체 필수값 재검사를 제공한다. 실제 개인정보 수집 목적·보관 기간·파기 기준은 확정 전임을 표시한다. 제출 중에는 영역 수정과 동의 변경을 막고, 실패 후에는 입력값을 유지한 채 다시 제출할 수 있다. 완료 화면은 `YS-` 지원 조회 코드·제출 시각·공연·공고·배역, 회원가입 CTA와 다른 공고 최대 3개를 표시한다. 조회 코드는 `/apply/lookup`에서 연락처와 함께 재조회한다. 제출 스냅샷은 같은 숫자형 `ApplicationId`로 지원자 지원 이력과 공연사 1차 심사 풀에 함께 반영된다.
- 비회원 제출 응답은 7일 만료·1회용 `profileClaimToken`을 함께 발급한다. MSW 가입 API는 유효한 토큰의 지원서 소유권을 새 계정에 귀속하고 표준 11개 항목을 프로필에 복사한다. 토큰이 무효여도 가입은 성공하고 화면이 귀속 실패를 별도로 안내한다.
- 실제 임시 저장은 없으므로 값·사진·영상·경력·동의 중 하나라도 작성한 지원서는 `dirty` 상태다. 공고 상세로 돌아갈 때는 데이터 손실 확인 모달을, 새로고침·탭 닫기·문서 이탈에는 브라우저 기본 경고를 사용한다. 내부 단계 이동은 경고하지 않으며, 목 접수 완료 뒤에는 어느 이탈 경고도 표시하지 않는다. Provider는 현재·완료·오류·접근 가능 단계를 함께 제공해 검증을 통과한 단계만 다시 열 수 있다.
- `/apply/{postingId}` 본문은 `GET /api/public/postings/{postingId}`를 사용한다. 목 환경의 최초 SSR과 메타데이터는 서버 카탈로그 읽기 모델을 사용하고, 새로 만든 공고처럼 서버 목에 없는 항목은 브라우저 MSW API로 조회한다. 실제 API 환경에서는 `API_ORIGIN`의 같은 공개 API를 메타데이터와 최초 SSR이 함께 조회한다.
- 실제 연결 전에는 공개 공고 조회의 접근·마감 판정, 파일 저장·바이러스 검사·삭제, 조회 코드 보안·rate limit, 제출 실패 재시도 규칙, 개인정보 수집·보관·파기 정책과 외부 이메일 제출의 병행 여부를 확정해야 한다.

## API 계약

모든 경로는 Notion 정본에 따라 `/api` 아래에 둔다.

| 기능 | 메서드 | 경로 |
| --- | --- | --- |
| 사이드바 트리 | `GET` | `/api/navigation/tree` |
| 공연 목록·추가 | `GET`, `POST` | `/api/performances` |
| 공연 수정·삭제 | `PATCH`, `DELETE` | `/api/performances/{performanceId}` |
| 공고 목록·추가 | `GET`, `POST` | `/api/performances/{performanceId}/postings` |
| 공고 편집 초기값(프론트 제안) | `GET` | `/api/postings/{postingId}` |
| 공고 수정·삭제 | `PATCH`, `DELETE` | `/api/postings/{postingId}` |
| 배역 목록 | `GET` | `/api/postings/{postingId}/roles` |
| 공개 공고 상세 | `GET` | `/api/public/postings/{postingId}` |
| 공개 지원서 제출 | `POST` | `/api/public/applications` |
| 심사 화면 | `GET` | `/api/screenings/roles/{roleId}?round={1\|2\|3}` |
| 심사 결과·메모 저장 | `PATCH` | `/api/screenings/reviews` |
| 차수 마감 | `POST` | `/api/screenings/rounds/close` |

### 조회 규칙

- `GET /screenings/roles/{roleId}`의 `round`를 **비우면 서버가 아직 마감되지 않은 가장 이른 차수**를 골라 응답의 `round`에 담아 돌려준다. 클라이언트가 진입 차수를 몰라도 한 번에 들어갈 수 있다.
- `GET /performances/{performanceId}/postings`는 공고 목록과 함께 공연의 `roleTemplates`를 내려준다. 공고 추가 화면은 이 목록에서 모집 배역을 선택한다.
- 심사 화면 응답은 해당 차수의 **대상 전체**를 내려준다. 성별·나이·키·몸무게·조건 불일치 필터는 클라이언트가 건다. 배역당 지원자 수가 작아 지금은 서버 페이징이 필요 없다.
- 지원서 응답에는 조회 차수의 `review`와 함께 **차수별 기록 `reviewHistory`** 를 담는다. 아직 대상이 아니었던 차수는 `null`이라 화면에 `해당 없음`으로 뜬다.

### 변경 규칙

`PATCH /screenings/reviews`는 한 명과 여러 명을 같은 모양으로 처리한다.

```json
{
  "roleId": "po1_r1",
  "round": 1,
  "applicationIds": [101, 102],
  "status": "PASS",
  "memo": "",
  "note": ""
}
```

- `status`, `memo`, `note`는 모두 선택이다. 준 필드만 갱신한다.
- `status`가 `ETC`가 아니면 `memo`를 비운다.
- 1차에는 `ABSENT`를 저장할 수 없고, `ETC`를 저장할 때는 공백이 아닌 `memo`가 필요하다. 화면과 MSW가 모두 같은 규칙을 검증한다.
- 마감된 차수면 400.
- 해당 차수 대상이 아닌 지원서 식별자는 조용히 무시한다.

`POST /screenings/rounds/close`는 `{ "roleId": "...", "round": 1 }`을 받는다. 검토 대기가 남아 있거나 대상이 0명이면 400.

두 심사 변경 API 모두 **갱신된 심사 화면 한 벌을 그대로 돌려준다.** 마감의 경우 다음 차수 화면을 준다. 클라이언트가 재조회하지 않아도 되게 하려는 의도다.

`PATCH /postings/{postingId}`는 요청 필드를 기존 공고와 먼저 합쳐 완성 상태를 만든 뒤 생성과 같은 검증기를 적용한다. 시작일만 바꿔 종료일을 넘기거나, 잘못된 배역·인원·전형 순서·일정·지원서 항목을 부분 PATCH로 우회할 수 없다.

공개 제출과 내 지원서 수정도 같은 답변 검증기를 사용한다. 필수값, 알 수 없는·중복 키, 문자열·날짜·선택값·파일 배열·경력 배열·복합 신체값 구조와 최소 글자 수를 서버 계약 경계에서 다시 검사한다.

### 생성 규칙

`POST /performances`는 공연과 배역 템플릿을 함께 만든다.

```json
{
  "posterUrl": "data:image/webp;base64,...",
  "title": "뮤지컬 <새 작품>",
  "venue": "대학로예술극장",
  "roles": [
    {
      "name": "주연",
      "description": "성별 무관 · 20대",
      "gender": "ANY",
      "ageMin": 20,
      "ageMax": 29
    }
  ]
}
```

성공하면 갱신된 `PerformanceListResponse`를 돌려준다.

`POST /performances/{performanceId}/postings`는 공연의 배역 템플릿을 골라 실제 모집 배역을 만들고 모집·전형·지원서 설정을 저장한다. 현재 요청 body에도 `performanceId`가 있어 Notion 문서 안의 path/body 모순을 그대로 드러낸다. 백엔드 구현 전 한쪽으로 통일해야 한다.

```json
{
  "performanceId": "p1",
  "isOpenCall": false,
  "title": "2026 겨울 시즌 배우 모집",
  "recruitmentStart": "2026-08-10",
  "recruitmentEnd": "2026-08-31",
  "roles": [{ "templateId": "p1_t1", "quota": 1 }],
  "rounds": [
    { "round": 1, "name": "서류 심사", "date": "2026-09-02", "note": "온라인 검토" },
    { "round": 2, "name": "대면 오디션", "date": "2026-09-05", "note": "연습실 A" }
  ],
  "applicationFields": [
    { "id": "NAME", "key": "NAME", "label": "이름", "enabled": true, "required": true, "custom": false, "section": "BASIC", "inputType": "TEXT", "order": 10, "layout": "HALF", "config": { "placeholder": "이름을 입력해 주세요." } },
    { "id": "GENDER", "key": "GENDER", "label": "성별", "enabled": true, "required": true, "custom": false, "section": "BASIC", "inputType": "SELECT", "order": 40, "layout": "HALF", "config": { "options": ["여성", "남성", "응답하지 않음"] } },
    { "id": "custom-1", "label": "특기", "enabled": true, "required": false, "custom": true, "section": "CUSTOM", "inputType": "TEXT", "order": 10, "layout": "FULL", "config": { "placeholder": "특기를 입력해 주세요." } }
  ],
  "applicationGuide": "프로필 사진은 최근 6개월 이내 촬영본을 첨부해 주세요."
}
```

- 모집 배역은 하나 이상, 배역별 모집 인원은 1명 이상이어야 한다.
- `isOpenCall: true`이면 배역 구분 없이 접수하며 대표 모집 분야를 정확히 하나만 받는다.
- 모집 종료일은 시작일보다 빠를 수 없다.
- 1차 전형은 모집 종료일보다 빠를 수 없고 이후 일정은 차수 순서대로 입력한다.
- 현재 MVP는 기존 심사 화면과 맞춰 전형을 2개 이상 3개 이하로 받는다. 입력한 전형만 심사 스테퍼와 마감 흐름에 노출한다.
- 지원서 기본 항목과 사용자 정의 항목은 모두 사용 여부와 필수 여부를 독립적으로 저장한다.
- 각 지원서 항목은 `section`(BASIC, CUSTOM, CAREER, MATERIALS, INTRODUCTION), `inputType`, `order`, `layout`(FULL, HALF), `config`을 함께 저장한다. `config`은 placeholder, 선택지, 글자 수와 복합 입력의 하위 필드를 담는다.
- 공개 지원서는 BASIC, INTRODUCTION, MATERIALS, CAREER, CUSTOM 섹션을 모두 지원한다. 활성 필드가 하나도 없으면 해당 단계는 표시하지 않는다. 공고 상세의 제출 자료도 같은 활성 필드·필수 여부·섹션 순서에서 파생한다. 현재 MSW 제출 API와 조회 코드를 통해 흐름을 검증한다.
- 성공하면 해당 공연의 갱신된 `PostingListResponse`와 새 공고의 `createdPostingId`를 돌려준다.
- 공연사 화면은 `createdPostingId`로 `${origin}/apply/{postingId}` 형식의 공개 지원서 링크를 만들고, 생성 성공 화면에서 OTR 등 외부 공고에 붙여 넣을 수 있도록 복사 기능을 제공한다.
- 생성 이후에도 공연의 공고 카드, 공고의 배역 선택 화면과 지원자 심사 화면 상단에서 같은 공개 지원서 링크를 다시 복사할 수 있다.
- `/apply/{postingId}`는 기본 공고와 새로 생성한 공고 모두 공개 조회 API를 거쳐 상세·지원서 작성·검토·목 접수 완료로 연결한다. 제출하면 같은 지원서가 지원자 이력과 해당 배역의 공연사 심사 보드에 즉시 나타난다.

## MSW 운영 방식

- 핸들러: `frontend/src/mocks/handlers.ts`
- 목 데이터·상태: `frontend/src/mocks/auditions/`
  - `catalog.ts` — 공연·공고·배역 원본
- `create.ts` / `manage.ts` — 공연·공고 생성·수정·삭제와 식별자·진행 단계 생성
  - `applicants.ts` — 시드 고정 난수로 만든 지원서
  - `store.ts` — 심사 결과와 차수 마감 상태(브라우저 메모리)
  - `aggregate.ts` / `serialize.ts` — 집계와 응답 변환
- **시드를 고정**했다(`AUDITION_SEED = 20260803`). 새로고침해도 같은 인원·통계가 나와야 화면을 비교할 수 있다.
- 목 데이터는 브라우저 메모리에 있으므로 새로고침하면 심사 결과와 마감 상태가 초기화된다.
- 추가한 공연·공고도 브라우저 메모리에만 있으므로 새로고침하면 사라진다.
- 지난 시즌 공고(`finished: true`)는 전 차수 심사 이력이 채워진 상태로 시작한다. 마감된 화면이 어떻게 보이는지 바로 확인하기 위해서다.
- 지원자 사진은 `i.pravatar.cc`를 쓰고, 실패하면 이름 첫 글자를 넣은 인라인 SVG로 대체한다. 최적화 이득이 없어 `next/image`를 `unoptimized`로 둔다.
- 성별·나이 조건을 벗어난 지원자를 약 13% 섞어 넣는다. 조건 불일치 표시가 실제로 보이는지 확인하기 위한 의도된 노이즈다.
- 기본값은 MSW 사용이며, 실제 백엔드 연결 시 `NEXT_PUBLIC_API_MOCKING=disabled`로 비활성화한다.

## 권한 원칙

- 클라이언트는 공연사 ID를 어떤 요청에도 넣지 않는다.
- 서버는 인증 정보에서 공연사 ID를 확인한다.
- 조회·변경 모두 인증된 공연사에 속한 공연·공고·배역·지원서만 다룬다.
- 현재 MSW는 소유권 검사를 하지 않는다. 목 데이터 전체가 한 공연사의 것이라고 가정한다. **백엔드 구현 시에는 반드시 소유권 검사를 넣어야 한다.**

## 의도적으로 뺀 것

- 오디션 슬롯 판 / 일정 배정
- 결과 일괄 연락, 공지문 생성, 발송 이력

서비스는 결과를 대신 발송하지 않는다. `검토 완료` 탭에서 **합격자 연락처를 모아 복사**하는 데까지만 돕고, 연락은 공연사가 쓰던 방식(단체 채팅방·문자·전화)대로 한다. 연락처 모아보기 모달과 인쇄/PDF 출력이 그 역할을 한다.

## 현재 한계

- 필터가 클라이언트 전용이라 지원자가 크게 늘면 서버 필터·페이징이 필요하다.
- 목록 정렬은 접수 순서 그대로다. 정렬 기준 선택은 아직 없다.
- 공고 수정 폼 초기값을 위한 `GET /postings/{postingId}`는 프론트엔드 제안 계약이며 현재 Notion API 목록에는 없다.
- 생성한 공고는 지원자가 0명인 상태로 시작한다. 공개 상세·제출·조회·심사 반영과 claim 가입 귀속은 하나의 MSW 메모리 흐름으로 연결되지만 실제 파일 저장과 영속 DB는 없다.
- 인쇄는 브라우저 인쇄 대화상자를 그대로 쓴다. 팝업이 차단되면 토스트로 안내만 한다.

## 작업 후 문서화

이 영역을 구현하거나 변경한 뒤에는 팀 공유가 필요한 내용이 있는지 확인하고, 필요한 경우 이 문서의 도메인 계층·API 계약·MSW 운영 방식을 실제 구현과 함께 갱신한다. 공통 기준은 [문서 운영 원칙](./README.md)을 따른다.
