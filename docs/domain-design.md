# 도메인 설계 기준과 추가 결정 사항

> 기준일: 2026-08-12<br>
> 최초 기준: [Notion 도메인 설계](https://app.notion.com/p/3b94b21dcd3c80478a8ce0bb76965dc9)<br>
> 후속 결정: [0008 지원서·프로필·배역 규칙](./decisions/0008-application-profile-and-role-rules.md), [0009 로컬 우선 서버 Draft 동기화](./decisions/0009-local-first-server-draft.md), [0010 Backend 첫 영속화 구조](./decisions/0010-backend-persistence-slice.md), [0011 활성 공연사와 mock seed 이관 경계](./decisions/0011-active-company-and-seed-boundaries.md), [0012 Frontend·MSW·Backend 단일 API 계약](./decisions/0012-frontend-msw-backend-contract.md)

이 문서는 Notion의 최초 설계와 이후 팀이 확정한 도메인 결정을 개발자가 읽기 쉬운 형태로 정리한다. 현재 코드나 다른 문서가 이 내용과 다르면 **결정된 설계**, **현재 구현**, **추가 설계 필요**를 구분한다. 추가 설계 항목은 답이 아니라 팀이 결정해야 할 질문이다.

## 결정된 설계

### 회원 구조

- 지원자와 공연사를 분리한다.
- 로그인 자격은 공통 `Account`가 소유하고 지원자와 공연사 멤버십은 별도 도메인 레코드로 분리한다.
- 한 계정은 지원자이면서 여러 공연사의 멤버가 될 수 있다.
- MVP 공연사 계정의 역할은 `ADMIN` 하나만 둔다.
- 공연사 전용 API는 세션의 소속 검증된 `activeCompanyId`를 사용한다. 단일 멤버십 로그인과 공연사 가입에서는 자동 선택하고 별도 전환 API로 바꾼다.
- 향후 팀원 기능을 도입할 때 초대로 가입하는 `TEAM_MEMBER` 역할을 추가할 수 있도록 역할을 ENUM 필드로 관리한다.
- `TEAM_MEMBER`의 권한과 초대·탈퇴·삭제, `ADMIN` 양도 절차는 아직 정하지 않았다.

### 지원 흐름

1. 지원자는 공고에서 지원을 시작한다.
2. 로그인 세션이 있으면 이전 프로필 정보를 이용할 수 있다.
3. 로그인 세션이 없으면 이전 기본 프로필을 불러올지 묻는다. 기존 가입자는 로그인할 수 있고 처음 이용하는 사용자는 불러오지 않고 작성할 수 있다.
4. 로그인 여부와 관계없이 지원서를 작성하고 사진을 선택할 수 있다.
5. 작성 내용과 사진은 로그인 전에도 IndexedDB와 서버 Draft에 함께 저장한다.
6. 로그인·회원가입 화면을 다녀와도 작성 중인 Draft를 복원한다.
7. 로그인 또는 회원가입이 완료되면 현재 브라우저의 서버 Draft와 임시 파일을 해당 계정에 자동 연결한다.
8. 계정에 같은 공고의 기존 Draft가 있으면 수정 시각이 더 최신인 Draft가 이전 Draft 전체를 덮어쓴다.
9. 회원가입이 최종 제출 과정에서 완료되면 연결한 Draft를 곧바로 제출한다.
10. 최종 제출 시 서버 시각 기준으로 모집 중인지 다시 검사하고, 마감됐으면 제출을 즉시 차단한다.
11. 제출에 성공하면 Draft의 내용을 불변 지원서 스냅샷으로 확정한다. 제출된 지원서는 인증 계정에 귀속된다.

로그인 전·후 모두 IndexedDB에 먼저 저장한 뒤 서버 Draft와 지연·묶음 동기화한다. 로그인 전 Draft와 사진은 계정에 속하지 않은 임시 데이터이며, 인증이 완료되면 계정 소유로 전환한다. 최종 제출 전 Draft는 공연사에 공개하지 않는다. 마감으로 제출하지 못한 Draft는 전형 종료 후 별도 기간까지 유지한 뒤 삭제하되 정확한 기간은 추가 결정한다. 제출 성공 전까지 IndexedDB 사본을 복구용으로 유지한다. 인증 전 Draft의 식별·접근 통제, 최신 수정본 판정 방식, 두 저장소의 보관기간과 동기화 주기는 추가 결정이 필요하다.

### 지원서

#### 배역과 지원 단위

- 공연사가 복수 배역 지원을 허용한 공고에서는 하나의 지원서로 여러 배역을 선택할 수 있다.
- 복수 배역을 허용하지 않은 공고에서는 하나의 배역만 선택한다.
- 동일 계정은 같은 공고에 지원서를 하나만 제출할 수 있다. 복수 배역 선택은 중복 지원으로 보지 않는다.
- 복수 배역 지원서는 심사 화면에서 선택한 배역마다 별도 심사 대상으로 표시한다.
- 심사 결과는 `(지원서, 배역, 차수)`별로 관리하고 다른 배역이나 차수의 결과를 덮어쓰지 않는다.
- 별도의 `자유 배역` 타입은 두지 않는다. 공연사가 일반 배역 하나를 `자유`라는 이름으로 추가한다.
- 공고의 배역이 하나뿐이면 지원자의 배역 선택 화면을 생략한다.

#### 기본 정보

다음 8개 항목은 필수다.

- 이름
- 키
- 몸무게
- 생년월일(연·월·일)
- 성별
- 연락처
- 이메일
- 거주지

#### 공연사가 선택하는 추가 정보

공연사는 공고에 필요한 항목을 선택할 수 있고 값은 nullable이다.

- 학력
- 경력
- 링크
- 국적
- 자기소개
- 특기
- 취미
- 군필 여부

#### 사진

- 사진은 최대 10장이다.
- 공연사는 지원서 양식에서 사진 유형 설명과 요구 장수를 여러 개 지정할 수 있다.
- 예를 들어 `전신사진 3장`, `얼굴사진 1장`을 요구하면 지원자는 각 유형에 지정된 장수만큼 사진 보관함에서 선택하거나 새로 추가한다.
- 유형별 요구 장수의 합은 전체 최대 10장을 넘을 수 없다.
- 로그인 전에도 사진을 IndexedDB와 서버 Draft의 임시 파일로 보관한다. 이 파일은 개인 사진 보관함에 속하지 않는다.
- 인증 후에는 Draft와 임시 파일을 계정에 연결하고, 프로필 저장에 동의한 사진만 개인 사진 보관함에서도 재사용한다.
- 개인 사진 보관함에서 사진을 삭제해도 해당 사진을 사용 중인 Draft와 제출 지원서는 독립 참조를 유지한다.

#### 커스텀 질문

- 공연사는 공고별 커스텀 질문을 여러 개 추가할 수 있다.
- MVP 질문 유형은 단일 선택, 단답, 장답, 복수 선택이다.
- 첫 지원서가 제출된 뒤에는 질문의 문구·유형·선택지·순서·삭제를 변경할 수 없다.
- 공연사는 지원 접수를 시작하기 전에 미리보기로 질문을 확인한다.
- 커스텀 답변은 재사용하는 개인 프로필에 저장하지 않는다.

#### 프로필 재사용과 제출 스냅샷

- 재사용 프로필에는 하나의 선택 동의로 기본 정보 8개, 학력·경력·링크 등 추가 정보와 개인 사진 보관함을 저장한다.
- 지원서를 작성할 때 해당 공연사가 요구하는 항목과 겹치는 프로필 값만 자동으로 채운다.
- 자동 채움 값을 지원서에서 수정해도 프로필은 자동으로 바꾸지 않는다. 제출 화면에서 `프로필에도 저장`을 선택한 경우에만 프로필을 갱신한다.
- 공고별 커스텀 질문 답변은 프로필에 저장하지 않고 지원할 때마다 새로 작성한다.
- 제출 시 기본·추가 정보, 선택한 사진, 커스텀 답변과 선택 배역을 지원서 스냅샷으로 보존한다.
- 제출 뒤 프로필을 수정하거나 개인 사진 보관함에서 사진을 삭제해도 과거 지원서와 공연사에 전달된 내용은 바뀌지 않는다.

## 현재 구현 상태와 차이

### Backend

`backend/`에는 Flyway 기반 MySQL 스키마와 분리된 도메인/JPA 모델이 있다. Account 가입·세션 인증·CSRF, Applicant 프로필·자동 채움, 활성 공연사 문맥, 공개 공고, 공연·공고·배역·차수 관리, 계정 소유 Draft, 최종 제출, 내 지원서와 배역별 심사 API를 제공한다. 제출 트랜잭션은 서버가 공고·배역·필드·동의를 다시 조회해 불변 JSON Snapshot을 만들고 `(지원서, 배역, 차수)`별 첫 심사 대상을 함께 생성한다.

Draft 전체 교체는 `expectedRevision`이 현재 revision과 같고 `clientModifiedAt`이 기존 값보다 늦을 때만 허용한다. 같은 `(account, posting)` Draft 연결 시에도 이 비교로 한 벌만 유지한다. 익명 Draft와 파일 API는 접근 증명·개인정보·정리 계약이 확정되지 않아 공개하지 않는다.

구조상 남은 차이는 일부 `infrastructure/*ServiceAdapter`가 application orchestration과 트랜잭션까지 담당한다는 점이다. Domain 규칙과 application port는 분리돼 있지만, 승인된 계층 설계대로 application service와 output port로 완전히 분해하는 작업은 남아 있다.

### Frontend·MSW

Frontend와 MSW는 Backend와 같은 `/api/v1` 계약을 사용한다. 실제 로그인·세션·CSRF, 공개 공고, 프로필, 계정 Draft·최종 제출, 내 지원서, 공연·공고와 배역별 심사 흐름을 같은 feature API로 호출한다. 제출 지원서 수정과 비로그인 조회 흐름은 제거했고 사진 상한은 10장, 이름·키·몸무게·생년월일·성별·연락처·이메일·거주지는 항상 필수로 고정했다.

아직 목표 정책과 다른 부분은 다음과 같다.

- 작성 중 값을 IndexedDB에 저장하고 지연·묶음 동기화하는 브라우저 계층은 아직 없다. 현재 계정 Draft는 최종 제출 직전에 동기화한다.
- 인증 전 Draft 복원·계정 자동 연결과 로그인 왕복 후 폼 복원은 미구현이다.
- 사진은 최대 10장을 선택할 수 있지만 서버 파일 업로드와 공연사가 지정하는 사진 유형별 설명·정확한 장수는 미구현이다.
- 커스텀 질문 UI는 단답형 추가만 제공한다. 단일 선택·장답·복수 선택 편집은 후속 구현이 필요하다.
- 제출 화면의 `프로필에도 저장` 선택과 그에 따른 프로필 갱신은 아직 구현되지 않았다. 제출 스냅샷은 프로필과 독립적으로 저장된다.
- 공연사 화면 집계 중 지원자 수·진행률은 전용 요약 API가 없어 일부 목록에서 기본값으로 표시된다. 심사 보드 자체의 집계는 실제 Backend 응답을 사용한다.
- Draft·계정·제출 데이터의 보관기간에 따른 자동 삭제 작업과 관리자 감사 로그는 아직 없다. 운영 배포 전 보관기간 결정과 삭제·감사 구현이 필요하다.
