이 문서는 Notion의 최초 설계와 이후 팀이 확정한 도메인 결정을 개발자가 읽기 쉬운 형태로 정리한다. 현재 코드나 다른 문서가 이 내용과 다르면 **결정된 설계**, **현재 구현**, **추가 설계 필요**를 구분한다. 추가 설계 항목은 답이 아니라 팀이 결정해야 할 질문이다.

## 결정된 설계

### 회원 구조

- 배우와 기획사/제작사를 분리한다.
- 배우는 별도 회원가입 화면을 두지 않고 카카오·네이버·Google 소셜 로그인만 사용한다. 처음 소셜 로그인하면 배우 계정을 자동 생성한다.
- 기획사/제작사는 이메일·비밀번호로 로그인하며 기획사/제작사명, 휴대폰 번호, 이메일, 비밀번호로 가입한다. 비밀번호 확인과 필수 약관 동의는 가입 보조 입력으로 유지한다.
- 기획사/제작사 계정 상태는 `PENDING`, `ACTIVE` 두 개다. 가입 직후 `PENDING`이며 기획사/제작사 정보 설정은 가능하지만 공연 조회·관리 기능은 사용할 수 없다.
- `PENDING` 계정은 등록한 휴대폰과 이메일로 가입 안내를 받고 운영진 수동 확인 후 `ACTIVE`로 전환된다. 카카오톡 채널 문의로 빠른 확인을 요청할 수 있다.
- MVP 기획사/제작사 계정의 역할은 `ADMIN` 하나만 둔다.
- 향후 팀원 기능을 도입할 때 초대로 가입하는 `TEAM_MEMBER` 역할을 추가할 수 있도록 역할을 ENUM 필드로 관리한다.
- `TEAM_MEMBER`의 권한과 초대·탈퇴·삭제, `ADMIN` 양도 절차는 아직 정하지 않았다.

### 지원 흐름

1. 배우는 공고에서 지원을 시작한다.
2. 로그인 세션이 있으면 이전 프로필 정보를 이용할 수 있다.
3. 로그인 세션이 없으면 이전 기본 프로필을 불러올지 묻는다. 기존 가입자는 로그인할 수 있고 처음 이용하는 사용자는 불러오지 않고 작성할 수 있다.
4. 로그인 여부와 관계없이 지원서를 작성하고 사진을 선택할 수 있다.
5. 작성 내용과 사진은 로그인 전에도 IndexedDB와 서버 Draft에 함께 저장한다.
6. 소셜 로그인 화면을 다녀와도 작성 중인 Draft를 복원한다.
7. 소셜 로그인이 완료되면 현재 브라우저의 서버 Draft와 임시 파일을 해당 계정에 자동 연결한다. 처음 로그인한 배우는 이때 계정을 자동 생성한다.
8. 계정에 같은 공고의 기존 Draft가 있으면 수정 시각이 더 최신인 Draft가 이전 Draft 전체를 덮어쓴다.
9. 최종 제출 과정에서 소셜 로그인이 완료되면 연결한 Draft의 최종 검토를 이어간다.
10. 최종 제출 시 서버 시각 기준으로 모집 중인지 다시 검사하고, 마감됐으면 제출을 즉시 차단한다.
11. 제출에 성공하면 Draft의 내용을 불변 지원서 스냅샷으로 확정한다. 제출된 지원서는 인증 계정에 귀속된다.

로그인 전·후 모두 IndexedDB에 먼저 저장한 뒤 서버 Draft와 지연·묶음 동기화한다. 로그인 전 Draft와 사진은 계정에 속하지 않은 임시 데이터이며, 인증이 완료되면 계정 소유로 전환한다. 최종 제출 전 Draft는 기획사/제작사에 공개하지 않는다. 마감으로 제출하지 못한 Draft는 전형 종료 후 별도 기간까지 유지한 뒤 삭제하되 정확한 기간은 추가 결정한다. 제출 성공 전까지 IndexedDB 사본을 복구용으로 유지한다. 인증 전 Draft의 식별·접근 통제, 최신 수정본 판정 방식, 두 저장소의 보관기간과 동기화 주기는 추가 결정이 필요하다.

### 공연과 공고 관리

- 공연은 포스터, 공연명, 장소명, 도로명주소·상세주소·우편번호·좌표와 배역 템플릿을 가진다. 공연 배역 템플릿은 배역 이름과 한 줄 설명만 보관한다.
- 모집 인원, 성별, 최소·최대 나이 같은 지원 조건은 공연이 아니라 공고의 모집 분야에 둔다.
- 신규 공고는 배역별 모집만 사용한다. 과거 `isOpenCall` 데이터는 읽기 호환을 위해 유지하지만 신규 공고에는 만들지 않는다.
- 공고를 만들 때 공연 포스터를 공고 대표 이미지의 초기 스냅샷으로 복사하고 공고에서 교체할 수 있다. 이후 공연 포스터가 바뀌어도 기존 공고와 제출 지원서의 대표 이미지는 바뀌지 않는다.
- 공고는 대표 이미지와 별개로 배우가 보는 공고 본문에 표시할 상세 이미지 하나를 선택적으로 가진다.
- 공연 장소는 공연에서 관리한다. 공고에는 공연 장소를 중복 저장하지 않고, 공고별로 달라질 수 있는 연습 장소명과 도로명주소·상세주소·우편번호·nullable 좌표를 선택적으로 둔다.
- 공연 시작일은 필수, 공연 종료일은 선택이다. 종료일을 두지 않은 공연은 오픈런으로 해석하고 화면에도 오픈런으로 표시한다. 모집 시작·종료는 분 단위 일시, 전형 일정은 날짜로 기록한다.
- 전형은 기본 1차에서 시작하고 최대 5차까지 추가한다. 각 차수는 전형 이름, 일정, 안내 사항을 가진다.
- 공고 상태는 `DRAFT`(작성 중), `UPCOMING`(진행 예정), `OPEN`(진행 중), `RECRUIT_CLOSED`(접수 마감), `FINISHED`(전형 종료) 다섯 단계다.
- 지원 안내는 최대 2,000자로 작성한다.
- 공고 생성 뒤 수정할 수 있는 항목은 공연·모집·전형 일정뿐이다. 모집 시작 또는 첫 지원서 이후에는 모집 시작을 잠그고 모집 종료는 연장만 허용하며 완료한 전형은 잠근다.
- 공연 관리 목록은 공연별 카드로 제공한다. 공연 카드를 선택하면 해당 공연의 상세 공고 관리 화면으로 이동한다.

### 지원서

#### 공고 작성

- 공고는 공연에 속하고 `DRAFT → PUBLISHED → CLOSED` 생명주기를 가진다.
- 공고명과 공연 기간을 완성한 첫 저장에서 DRAFT를 만들고 배역·일정·지원 폼을 독립된 섹션으로 저장한다.
- 기본 정보는 공고명, 공연 시작일과 선택적인 종료일이다. 종료일이 없으면 오픈런이다.
- DRAFT는 아직 생성하지 않은 섹션을 허용하고 게시 시 모든 섹션의 필수 규칙을 검사한다.
- 상세 규칙과 구현 순서는 [공고 관리](./backend/audition-management.md)를 따른다.

#### 배역과 지원 단위

- 기획사/제작사가 복수 배역 지원을 허용한 공고에서는 하나의 지원서로 여러 배역을 선택할 수 있다.
- 복수 배역을 허용하지 않은 공고에서는 하나의 배역만 선택한다.
- 동일 계정은 같은 공고에 지원서를 하나만 제출할 수 있다. 복수 배역 선택은 중복 지원으로 보지 않는다.
- 복수 배역 지원서는 심사 화면에서 선택한 배역마다 별도 심사 대상으로 표시한다.
- 심사 결과는 `(지원서, 배역, 차수)`별로 관리하고 다른 배역이나 차수의 결과를 덮어쓰지 않는다.
- 배우의 내 지원서에서는 지원한 배역마다 전형 진행 상황을 구분해 표시한다. 검토 중인 내부 결과는 노출하지 않고 해당 배역의 차수가 마감된 뒤 확정 결과만 공개한다.
- 별도의 `자유 배역` 타입은 두지 않는다. 기획사/제작사가 일반 배역 하나를 `자유`라는 이름으로 추가한다.
- 공고의 배역이 하나뿐이면 배우의 배역 선택 화면을 생략한다.

#### 기본 정보

다음 8개 항목 중 기획사/제작사가 공고에서 선택한 항목만 지원서에 표시하며, 선택한 기본 정보는 필수다.

- 이름
- 키
- 몸무게
- 생년월일(연·월·일)
- 성별
- 연락처
- 이메일
- 거주지

#### 기획사/제작사가 선택하는 추가 정보

기획사/제작사는 공고에 필요한 항목을 선택할 수 있고 값은 nullable이다.

- 학력
- 경력
- SNS·외부 링크
- 국적
- 자기소개
- 특기
- 취미
- 군필 여부

#### 사진

- 개인 사진 보관함에는 최대 20장을 저장하고 한 장을 대표 프로필 사진으로 지정한다.
- 기획사/제작사는 공고 양식에서 지원서에 첨부할 사진 장수를 1~10장으로 설정한다.
- 배우는 보관함 사진 또는 새 사진 중 공고가 요청한 장수만큼 선택하며 한 지원서에는 최대 10장만 첨부한다.
- 기획사/제작사는 지원서 양식에서 사진 유형 설명과 요구 장수를 여러 개 지정할 수 있다.
- 새 공고의 사진 요구는 `프로필 사진 1장`으로 시작하며 사진 유형 설명은 최대 255자다.
- 예를 들어 `전신사진 3장`, `얼굴사진 1장`을 요구하면 배우는 각 유형에 지정된 장수만큼 사진 보관함에서 선택하거나 새로 추가한다.
- 유형별 요구 장수의 합은 전체 최대 10장을 넘을 수 없다.
- 로그인 전에도 사진을 IndexedDB와 서버 Draft의 임시 파일로 보관한다. 이 파일은 개인 사진 보관함에 속하지 않는다.
- 인증 후에는 Draft와 임시 파일을 계정에 연결하고, 프로필 저장에 동의한 사진만 개인 사진 보관함에서도 재사용한다.
- 개인 사진 보관함에서 사진을 삭제해도 해당 사진을 사용 중인 Draft와 제출 지원서는 독립 참조를 유지한다.

#### 영상

- 개인 영상 보관함에는 YouTube 공개·일부공개 링크를 최대 10개까지 저장한다.
- 프로필 화면은 링크를 임베드해 미리보기로 제공하며 영상 파일 자체를 업로드하지 않는다.
- 영상 추가·삭제·순서 변경은 각각 즉시 저장한다.
- 기획사/제작사는 공고 지원 폼에서 `자유 연기 영상`처럼 제출할 영상의 설명을 최대 10개까지 추가한다. 새 공고는 영상 요구 0개로 시작한다.
- 영상 요구 설명은 항목별 최대 255자다.
- 배우는 활성화된 각 영상 요구에 맞는 YouTube 링크를 하나씩 제출한다.

#### 커스텀 질문

- 기획사/제작사는 공고별 커스텀 질문을 여러 개 추가할 수 있다.
- 현재 MVP 질문 유형은 텍스트 하나이며, 기획사/제작사가 질문별 필수·선택을 정한다.
- 커스텀 질문 문구는 최대 255자다.
- 커스텀 질문의 답변은 문항별 최대 2,000자다.
- 첫 지원서가 제출된 뒤에는 질문의 문구·유형·선택지·순서·삭제를 변경할 수 없다.
- 기획사/제작사는 지원 접수를 시작하기 전에 미리보기로 질문을 확인한다.
- 커스텀 답변은 재사용하는 개인 프로필에 저장하지 않는다.

#### 프로필 재사용과 제출 스냅샷

- 재사용 프로필에는 하나의 선택 동의로 기본 정보 8개, 학력·경력·링크 등 추가 정보, 개인 사진·영상 보관함을 저장한다.
- 지원서를 작성할 때 해당 기획사/제작사가 요구하는 항목과 겹치는 프로필 값만 자동으로 채운다.
- 자동 채움 값을 지원서에서 수정해도 프로필은 자동으로 바꾸지 않는다. 제출 화면에서 `프로필에도 저장`을 선택한 경우에만 프로필을 갱신한다.
- 공고별 커스텀 질문 답변은 프로필에 저장하지 않고 지원할 때마다 새로 작성한다.
- 제출 시 기본·추가 정보, 선택한 사진, 커스텀 답변과 선택 배역을 지원서 스냅샷으로 보존한다.
- 제출 뒤 프로필을 수정하거나 개인 사진 보관함에서 사진을 삭제해도 과거 지원서와 기획사/제작사에 전달된 내용은 바뀌지 않는다.

## 현재 구현 상태와 차이

### Backend

`backend/`에는 파일 직접 업로드, 공연·배역 생성·수정과 공고 DRAFT 생성·기본 정보 저장이 구현되어 있다.
공고의 배역·일정·지원 폼·게시와 회원, 기획사/제작사, 프로필, 지원서, 사진 보관함은 아직 구현되지 않았다.

### Frontend·MSW·기존 문서

- 제출 지원서는 내 지원서에서 읽기 전용 스냅샷으로 표시하고 일반 수정 UI를 제공하지 않는다.
- 내 지원서 목록은 현재 브라우저 IndexedDB의 작성 중 Draft와 제출 완료 스냅샷을 구분한다. 제출 완료 건은 지원서 1개와 선택한 배역 수, 배역별 공개 전형 상태를 표시한다.
- 제출 성공 시 현재 브라우저의 해당 Draft를 삭제한다. 서버 Draft와 다른 기기의 Draft 목록은 아직 구현하지 않았다.
- 기본 정보와 nullable 추가 정보 8개를 분리했다. 공고에서 선택한 기본 정보는 필수이며 추가 정보는 nullable이다.
- 공고 설정에서 `{사진 유형 설명, 요구 장수}`를 여러 개 추가하고 합계를 최대 10장으로 제한한다. 배우 화면은 유형별 요구를 안내하고 전체 합계 장수를 검증하지만, 각 사진을 특정 유형에 연결하는 저장 계약은 아직 없다.
- 공고 지원 안내와 커스텀 답변은 각각 최대 2,000자로 제한한다. 영상 요구는 0개로 시작해 설명을 최대 10개까지 추가하며, 배우 지원서와 제출 스냅샷은 요구 순서대로 링크 배열을 보관한다.
- 공연 포스터·도로명주소, 이름·설명만 갖는 공연 배역, 공고별 지원 조건·대표 이미지 스냅샷·선택 상세 이미지·구조화된 연습 장소 주소·공연 기간·분 단위 모집 기간·최대 5차 전형을 MSW에 반영했다. 상세 이미지는 공개 공고 본문에 표시한다. 공연 장소와 연습 장소는 같은 주소 검색·지도 UI를 사용하며, 카카오 지도 키가 없으면 주소는 표시하지만 좌표 검색과 지도 렌더링은 동작하지 않는다.
- `/producers/performances`는 공연 카드 목록이며 카드를 선택하면 해당 공연의 공고 관리 화면으로 이동한다. 공연별 공고 화면은 상태 필터와 검색을 갖춘 목록으로 공고 관리와 배우 관리를 분리하며, 공개 공고 보기와 `지원자 관리`를 각각 제공한다. `GET /api/performances`는 카드 통계 계산을 위한 공고 요약을 포함하고, 공고 수정 화면은 일정 항목만 제공한다.
- 공고 상태 표시 타입은 작성 중·진행 예정·진행 중·접수 마감·전형 종료를 지원한다. 현재 공고 생성 API와 화면은 완성된 공고 등록만 제공하며, 작성 중 공고를 생성·갱신하는 임시 저장 계약과 버튼은 아직 구현하지 않았다.
- 프로필은 공고별 커스텀 답변을 보관하지 않는다.
- 프로필 화면은 사진 최대 20장, YouTube 영상 최대 10장을 별도 탭에서 관리하고 추가·삭제·순서·대표 사진 변경을 MSW에 즉시 저장한다. 실제 파일 업로드와 영속 저장 API는 구현하지 않았다.
- 복수 배역 선택 UI와 `(지원서, 배역, 차수)` 심사 저장 키를 적용했다.
- `/apply/lookup`은 로그인 후 내 지원서로 이동하게 전환했고, 최종 검토 화면은 인증 전 제출을 차단한다.
- 공개 지원서는 공고별 입력값, 선택 배역, 진행 단계와 사진 Blob을 IndexedDB에 저장한다. 실제 저장 결과에 따라 `저장 중`, `이 기기에 저장됨`, `저장 실패`를 표시하고 저장되지 않은 변경이 있을 때만 공고 이동·새로고침·탭 닫기를 경고한다.
- 같은 브라우저에서는 새로고침과 공고 상세 왕복 뒤 Draft를 복원한다. 소셜 로그인 뒤 돌아올 경로에도 로컬 Draft 재개 정보를 유지하지만, 현재 인증 여부는 목 쿼리 흐름으로 표현하며 서버 Draft 동기화·계정 자동 연결·다른 기기 이어쓰기는 구현하지 않았다.
- `/login`은 일반 진입에서 배우·기획사/제작사 유형을 선택한다. 배우는 카카오·네이버·Google 버튼만, 기획사/제작사는 이메일·비밀번호 입력만 표시한다. 배우 소셜 로그인은 프론트 전용 불투명 자격값을 React 상태에 보관해 다음 화면에서 재사용하지만 새로고침 복원과 실제 OAuth·서버 세션은 구현하지 않았다.
- `/signup`은 기획사/제작사 전용이다. MSW 가입은 기획사/제작사 계정을 `PENDING`으로 만들고 기획사/제작사 정보 설정으로 이동한다. `PENDING` 세션은 정보 설정 외 기획사/제작사 화면에서 인증 필요 안내와 카카오톡 문의 링크를 표시한다.
- 실제 카카오·네이버·Google OAuth, 기획사/제작사 세션 로그인, 가입 직후 문자·이메일 발송과 운영진의 `PENDING → ACTIVE` 변경은 구현하지 않았다.
- `returnTo`가 `/apply/{postingId}`인 로그인은 일반 인증 화면과 구분해 공연·공고·검증된 선택 배역, 현재 브라우저에만 저장되는 Draft 범위와 인증 후 최종 검토 복귀를 안내한다. 인증 취소는 목 인증 상태를 만들지 않고 같은 브라우저의 로컬 Draft만 다시 연다.

프론트엔드·MSW는 위 정책을 확인할 수 있는 UI와 시드 데이터를 제공한다. IndexedDB 사본은 서버에 전송되지 않으며 기획사/제작사에 공개되지 않는다. 인증 전 Draft 보호와 계정 연결을 포함한 실제 서버 API 경로·요청·응답은 추가 결정 후 구현한다.

## 문서 적용 원칙

- **결정된 설계**만 현재 도메인 기준으로 사용한다.
- **현재 구현 상태와 차이**는 구현 사실이며 목표 정책이 아니다.
- 체크리스트의 답이 결정되면 이 문서와 관련 flowchart·API·정책 문서를 함께 갱신한다.
- 새 Entity, 테이블, API 구조를 이 문서에서 임의로 확정하지 않는다.
