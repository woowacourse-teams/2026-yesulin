# 도메인 설계 기준과 추가 결정 사항

> 기준일: 2026-08-23<br>
> 최초 기준: [Notion 도메인 설계](https://app.notion.com/p/3b94b21dcd3c80478a8ce0bb76965dc9)<br>
> 관련 설계의 배경은 [결정 기록](./decisions/README.md)에서 필요한 항목만 확인한다.

이 문서는 팀이 확정한 현재 비즈니스 규칙의 정본이다. 현재 코드나 다른 문서가 이 내용과 다르면 **결정된 설계**, **현재 구현**, **추가 설계 필요**를 구분한다. 추가 설계 항목은 답이 아니라 Backend 구현 또는 출시 전에 팀이 결정해야 할 질문이다.

## 결정된 설계

### 회원·인증

- 인증 자격은 HttpOnly Cookie 기반 서버 Session으로 전달한다. 브라우저 JavaScript가 인증 자격을 직접 읽거나 저장하지 않는다.
- 배우와 기획사/제작사는 인증 주체와 계정을 완전히 분리한다. 같은 이메일을 사용해도 유형 간 계정을 자동 병합하지 않으며 한 유형의 세션으로 다른 유형의 권한을 얻을 수 없다.
- 배우는 카카오·네이버·Google 소셜 로그인만 사용하며 첫 로그인 시 배우 계정을 생성한다. 동일 이메일의 기존 배우 계정이 발견되어도 자동 연결하지 않고, 기존 가입 안내와 본인의 명시적 연결 요청·확인을 거친 뒤에만 소셜 제공자를 연결한다.
- 기획사/제작사는 이메일·비밀번호로 가입·로그인한다. 현재 MVP에서는 가입 직후 `ACTIVE`로 생성해 공연·공고·심사 기능을 바로 사용한다. MVP 이후 이메일·기획사 인증을 도입할 때 `PENDING` 접근 제한과 운영진 확인 흐름을 활성화한다.
- MVP는 `1 Company = 1 ADMIN 계정`만 허용한다. 한 계정의 복수 Company 관리와 팀원·직원 계정은 지원하지 않는다.
- 만 14세 미만 배우도 소셜 로그인에 따른 계정 생성까지는 허용할 수 있으나 지원서 제출은 허용하지 않는다. 제출 시 생년월일로 나이를 검증해 만 14세 미만이면 서버에서 차단한다.
- 약관·개인정보 동의 이력은 동의 주체, 문서 종류와 버전, 동의 시각, 동의 당시 표시한 핵심 내용을 식별 가능하게 저장한다. 현재 약관 문자열을 회원 행의 boolean 하나로만 저장하지 않는다.
- 회원 탈퇴 Backend 기능은 MVP에서 제외한다. Frontend는 안내 화면만 준비하며 실제 탈퇴·개인정보 권리 요청은 공개 정책의 문의 경로로 접수한다.

### 지원 흐름과 Draft

1. 배우는 공개 공고에서 배역을 선택하고 지원을 시작한다.
2. 로그인 세션이 있으면 저장된 프로필의 기본·추가 정보 중 공고가 요구하는 값만 불러올 수 있다.
3. 로그인하지 않아도 지원서와 사진을 작성할 수 있다. 인증 전 Draft와 사진은 현재 브라우저의 IndexedDB에만 저장하며 서버로 전송하지 않는다.
4. Draft를 복원할 때 이전 필수 동의 체크 상태는 복원하지 않고 항상 미동의 상태로 초기화한다.
5. 최종 제출 전에 배우 소셜 로그인을 완료한다. 로그인 화면을 다녀와도 같은 브라우저의 로컬 Draft는 유지한다.
6. 최종 제출 과정에서 사진 업로드, 서버 유효성 검증과 동의 기록을 처리한다. 이 전까지 작성 내용과 사진은 기획사/제작사와 서버에 공개되지 않는다.
7. 제출 버튼을 클릭한 시점의 서버 시간(UTC)을 기준으로 모집 중인지 다시 검사하고 마감됐으면 제출을 차단한다. 사용자가 마감 전에 화면을 열어 둔 사실은 예외가 아니다.
8. 제출에 성공하면 기본·추가 정보, 답변, 배역, 나이와 파일 참조를 제출 당시의 불변 지원서 스냅샷으로 확정하고 인증 계정에 귀속한다.

인증 전 Draft는 서버 식별자·계정 연결·서버 보관기간이 없다. 다른 브라우저·기기에서 이어쓰기는 MVP 범위가 아니며 브라우저 데이터를 지우면 복원할 수 없다. 제출 성공 뒤 해당 로컬 Draft는 삭제한다.

### 공연과 공고 관리

- 공연은 포스터, 공연명, 장소명·구조화된 주소와 배역 템플릿을 가진다. 공연 배역 템플릿은 배역 이름과 한 줄 설명만 보관한다.
- 공연 배역은 공연 등록 시 확정하며 이후 추가·수정·삭제하지 않는다. 공연 수정은 포스터, 공연명과 장소만 허용한다.
- 모집 인원, 성별, 최소·최대 나이 같은 지원 조건은 공연이 아니라 공고의 모집 분야에 둔다.
- 공고 게시 시 선택한 공연 배역의 이름을 공고 배역에 복사해 스냅샷으로 보존한다.
- 공고를 만들 때 공연 포스터를 공고 대표 이미지의 초기 스냅샷으로 복사하고 공고에서 교체할 수 있다. 이후 공연 포스터 변경은 기존 공고와 지원서에 영향을 주지 않는다.
- 공연 시작일은 필수, 공연 종료일은 선택이다. 종료일이 없으면 오픈런이다. 모집 시작·종료는 분 단위 일시, 전형 일정은 날짜로 기록한다.
- 공고의 저장 상태는 `DRAFT`, `PUBLISHED`, `CLOSED`로 관리한다. 화면 표시 상태 `UPCOMING`, `OPEN`, `RECRUIT_CLOSED`는 저장 상태와 모집 기간을 이용해 Backend가 계산한다. 전형 종료 표시는 별도로 계산한다.
- `UPCOMING`에서는 모든 공고 항목을 수정할 수 있다. `OPEN`에서는 공고명과 모집 종료 시각의 연장만 허용한다. 모집 시작 시각은 바꿀 수 없고 모집 종료를 앞당길 수도 없다. `RECRUIT_CLOSED`에서는 모든 항목을 수정할 수 없다.
- 기본 정보 8개 중 플랫폼이 모든 공고에 고정하는 필수 항목은 없다. 기획사/제작사가 공고마다 수집 항목을 선택하고, 선택한 기본 정보는 해당 지원서에서 필수다.
- 학력은 단일 문자열, SNS·외부 링크는 최대 5개, 경력은 최대 10개다.
- 추가 질문은 텍스트형만 제공하고 공고당 최대 10개다. 질문별 필수 여부를 정하며 모집이 시작된 뒤에는 문구·필수 여부·순서·삭제를 포함한 질문 설정을 수정할 수 없다.
- 전형은 1차부터 시작해 최대 5차까지 둔다.

### 지원서 입력

#### 배역과 지원 단위

- 기획사/제작사가 허용하면 하나의 지원서에서 여러 배역을 선택하고, 허용하지 않으면 하나만 선택한다.
- 동일 계정은 같은 공고에 지원서를 하나만 제출할 수 있다. 복수 배역 선택은 중복 제출이 아니다.
- 심사 결과는 `(지원서, 공고 배역, 차수)`별로 관리한다. 배우에게는 해당 차수 마감 뒤 확정 결과만 배역별로 공개한다.
- `ABSENT`는 현장 불참을 구분하기 위한 상태다. 1차 서류 심사에는 사용할 수 없고 2차 이상 전형에서만 사용할 수 있다.
- 별도의 `자유 배역` 타입은 두지 않는다. 일반 배역 이름을 `자유`로 등록한다.

#### 기본·추가 정보

기본 정보는 아래 8개로 통일한다. 공고에서 선택한 항목만 표시하며 선택한 항목은 필수다.

- 이름
- 키
- 몸무게
- 생년월일
- 성별
- 연락처
- 이메일
- 거주지

거주지는 상세 도로명주소가 아니라 시·군·구 수준만 수집한다. 성별에는 `응답하지 않음`을 두지 않는다. 휴대폰 번호는 `000-0000-0000`, 키·몸무게는 정수, 생년월일은 미래가 아닌 날짜만 허용하며 Frontend와 Backend가 각각 검증한다.

나이는 단순 연도 차가 아니라 공고 모집 마감일을 기준으로 계산한 만 나이다. 계산 결과는 제출 시 지원서에 스냅샷으로 저장해 이후 조회 기준이 바뀌지 않게 한다.

추가 정보는 학력, 경력, SNS·외부 링크, 국적, 자기소개, 특기, 취미, 군필 여부이며 공고가 선택한 항목도 nullable이다. 학력은 단일 문자열, 링크는 최대 5개, 경력은 최대 10개다.

#### 사진·영상·추가 질문

- 지원 사진의 목표 정책은 파일당 최대 20MB의 PNG, JPG, JPEG, WEBP만 허용하고, Backend가 실제 형식을
  검증해 EXIF 위치정보를 제거한 파일만 제출 스냅샷에 연결하는 것이다.
- 사진 요구는 유형별 설명과 장수를 가지며 전체 합은 최대 3장이다. 사진은 배열 순서가 아니라 `(photoRequirementId, fileId)`로 연결한다.
- 영상 요구는 최대 3개이며 각 요구에 YouTube 링크 하나를 `(videoRequirementId, url)`로 연결한다. 영상 파일은 업로드하지 않는다.
- 추가 질문은 최대 10개, 문구는 최대 255자, 답변은 문항별 최대 2,000자다. 답변은 `(questionId, answer)`로 연결하고 재사용 프로필에 저장하지 않는다.

### 프로필·동의·스냅샷

- 재사용 프로필의 값은 기본 정보 8개와 추가 정보다. 8개 기본 정보가 모두 채워지지 않아도 입력된 항목만 부분 저장·업데이트할 수 있다.
- 개인 사진·영상 보관함이 존재하더라도 지원서 제출 사진·영상 링크를 `프로필에도 저장` 동작으로 추가하거나 갱신하지 않는다. 공고별 추가 질문 답변도 프로필에 저장하지 않는다.
- `앞으로 입력한 프로필 데이터를 플랫폼에 보관할지`에 대한 선택 동의와 `이번 지원서의 기본·추가 정보로 프로필을 갱신할지`에 대한 제출별 선택을 별도 값으로 관리한다. 후자는 전자의 유효한 동의가 있을 때만 적용한다.
- 지원서 화면은 `개인정보 수집·이용`과 `제3자 제공`을 각각 필수 체크박스로 받는다. 상단 `필수 항목 모두 동의`는 두 하위 체크박스를 함께 변경하는 편의 기능으로만 제공하며, 서버에는 두 동의 이력을 각각 생성한다.
- Draft를 복원할 때 필수 동의와 제출별 프로필 갱신 선택은 복원하지 않고 초기화한다.
- 제출된 지원서는 공고가 선택한 기본·추가 정보 항목 목록, 입력한 텍스트 값, 계산된 나이, 선택 배역명과 파일 참조를 제출 당시 상태로 고정한다. 이후 공고 폼이나 프로필을 수정하거나 개인 사진을 Soft Delete해도 제출 지원서가 참조하는 파일과 표시 값은 바뀌지 않는다.
- 중복 제출 방지를 위한 별도 Idempotency Key와 제출 스냅샷 관리자 정정본은 MVP Backend 우선순위에서 제외한다. 동일 계정·공고의 지원서 하나라는 DB 제약과 개인정보 권리 요청 절차는 별도로 유지한다.

## 현재 구현 상태와 차이

### Backend

`backend/`에는 파일 직접 업로드, 사진 보관함, 공연 등록 시 배역 생성, 공연 포스터·공연명·장소 수정이 구현되어 있다.
공연 배역은 영속화 뒤 도메인에서도 추가할 수 없고 수정·삭제 API도 제공하지 않는다. 공고 DRAFT 생성·기본 정보·배역·일정·
지원 폼 저장 및 게시 상태 전이도 구현되어 있다. 공고 일정은 모집 시작·종료와 ID를 유지하는 전형 1~5개를
독립 섹션으로 관리한다. 심사 결과는 `(지원서 UUID, 공고 배역 ID, 전형 ID)`별 상태·기타 사유·내부 메모를
저장한다. 회원과 기획사/제작사 가입·로그인, 세션 기반 인증·인가, 사진 보관함이 구현되어 있다. 기획사/제작사
계정은 현재 MVP에서 가입 직후 `ACTIVE`이며 공연·공고·심사 API를 바로 사용한다. `ACTIVE`만 해당 API를 사용하는 인가 경계와 향후 `PENDING` 상태 모델은 유지한다.

Submission 도메인·영속성 모델, 제출 Request·Command와 제출 검증, 지원서·동의·사진 파일 참조를 한 트랜잭션으로
저장하는 Service가 구현됐다. 지원서별 필수 동의 기록 모델·영속성 구조와 공고별 현재 문서 버전·제3자 제공받는 자
명칭을 결정할 Application 경계도 구현됐다. 현재 MVP Backend는 명시적인 임시 문서 버전과 임시 제공받는 자
명칭으로 제출을 허용한다. 이는 실제 동의 문서가 아니며 실서비스 공개 전 운영 활성 버전과 공고별
기획사/제작사명을 제공하는 구현으로 교체해야 한다. 제출 API와 배우용 목록·상세 스냅샷 조회, 배우용 공개 공고
상세 조회가 구현됐다. 배우 재사용 프로필의 기본·추가정보 조회·수정과 YouTube 영상 보관함도 구현됐다.
공고 양식 기준 프로필 자동 채움과 MVP 이후 기획사/제작사 인증·활성화 운영 도구는 아직 구현되지 않았다.

현재 지원 사진은 S3 HEAD의 Content-Type·크기로 완료된 `READY` 파일 중 소유권과 메타데이터 이미지 유형을
검증해 제출에 연결한다. 실제 형식 검사·디코딩·EXIF 제거는 구현하지 않았으며 현재 `READY`를 정제 완료로
해석하지 않는다. 목표 정제 정책은 실서비스 공개 전에 구현한다.

현재 공고 배역은 공연 배역 이름을 실시간 참조하고 PUBLISHED 기본 정보를 수정할 수 있어 새 정책의 배역명 스냅샷과 상태별 수정 범위가 아직 반영되지 않았다.

### Submission Backend 1차 구현 범위

- 만 14세 미만 제출 차단은 이번 Submission Backend 1차 구현에서 제외하고 별도 GitHub Issue로 추적한다.
- 이는 만 14세 미만 지원자의 제출을 허용한다는 정책 변경이 아니다. 목표 정책은 제출 차단으로 유지하며,
  실제 개인정보를 처리하는 서비스 출시 전 생년월일 확인 경계와 차단 시점 또는 법정대리인 동의·확인
  절차를 확정하고 구현해야 한다.
- 공고가 생년월일을 수집 항목으로 선택하지 않은 경우의 나이 확인 입력과 기획사/제작사 제공 범위도 같은
  Issue에서 결정한다.

### Frontend·MSW

상세 동작은 [프론트엔드 현재 구현 상태](./development/frontend/current-implementation.md)에서 관리한다. 핵심 차이는 다음과 같다.

- 지원서와 공연·공고 작성 내용은 현재 브라우저 IndexedDB에만 저장되며 서버 Draft·다른 기기에 동기화되지 않는다.
- 기본 개발 환경의 인증은 React·MSW로 동작한다. 실제 소셜 로그인과 HttpOnly Session 복원·로그아웃 연동은
  구현됐지만 소셜 계정 연결, 약관 버전별 동의 저장과 만 14세 제출 차단은 아직 구현되지 않았다.
- `/apply/lookup`은 조회 코드·연락처로 비로그인 제출 내역을 보여 주고 모집 마감 전 수정 가능 문구를 노출한다. 목표 정책은 인증 후 제출과 제출 스냅샷 일반 수정 불가다.
- 사진은 슬롯 순서로 저장하고 파일당 10MB로 제한한다. 새 정책은 requirementId 연결, 20MB와 Backend EXIF 제거가 필요하다.
- 영상은 requirementId별 값을 입력하지만 제출 읽기 모델 일부는 여전히 요구 순서에 의존한다.
- 연락처는 서울 지역번호 등 여러 형식을 허용하고, 키·몸무게 정수와 미래 생년월일 검증이 완전하지 않다.
- 링크 입력은 단일 값이며 추가 질문 최대 10개 제한이 없다. 경력 최대 10개는 이미 적용되어 있다.
- 공고 수정 화면은 진행 중에도 공연·전형 일정을 노출하고 수정할 수 있어 새 수정 범위보다 넓다. 모집 종료 연장 동작은 목표 정책과 일치한다.
- 파일·프로필·지원서와 심사 화면은 MSW 시드와 로컬 상태로 검증한다. Backend의 배우용 지원서 스냅샷 조회는
  구현됐지만 Frontend·MSW는 과거 응답 계약을 사용하며, 심사 진행 상태 공개 읽기 모델도 아직 연결하지 않았다.

## 문서 적용 원칙

- **결정된 설계**만 현재 도메인 기준으로 사용한다.
- **현재 구현 상태와 차이**는 구현 사실이며 목표 정책이 아니다.
- 체크리스트의 답이 결정되면 이 문서와 관련 흐름·공개 정책·API 계약을 함께 갱신한다.
- 새 Entity, 테이블, API 구조를 이 문서에서 임의로 확정하지 않는다.
