# 도메인 설계 기준과 추가 결정 사항

> 기준일: 2026-08-11<br>
> 기준 문서: [Notion 도메인 설계](https://app.notion.com/p/3b94b21dcd3c80478a8ce0bb76965dc9)

이 문서는 Notion에서 이미 결정된 도메인 설계를 개발자가 읽기 쉬운 형태로 정리한다. 현재 코드나 다른 문서가 이 내용과 다르면 **결정된 설계**, **현재 구현**, **추가 설계 필요**를 구분한다. 추가 설계 항목은 답이 아니라 팀이 결정해야 할 질문이다.

## 결정된 설계

### 회원 구조

- 지원자와 공연사를 분리한다.
- 공연사 회원은 `공연사 master`와 `공연사 팀원` 역할로 나눈다.
- MVP에서는 역할을 ENUM 필드로만 관리하고 역할별 기능 차이는 두지 않는다.
- 실제 ENUM 상수명과 역할별 기능은 아직 정하지 않았다.

### 지원 흐름

1. 지원자는 공고에서 지원을 시작한다.
2. 로그인 세션이 있으면 이전 프로필 정보를 이용할 수 있다.
3. 로그인 세션이 없으면 이전 기본 프로필을 불러올지 묻는다. 기존 가입자는 로그인할 수 있고 처음 이용하는 사용자는 불러오지 않고 작성할 수 있다.
4. 로그인 여부와 관계없이 지원서를 작성한다.
5. 최종 제출 시점에는 로그인 또는 회원가입이 반드시 필요하다.
6. 인증이 완료된 뒤 지원서를 제출한다. 가입한 사용자는 작성한 프로필 정보를 이후 지원에서 재사용할 수 있다.

로그인하지 않은 동안 작성은 가능하지만 최종 제출 전에는 인증을 완료한다. 인증 전 작성 내용의 보관과 인증 왕복 방식은 추가 설계가 필요하다.

### 지원서

#### 기본 정보

다음 8개 항목은 필수다.

- 이름
- 키
- 몸무게
- 생년월일(연·월·일)
- 성별
- 연락처
- 이메일
- 거주지

#### 공연사가 선택하는 추가 정보

공연사는 공고에 필요한 항목을 선택할 수 있고 값은 nullable이다.

- 학력
- 경력
- 링크
- 국적
- 자기소개
- 특기
- 취미
- `필 여부` — Notion 원문 표현이며 정확한 의미는 확인이 필요하다.

#### 사진

- 사진은 최대 10장이다.
- 사진 설명 요구사항은 `{문자, 숫자}` 쌍을 여러 개 추가할 수 있는 형태다.
- Notion의 예시는 `{전신, 3}`, `{얼굴, 1}`이다.
- 이 쌍이 사진 종류별 요구 수량인지 사진별 메타데이터인지는 아직 정하지 않았다.

#### 커스텀 질문

- 공연사는 공고별 커스텀 질문을 여러 개 추가할 수 있다.
- 텍스트, boolean, 숫자 등 질문의 입력 형태를 선택할 수 있다.
- 커스텀 답변은 재사용하는 개인 프로필에 저장하지 않는다.

## 현재 구현 상태와 차이

### Backend

`backend/`에는 Spring Boot 진입점과 컨텍스트 로드 테스트만 있다. 회원, 공연사, 프로필, 지원서, 사진, 커스텀 질문의 도메인 객체·관계·상태·제약은 아직 구현되지 않았다.

### Frontend·MSW·기존 문서

- 제출 후 모집 마감 전 답변 수정이 가능하다. 공개 정책 문서는 제출 후 수정 불가로 설명해 이미 문서와 구현이 다르다.
- 기본 정보에 이메일과 거주지가 없고, 학교·전공이 기본 정보에 포함된다.
- 공고 설정에서 기본 정보도 끄거나 선택 항목으로 바꿀 수 있다.
- 사진은 최대 4장이고 `{문자, 숫자}` 설명 요구사항을 표현하지 않는다.
- 프로필에 공고별 커스텀 답변을 보관하며 커스텀 boolean 입력 타입이 없다.

이번 작업에서는 애플리케이션 코드를 수정하지 않는다. 인증 후 제출 API의 구체적인 경로·요청·응답도 새로 설계하지 않는다.

## 추가 도메인 설계 필요

### P0 — Backend 구현 전에 반드시 결정

| 영역 | 결정해야 하는 질문 | 필요한 이유 | 영향 영역 |
| --- | --- | --- | --- |
| 회원 | - [ ] 지원자와 공연사를 어느 인증 주체·식별자·생명주기까지 분리하며 한 사람이 두 유형에 속할 수 있는가? | 회원 참조와 인증 경계의 기준이 된다. | Applicant, CompanyMember, 인증 |
| 공연사 | - [ ] Company와 CompanyMember의 관계, 소속 가능 개수와 최초 master 생성 규칙은 무엇인가? | 공연·공고의 소유권을 정해야 한다. | Company, CompanyMember, Performance, Posting |
| 역할 | - [ ] 두 역할의 실제 ENUM 상수명과 부여·변경 주체는 무엇인가? | 저장 값과 유효한 역할 상태를 확정해야 한다. | CompanyMember, 가입·초대 |
| 지원서 생성 | - [ ] 인증 전 작성 중인 지원서는 서버에 존재하지 않는가? 인증 완료 뒤 어느 시점에 Application을 생성하는가? | 최종 제출 전 인증과 생성·실패 복구 시점을 함께 정해야 한다. | Application, 인증 흐름 |
| 프로필과 지원서 | - [ ] 어떤 항목을 프로필로 재사용하며 제출 지원서는 값을 복사하는가, 프로필을 참조하는가? | 프로필 변경이 과거 심사 자료에 미치는 영향을 결정한다. | ApplicantProfile, Application |
| 사진 설명 | - [ ] `{문자, 숫자}`의 두 값은 무엇을 뜻하며 지원서·사진과 어떤 관계인가? | 현재 예시만으로 저장 구조와 검증을 정할 수 없다. | Photo, Posting, Application |
| 커스텀 질문 | - [ ] MVP 입력 타입 목록과 타입별 값·검증 규칙은 무엇인가? | 질문과 답변의 저장·검증 경계를 정해야 한다. | CustomQuestion, CustomAnswer |
| 지원 계약 | - [ ] 인증 완료 후 제출, 파일 업로드와 지원서 조회의 인증·소유권 경계를 어떻게 정할 것인가? | 모든 제출 데이터가 인증 계정에 속하도록 계약을 정해야 한다. | 인증, Application, File |

| 질문 변경 | - [ ] 답변이 생긴 뒤 커스텀 질문의 문구·타입·순서·삭제를 허용하는가? | 과거 답변의 의미를 보존해야 한다. | Posting, CustomQuestion |
| 반복 항목 | - [ ] 학력·경력·링크의 다중 값과 개수·값 제약은 무엇인가? | 반복 항목의 저장과 검증에 필요하다. | Profile, Application |
| 공연사 구성원 | - [ ] 팀원의 가입·초대·탈퇴·삭제와 마지막 master 처리 규칙은 무엇인가? | 공연사 소유권과 접근을 유지해야 한다. | Company, CompanyMember |

## 문서 적용 원칙

- **결정된 설계**만 현재 도메인 기준으로 사용한다.
- **현재 구현 상태와 차이**는 구현 사실이며 목표 정책이 아니다.
- 체크리스트의 답이 결정되면 이 문서와 관련 flowchart·API·정책 문서를 함께 갱신한다.
- 새 Entity, 테이블, API 구조를 이 문서에서 임의로 확정하지 않는다.
