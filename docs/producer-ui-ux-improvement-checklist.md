# 공연사 UI/UX 개선 체크리스트

공연사 사용성 테스트에서 확인한 피드백을 실제 구현 작업으로 옮기기 위한 체크리스트다. 기존 심사 업무에서
익숙한 정보 배치와 처리 흐름을 최대한 유지하되, 기존 시스템의 불편까지 그대로 복제하지 않는 것을 원칙으로 한다.

## 기준과 범위

- 비교 기준: `origin/main` `dc54d4c`, 현재 브랜치 `feat/local-producer-demo-seed` `6ed5f5e`
- `[x]`는 현재 브랜치에서 구현되어 있으나 아직 `main`에는 없는 항목이다.
- `[ ]`는 추가 구현이 필요한 항목이다.
- 로컬 공연사 데모 시드, 데모 지원자 사진과 데모 전용 정렬은 제품 UI/UX 작업에서 제외한다.
- 지원자 화면은 이번 피드백에서 별도 요구가 없으므로, 공연사 흐름을 위해 계약이 바뀌는 부분만 함께 수정한다.
- API 계약을 변경하면 백엔드 DTO·Controller·테스트, 프론트 타입·호출·MSW와 관련 정본 문서를 함께 변경한다.

## 공통 UX 원칙

- [ ] 공연사가 기존에 사용하던 지원서 검토 순서인 `사진 → 경력 → 학력 → 키 → SNS`를 기본 정보 위계로 사용한다.
- [ ] 자주 사용하는 합격 선택과 다음 지원자 이동은 한 화면에서 처리하고, 부가 기능은 시선을 뺏지 않도록 낮춘다.
- [ ] 기존 시스템과 비슷한 용어와 정보 순서를 사용하되, 파일 편집·중복 입력·불필요한 상태 선택은 되살리지 않는다.
- [ ] 카드·표·한 명씩 보기에서 같은 지원자의 상태와 필터 결과가 일관되게 유지되도록 한다.
- [ ] 상태는 색만으로 구분하지 않고 텍스트, 배지, 선택 상태를 함께 표시한다.
- [ ] 데스크톱 1440×1000과 모바일 390×844에서 핵심 행동, 가로 스크롤, 고정 영역 겹침을 확인한다.

## 1. 현재 브랜치에서 완료된 기반 개선

### BASE-01. 공연별 전체 지원 건수 집계

- [x] 공연 카드의 지원자 수를 첫 배역만이 아니라 모든 배역의 심사 대상 건수 합계로 표시한다.
- [x] 복수 배역 지원은 각 배역에서 별도로 심사하므로 배역별 지원 건수의 합으로 계산한다.
- [x] 공연 카드의 `지원`과 `검토 대기` 수치가 배역 화면의 합계와 일치하는지 테스트한다.

완료 기준:

- 서연 233명, 지우 58명이면 공연 카드에 지원 291명이 표시된다.

### BASE-02. 검토 완료 화면의 기본 상태와 일괄 작업 정리

- [x] `검토 완료` 탭에 처음 진입하면 `전체`가 아니라 `합격`을 기본으로 표시한다.
- [x] 검토 완료 지원자를 선택했을 때 `합격·불합격·기타` 재지정 버튼을 숨긴다.
- [x] 검토 완료 지원자는 `검토 대기로`, `인쇄·PDF`, `연락처 모아보기`만 제공한다.
- [x] 잘못 저장한 심사 결과를 검토 대기로 되돌릴 수 있다.

### BASE-03. 조건 불일치 필터 피드백

- [x] 활성 상태를 `✓ 배역 조건 불일치 적용 중` 문구로 명확히 표시한다.
- [x] 조건 불일치 지원자를 일괄 불합격 처리하면 조건 불일치 필터를 자동으로 해제한다.

### BASE-04. 목록과 상세 화면 간 상태 보존

- [x] 지원자 상세 화면으로 이동할 때 검토 대기/완료, 상태 필터, 카드/표 보기 상태를 URL에 보존한다.
- [x] 상세 화면의 뒤로 가기와 이전/다음 지원자 이동 후에도 원래 목록 상태로 돌아간다.
- [x] 카드 보기와 표 보기 모두 같은 방식으로 동작한다.

## 2. P0 — 지원자 심사 정보 위계 개선

### UX-01. 지원 사진을 최대 3장까지 한눈에 검토

현재 상태:

- 지원 폼의 사진 요구 합계와 배우 사진 보관함은 모두 최대 3장이다.
- 카드와 표는 첫 번째 사진만 보여주고, 상세 화면은 한 장씩 넘겨보는 구조다.

구현 체크리스트:

- [x] 지원 제출 스냅샷이 사진 1~3장의 요구 순서와 설명을 그대로 보존하는지 검증한다.
- [x] 상세 화면에서 첫 번째 프로필 사진을 기존보다 크게 표시한다.
- [x] 데스크톱 상세 화면에는 최대 3장의 썸네일을 한 번에 볼 수 있는 열 갤러리를 제공한다.
- [x] 모바일은 대표 사진을 크게 보여주고 나머지 사진은 가로 스크롤 썸네일로 제공한다.
- [x] 사진을 누르면 원본 비율로 확대하고, 키보드와 이전/다음 버튼으로 이동할 수 있게 한다.
- [x] 사진이 0장, 1장, 3장일 때 빈 영역·장수 표기·대체 이미지가 깨지지 않는지 확인한다.

완료 기준:

- 공연사가 상세 화면에 진입한 직후 별도의 사진 넘기기 없이 최대 3장의 구도와 인상을 비교할 수 있다.

### UX-02. 학력을 `학교/학과`로 구조화

현재 상태:

- 프로필과 제출 스냅샷 모두 `school` 문자열 하나만 저장한다.
- 입력 안내에는 학교와 전공을 함께 쓰라고 되어 있지만 화면에서 분리해 활용할 수 없다.

구현 체크리스트:

- [x] 배우 프로필에 `최종 학력/학교/전공`을 저장하도록 도메인과 DB를 확장한다.
- [x] 기존 `school` 데이터는 학교 값으로 보존하고 새 `major` 값은 비운다. 기존 데이터는 시드이므로 별도 보정하지 않는다.
- [x] 지원 시점 스냅샷에도 최종 학력·학교·전공을 함께 저장한다.
- [x] 프로필 편집과 지원서 작성 화면에서 학력 없음·고등학교 졸업·대학교 졸업을 고르고, 해당 학교·전공을 입력한다.
- [x] 심사 카드·표·상세·인쇄 화면에서는 `학교 · 전공` 형식으로 표시한다.
- [x] 전공이 없는 기존 데이터는 학교만 표시하고 구분점이나 빈 괄호를 남기지 않는다.

완료 기준:

- 공연사가 표와 상세 화면에서 학교와 전공을 별도 해석 없이 바로 확인할 수 있다.

### UX-03. 지원자 상세 화면 정보 우선순위 재배치

- [x] 화면 첫 영역에 큰 프로필 사진, 이름, 지원 배역, 키, 학교/학과를 배치한다.
- [x] 사진 옆 또는 바로 아래에 주요 경력 2~3건을 먼저 노출한다.
- [x] 전체 경력은 접거나 별도 영역에서 모두 확인할 수 있게 한다.
- [x] SNS 링크는 주요 경력 다음에 배치하고 새 탭으로 안전하게 연다.
- [x] 자기소개와 추가 질문은 경력·학력 다음으로 배치한다.
- [x] 유튜브 영상은 상세 화면 하단의 `제출 영상` 영역으로 내린다.
- [x] 연락처, 이메일과 내부 심사 메모는 검토에는 필요하지만 사진보다 먼저 시선을 차지하지 않도록 한다.
- [x] 현재 심사 결과와 `합격/불합격/기타/다음 지원자` 행동은 스크롤 위치와 무관하게 접근 가능하게 한다.
- [x] 지원서 #06346749-2bf9-40e6-8ede-2e43e4e6bbf3 이런거 빼라

완료 기준:

- 상세 화면을 처음 연 상태에서 사진, 경력, 학교/학과, 키를 스크롤 없이 확인할 수 있다.
- 영상 링크가 첫 화면의 핵심 정보를 밀어내지 않는다.

## 3. P0 — 빠른 심사를 위한 보기 방식

### UX-05. `한 명씩 보기` 추가

목표:

- 카드와 표 외에 한 지원자를 크게 보고 바로 합격 처리하거나 다음 지원자로 넘어가는 집중 심사 모드를 제공한다.

구현 체크리스트:

- [x] 보기 선택에 `카드 | 표 | 한 명씩`을 추가한다.
- [x] 현재 검색어, 성별·나이·키 필터, 조건 불일치 필터가 한 명씩 보기에도 동일하게 적용되게 한다.
- [x] 한 명씩 보기에는 큰 프로필 사진, 현재 저장 정책 범위인 최대 3장 썸네일, 주요 경력, 학교/학과, 키, SNS만 우선 표시한다.
- [x] 하단에 `합격`, `다음 지원자`를 가장 강한 행동으로 배치한다.
- [x] `다음 지원자`는 현재 상태를 변경하지 않고 다음 사람으로 이동한다.
- [x] `불합격`, `기타`, 내부 메모는 보조 행동으로 제공한다.
- [x] 합격 저장 성공 후에는 같은 목록 위치의 다음 지원자로 자동 이동한다.
- [x] 첫 번째/마지막 지원자, 저장 중, 저장 실패, 검색 결과 0명 상태를 처리한다.
- [x] URL에 보기 방식과 검색어·성별·수치 필터·조건 불일치 필터를 보존해 새로고침과 상세 왕복에도 유지한다.
- [x] `A=합격`, `N=다음` 단축키를 제공하되 입력창 포커스 중에는 작동하지 않게 한다.
- [x] 각 버튼의 접근 가능한 이름, 포커스 순서와 저장 완료 알림을 확인한다.

완료 기준:

- 공연사가 마우스 이동을 최소화하면서 한 지원자의 핵심 정보 확인과 합격 선택을 반복할 수 있다.

### UX-06. 표 보기를 경력 중심으로 개편

현재 상태:

- 표 열은 `배우, 신체, 학교, 제출 자료, 접수, 상태`다.

구현 체크리스트:

- [x] `제출 자료`, `접수` 열을 제거한다.
- [x] 기본 열을 `선택, 배우, 주요 경력, 학교/학과, 키, 성별·나이, 상태` 순서로 구성한다.
- [x] 주요 경력은 최신 1~2건을 한 줄로 요약하고 전체 내용은 상세 화면에서 확인한다.
- [x] 경력이 없으면 빈칸 대신 `경력 없음`을 표시한다.
- [x] 긴 학교명과 경력은 말줄임하고 hover·focus에서 전체 내용을 확인할 수 있게 한다.
- [x] 좁은 표 영역에서는 우선순위가 낮은 열을 숨기고 배우, 키, 상태를 유지한다.
- [x] 행 선택 체크박스와 상세 열기 클릭 영역이 충돌하지 않게 유지한다.
- [x] 현재 심사 업무에는 표 정렬 요구가 없어 서버 정렬 계약을 추가하지 않는다.

완료 기준:

- 여러 지원자를 비교할 때 상세 화면을 열지 않고도 경력, 학교/학과와 키를 빠르게 비교할 수 있다.

## 4. P0 — 인쇄·PDF 개선

### UX-07. 실제 지원서와 유사한 A4 출력물

현재 상태:

- A4 한 지원자당 한 페이지를 만들지만 첫 번째 사진 한 장만 출력한다.
- 자기소개, 추가 질문, 경력, 심사 기록과 메모가 이어지는 구조다.

구현 체크리스트:

- [x] 첫 페이지 상단에 대표 사진을 기존보다 40%정도 크게 배치하고 차수별 심사기록은 제거한다. 메모는 남겨두고, 상단부분에 접수 부분도 삭제한다. 이름옆에있는 검토 부분도 제거한다.
- [x] 첫 페이지 핵심 정보 순서를 `이름/배역 → 키/나이 → 학교/학과 → SNS → 주요 경력`으로 맞춘다.
- [x] 경력은 표 형식으로 정리하고 연도, 작품명, 역할을 같은 열에 맞춘다.
- [x] 자기소개와 추가 질문은 다음 영역 또는 다음 페이지로 자연스럽게 넘긴다.
- [x] 여러 지원자 일괄 출력 시 지원자마다 새 페이지에서 시작하고 서로의 내용이 섞이지 않게 한다.
- [ ] Chrome 인쇄 미리보기에서 A4, PDF 저장, 실제 프린터 여백을 확인한다.
- [x] 외부 폰트 로딩 실패 시에도 한글과 레이아웃이 깨지지 않는 대체 글꼴을 둔다.

완료 기준:

- 공연사가 별도 한글/PDF 편집 없이 출력물을 현장 심사용 지원서로 사용할 수 있다.

## 5. P0 — 합격자 중심 전형 마감

### UX-08. 미선택 지원자가 남아 있어도 전형 마감

완료 정책:

- 현재 차수는 `PENDING`이 남아 있어도 마감할 수 있다.
- 0명 합격도 허용한다. 다음 차수 대상이 없으면 이후 빈 차수를 자동 마감해 배역 전형을 종료한다.
- 마감 후 결과 수정·되돌리기는 제공하지 않는다.

권장 정책:

- 합격자만 `PASS`로 명시하고 나머지는 `PENDING` 상태인 채 전형을 마감할 수 있게 한다.
- 다음 차수에는 `PASS` 지원자만 승격한다.
- 마감된 차수의 미선택 지원자는 내부적으로 `미선택`으로 표현하고 배우에게 `불합격`이라고 자동 통보하지 않는다.

구현 체크리스트:

- [x] `PENDING`이 남아 있어도 현재 차수 마감을 허용하도록 백엔드 완료 조건을 변경한다.
- [x] 전형 마감 요청 시 합격자 수와 미선택자 수를 응답·검증할 수 있게 한다.
- [x] 화면에는 항상 접근 가능한 `전형 마감` 행동을 제공하되 실수 방지를 위해 확인 모달을 연다.
- [x] 확인 모달에 `합격 N명`, `미선택 N명`, `다음 차수 승격 N명`을 명확히 표시한다.
- [x] 미선택자가 불합격으로 일괄 변경되지 않는다는 점을 설명한다.
- [x] 다음 차수가 있으면 합격자만 다음 차수 검토 대기로 생성되는지 확인한다.
- [x] 마지막 차수면 합격자가 최종 합격으로 유지되고 전형이 잠기는지 확인한다.
- [x] 마감 후 결과 수정·되돌리기 정책을 확정하고, 현재의 전체 잠금 규칙과 충돌하지 않게 한다.
- [x] 0명 합격으로 마감하는 경우를 허용하도록 정책을 확정한다.
- [x] 전형 마감 전후의 카드 수치, 탭, 연락처 모아보기 데이터가 현재 차수와 일치하도록 갱신한다.

완료 기준:

- 공연사가 합격자만 선택한 뒤 나머지 지원자를 일일이 불합격 처리하지 않고 전형을 종료할 수 있다.

## 6. P1 — 공연·공고 생성 흐름 재설계

### UX-09. 공연 생성 후 공고 생성으로 자연스럽게 연결

현재 상태:

- 공연 추가와 공고 추가가 서로 다른 모달이고, 공연 생성 후 사용자가 다시 공연을 찾아 공고 추가를 눌러야 한다.
- 공연에는 제목, 포스터, 공연 장소, 배역만 저장하고 공연 기간은 공고에 저장한다.

구현 체크리스트:

- [x] 공연 생성 화면에 전체 단계 안내 `공연 정보 → 공고/모집 정보 → 지원 폼 → 게시`를 표시한다.
- [x] 공연 생성 완료 화면에 `이 공연의 공고 만들기`를 기본 다음 행동으로 제공한다.
- [x] 나중에 공고를 만들 수 있도록 `공연만 저장하고 닫기`를 보조 행동으로 제공한다.
- [x] 공고 생성 화면 상단에 선택한 공연의 제목, 포스터와 배역을 요약해 잘못된 공연에 공고를 만드는 일을 줄인다.
- [x] 작성 중 닫아도 현재 임시 저장 기능으로 복구되는지 확인한다.
- [x] 공연 수정과 공고 수정에서 같은 필드의 책임이 달라지지 않게 한다.

완료 기준:

- 처음 사용하는 공연사가 별도 설명 없이 공연 생성 직후 같은 공연의 공고 작성으로 이동할 수 있다.

### UX-10. 공연 기간을 공연 정보로 이동

현재 상태:

- DB와 API에서 공연 기간은 공고에 속하며, 하나의 공연에 공고가 여러 개면 기간을 반복 입력한다.

구현 체크리스트:

- [x] 공연 도메인과 DB에 공연 시작일·종료일 또는 오픈런 정보를 추가한다.
- [x] 기존 공고 기간이 모두 같은 공연만 그 기간을 공연으로 이관한다.
- [x] 같은 공연의 기존 공고들에 서로 다른 기간이 있으면 공연 기간을 비워 두고, 공연사가 기간 전용 수정 화면에서 직접 확정한다.
- [x] 공연 추가·수정 화면에서 공연 기간을 입력한다.
- [x] 공고 생성 화면에서는 공연 기간을 읽기 전용 요약으로 보여주고 다시 입력받지 않는다.
- [x] 공개 공고에는 공연의 현재 기간을 표시하고, 지원서는 공고 생성 시점의 기간을 스냅샷으로 보존한다.
- [x] 공연 기간 전용 수정은 이미 제출된 지원서 스냅샷을 바꾸지 않는다.
- [x] `docs/domain.md`와 `backend/docs/api.md`의 공연/공고 책임을 변경한다.

완료 기준:

- 동일 공연의 공고를 추가할 때 공연 기간을 반복 입력하지 않는다.

### UX-11. 모집 시작을 게시 시점으로 단순화

권장 정책:

- 신규 공고는 게시되는 순간 모집을 시작하고, 사용자는 모집 마감일만 입력한다.
- 임시 저장 상태에서는 모집이 시작되지 않으며 실제 게시 시각을 서버가 모집 시작 시각으로 기록한다.

구현 체크리스트:

- [x] 공고 생성 폼에서 모집 시작일 입력을 제거하고 모집 마감일만 받는다.
- [x] 백엔드가 게시 시각을 모집 시작 시각으로 결정하도록 API와 상태 전이를 변경한다.
- [x] 예약 게시 기능은 추가하지 않아 이 단순화와 섞지 않는다.
- [x] 마감일이 게시 시각보다 미래인지 서버에서 검증한다.
- [x] 공고 수정에서 모집 시작 시각은 읽기 전용으로 표시한다.
- [x] 공개 공고에는 실제 게시·모집 시작 시각과 마감 시각을 표시한다.

완료 기준:

- 공고를 바로 게시하는 사용자는 모집 시작일을 별도로 선택하지 않고 마감일만 입력한다.

### UX-12. 공연 장소·연습 장소·오디션 장소의 책임 분리

현재 상태:

- 공연에는 공연장 주소가 있다.
- 프론트 타입에는 공고별 연습 장소가 있지만 실제 공고 생성 요청은 빈 값으로 보내며, 백엔드 정본에는 미구현으로 기록돼 있다.
- 전형별 오디션 장소 필드는 없다.

권장 모델:

- 공연 장소: 실제 공연이 열리는 곳, 공연 정보에 저장하며 선택 입력으로 낮춘다.
- 연습 장소: 공고 단위로 저장한다.
- 오디션 장소: 전형 차수별로 저장해 1차·2차 장소가 다를 수 있게 한다.

구현 체크리스트:

- [x] 공연 장소를 선택 입력으로 확정한다.
- [x] 공고 도메인·DB·API에 연습 장소명과 주소를 추가한다.
- [x] 전형 단계 도메인·DB·API에 오디션 장소명과 주소를 추가한다.
- [x] 주소, 상세 주소, 우편번호, 좌표 형식은 현재 카카오 주소 검색 입력을 재사용한다.
- [x] 공고 생성 화면에서 일정과 가까운 위치에 연습 장소를 배치한다.
- [x] 각 전형 일정 행에 해당 차수의 오디션 장소를 입력할 수 있게 한다.
- [x] 같은 장소를 다음 차수에 복사하는 기능을 제공해 반복 입력을 줄인다.
- [x] 공개 공고에는 연습 장소를, 전형 안내에는 해당 차수의 오디션 장소를 구분해 표시한다.
- [ ] 지원 시점 스냅샷과 마감 후 장소 변경 정책을 정한다. (미결정 사항으로 분리)
- [x] 길찾기와 주소 복사 버튼이 세 장소를 혼동하지 않도록 `공연장`, `연습 장소`, `N차 오디션 장소` 라벨을 구분한다.

완료 기준:

- 공연사가 공연장, 연습 장소, 오디션 장소를 목적에 맞게 따로 입력하고 지원자도 각 장소의 의미를 구분할 수 있다.
