# 온보딩

예술IN 저장소를 처음 여는 팀원을 위한 문서다. **읽는 순서대로 따라 하면 30분 안에 화면을 띄우고 코드 지도를 갖게 된다.**

---

## 1. 지금 어디까지 와 있나

| 영역 | 상태 |
| --- | --- |
| 백엔드 (`backend/`) | Spring Boot 4.1 / Java 25 **빈 스캐폴드**. `YesulinApplication.java` 하나뿐. 컨트롤러·엔티티·Flyway 마이그레이션 없음. DB 접속 정보도 없음 |
| 프런트엔드 (`frontend/`) | 공연사 관리자의 **공연·공고 생성과 지원자 심사 흐름이 MSW 목으로 동작**. 화면 4단계 + 생성/상세/모달/인쇄까지 |
| 인증 화면 | `/login`, `/signup`에 지원자·공연사 계정 유형별 UI가 구현됨. 공연사 목 계정만 프론트엔드에서 로그인되며 실제 인증·소셜·사업자 조회 API는 아직 연결하지 않음 |
| 공개 소개 화면 | `/` 지원자 서비스 소개와 `/producer-service` 공연사 서비스 소개 랜딩이 구현됨. 실제 지원자 공고 탐색·지원 화면은 아직 없음 |

프런트엔드가 앞서 있는 건 의도한 것이다. 아래 3번을 읽자.

가장 최근의 큰 변경: 지원자 심사 흐름은 유지하면서 **공연과 공고를 각각 추가하는 화면**을 붙였다. 공연은 배역 조건을, 공고는 모집·전형·지원서 설정을 책임진다. 자세한 구분은 [공연 관리 문서](./performance-management.md)의 `생성 기능 추가` 절에 있다.

## 2. 실행하기

### 프런트엔드

```bash
cd frontend
npm install
npm run dev        # http://localhost:3000
```

브라우저에서 **`http://localhost:3000/producers`** 를 연다. `/producers/performances`로 자동 이동한다.

`공연 관리 환경을 준비하고 있어요.` 화면이 잠깐 뜨는 건 정상이다. MSW(가짜 서버) 워커를 등록하는 중이다.

> **포트 3000이어야 하나? 아니다.**
> 코드 어디에도 절대 URL이 없고 API 경로는 전부 `/api/screening/...` 상대 경로다. MSW 워커도 페이지를 띄운 origin에 그대로 붙는다. 3001이든 5173이든 똑같이 동작한다.
>
> 3000이 막혀 있으면 Next가 알아서 3001로 넘어간다. 그런데 이때 이런 메시지가 뜨면서 **실행이 거부되는 경우**가 있다.
>
> ```text
> ⨯ Another next dev server is already running.
>   - Local: http://localhost:3000
>   - PID:   36764
> ```
>
> 포트 문제가 아니라 **같은 디렉터리에 대해 dev 서버를 두 개 띄우려 해서** 거부된 것이다. Next 16이 막는다. 해결은 둘 중 하나다.
>
> - 이미 떠 있는 걸 그대로 쓴다 → `http://localhost:3000` 열면 된다
> - 정리하고 새로 띄운다 → `taskkill /PID 36764 /F` (Windows) 또는 `kill 36764` (macOS/Linux) 후 `npm run dev`

빌드·검사 명령:

```bash
npm run build   # 프로덕션 빌드 (타입 체크 포함)
npm run lint    # eslint
npm run start   # 빌드 결과 실행
```

테스트 러너는 아직 붙어 있지 않다.

### 백엔드

```bash
cd backend
./gradlew bootRun      # 앱 실행
./gradlew build        # 컴파일 + 검사
./gradlew test         # 전체 테스트
./gradlew test --tests "art.yesulin.YesulinApplicationTests"   # 단일 클래스
```

Java 25는 Gradle이 없으면 알아서 받아온다. 로컬 MySQL·Docker 설정은 **아직 없다.** `application.yml`에 `spring.application.name`만 있다.

## 3. 우리 개발 방식 — 왜 프런트가 먼저인가

**화면을 먼저 만들고, 거기서 나온 계약을 백엔드가 그대로 구현한다.** 흔히 *계약 우선(Contract-First)* 또는 *소비자 주도 계약*이라 부르는 방식이다.

우리 팀은 백엔드 인원 위주라 "API를 어떤 모양으로 설계해야 하나"에서 자주 막혔다. 이 순서는 그 고민을 화면이 대신 풀어준다.

```text
1. 화면에 뭐가 필요한지 정한다        →  types.ts   (도메인 모델)
2. 그 화면이 뭘 요청하는지 정한다      →  api.ts     (엔드포인트 목록)
3. 화면이 실제로 돌아야 하니 가짜 서버를 만든다 → mocks/    (검증·필터·에러까지)
4. 사람이 읽을 문서로 남긴다          →  docs/
5. 백엔드가 1~4를 그대로 옮긴다
```

이렇게 하면 백엔드를 시작할 때 **경로·메서드·JSON 모양이 이미 확정**돼 있고, "필수값이 뭔지" "권한 없으면 404인지 403인지" 같은 엣지 케이스도 화면을 만들며 이미 한 번 걸러진 상태다.

문서가 언급하던 원본 프로토타입 `docs/index.html`은 현재 저장소에 없다. **화면 의도나 문구는 살아 있는 스펙과 현재 프런트엔드 구현을 우선하고, 둘로 결정할 수 없으면 팀에 확인한다.**

## 4. 화면 5분 투어

띄운 다음 이 순서로 눌러보면 전체 그림이 잡힌다.

1. **서비스 소개** (`/`, `/producer-service`) — 지원자와 공연사 각각의 장점과 이용 흐름을 소개하고 로그인·회원가입으로 연결한다.
2. **로그인·회원가입 UI** (`/login`, `/signup`) — 지원자는 이메일·카카오톡·네이버 진입 UI를, 공연사는 아이디 로그인과 사업자 정보를 확인한다.
   - 공연사 목 로그인: 아이디 `admin` 또는 `yesulin`, 비밀번호 `1234`. 성공하면 나인진엔터테인먼트 관리자 화면인 `/producers/performances`로 이동한다.
   - 카카오톡·네이버 버튼과 공연사 대표자 휴대폰 인증, 사업자 정보 대조, KOPIS 공연사 확인은 API 연결 필요 안내만 표시한다.
3. **공연 선택** (`/producers/performances`) — 공연 2건. 카드에 공고 수·지원자 수·검토 대기 인원
   - 우측 상단 **`공연 추가`** — 공연 포스터·제목·장소와 재사용할 배역·성별·나이 조건 등록
4. **공연 카드 클릭** → 공고 목록. 진행 단계 태그가 서로 다르다 (`진행중` / `접수마감` / `전형마감`)
   - 우측 상단 **`공고 추가`** — 모집 기간·배역/인원, 기본 2개 전형과 선택형 3차, 항목별 필수 여부·사용자 정의 지원서 항목 등록
5. **공고 카드 클릭** → 배역 목록. 경쟁률과 검토 진행률이 배역마다 다르다
6. **배역 클릭** → 심사 화면. 여기가 핵심이다
   - 상단 **차수 스테퍼** — 2·3차가 `잠김`인 이유는 1차를 아직 마감 안 해서다
   - **검토 대기 / 검토 완료** 탭
   - **필터바** — 성별, `나이` 칩을 눌러 `25 이상` 조건 추가, `조건 불일치만`
   - 카드 아무거나 클릭 → **지원자 상세**. 합격/불합격을 누르면 그 사람이 목록에서 빠지고 **다음 사람으로 자동으로 넘어간다**
   - 끝까지 처리하면 **"2차 오디션로 넘어가시겠습니까?"** 확인창이 뜬다
7. **`검토 완료`** 탭 → 카드 선택 → 하단 액션바의 **`연락처 모아보기`**
8. 사이드바의 전형마감 공고 — 이미 끝난 전형이 어떻게 보이는지 확인한다.
9. 예정 공고 — 눌러도 들어가지 않고 안내 토스트가 표시된다.

> 새로고침하면 심사 결과와 차수 마감이 **초기화된다.** 목 데이터가 브라우저 메모리에만 있기 때문이다. 지원자 명단·통계는 시드가 고정돼 있어 항상 똑같이 나온다.

## 5. 도메인 모델 — 반드시 이해하고 가야 할 것

```text
Performance  공연(작품)
  └ Posting      공고 — 실제 게시하는 모집 공고 한 건
      └ Role          배역 — 한 공고 안에 여러 개
          └ Application   지원서
```

백엔드 테이블 설계에 그대로 반영해야 할 결정 **두 가지**다.

**① 전형은 배역 단위로 독립 진행된다.**
차수 마감 상태는 `(배역, 차수)`에 붙는다. 같은 공고라도 `서연` 배역은 2차 중인데 `앙상블`은 아직 1차일 수 있다.

**② 심사 결과는 `(지원서, 차수)`에 붙는다.**
지원서 테이블에 `status` 컬럼을 두면 안 된다. 2차 결과가 1차 기록을 덮어써서 이력이 사라진다.

그 밖의 규칙(차수별 선택 가능한 결과, 공고 진행 4단계, 조건 불일치 판정)은 [공연 관리 문서](./performance-management.md)에 표로 정리돼 있다.

│
├── app/producers/                    라우트 (얇다 — 파라미터 받아 컴포넌트에 넘기는 게 전부)
│   ├── layout.tsx                    noindex + MswProvider + ToastProvider + ProducerShell
│   ├── performances/                 공연 선택 / [performanceId] 공고 선택
│   ├── postings/[postingId]/         배역 선택
│   └── roles/[roleId]/               지원자 심사

│   ├── types.ts                      도메인 모델 + 요청/응답 타입
│   ├── creation-types.ts             공연·공고 생성 요청과 배역 템플릿 타입

│   ├── routes.ts                     화면 경로 + 건너뛰기 규칙
│   ├── print.ts                      A4 인쇄 문서 생성
│   └── use-screening-query.ts        조회 훅
│
├── components/
│   ├── auth/                         공통 인증 레이아웃·역할 선택·입력 폼
│   ├── producers/                    사이드바 셸 · 트리 내비 · 폭 조절
│   └── screening/                    심사 화면 UI 전부
│       ├── board-workspace.tsx       ★ 상태와 액션의 중심. 여기부터 읽으면 된다
│       ├── board-context.tsx         공유 상태 인터페이스 (프롭 드릴링 대신)
│       ├── performance-create-modal.tsx  공연 생성 폼
│       ├── posting-create-modal.tsx      공고 생성 폼
│       └── ...                       스테퍼·필터바·목록·상세·모달

└── mocks/
    ├── handlers.ts                   MSW 핸들러 = 백엔드가 구현할 로직의 초안
    └── screening/
        ├── catalog.ts                공연·공고·배역 원본 데이터
        ├── create.ts                 공연·공고 인메모리 생성
        ├── applicants.ts             시드 고정 난수로 만든 지원서 72건
        ├── store.ts                  심사 결과 · 차수 마감 상태 (인메모리)

**어디부터 읽어야 하나**

- 도메인이 궁금하다 → `features/screening/types.ts`
- API 계약이 궁금하다 → `features/screening/api.ts` → `mocks/handlers.ts`
- 화면 동작이 궁금하다 → `components/screening/board-workspace.tsx`

초기 목 데이터 규모: 공연 2 · 공고 6 · 배역 13 · 지원서 72건. 화면에서 추가한 공연·공고는 새로고침 전까지 여기에 더해진다.

## 7. 백엔드를 시작한다면

`mocks/handlers.ts`를 Java로 옮기면 된다. 대응은 이렇다.

| 프런트엔드 | 백엔드 |
| --- | --- |
| `types.ts`의 응답 타입 | DTO / 레코드 |
| `api.ts`의 경로·메서드 | `@GetMapping` / `@PatchMapping` |
| `handlers.ts`의 검증 (`400` 반환) | Bean Validation + 도메인 규칙 |
| `store.ts`의 필터·집계 | JPA 쿼리 / 집계 쿼리 |
| `aggregate.ts`의 파생 상태 | 도메인 서비스 |

엔드포인트 7개와 요청/응답 예시는 [공연 관리 문서의 API 계약 절](./performance-management.md#api-계약)에 있다.

**목이 흉내내지 않는 것 — 백엔드에서 반드시 채워야 한다**

- **소유권 검사.** 지금 MSW는 목 데이터 전체가 한 공연사 것이라고 가정한다. 클라이언트는 공연사 ID를 **어떤 요청에도 보내지 않으므로**, 서버가 인증 정보에서 공연사를 판별해 모든 조회·변경을 그 범위로 제한해야 한다
- 트랜잭션·동시성 (두 심사자가 같은 지원자를 동시에 처리하는 경우)
- DB 제약조건·인덱스·페이지네이션 (지금은 차수별 대상 전체를 한 번에 내려준다)
- 실제 파일 저장소 (지원자 사진)

## 8. 자주 막히는 것

| 증상 | 원인과 해결 |
| --- | --- |
| `Another next dev server is already running` | 포트가 아니라 **중복 실행**. 위 2번의 안내 참고 |
| 화면이 로딩에서 안 넘어감 | MSW 워커 등록 실패. 브라우저 콘솔 확인. `public/mockServiceWorker.js`가 있어야 한다 (`npx msw init public/`로 재생성) |
| 심사한 게 새로고침하면 사라짐 | **정상.** 목 상태는 브라우저 메모리에만 있다 |
| 지원자 사진이 회색 실루엣 | 외부 아바타(`i.pravatar.cc`) 차단됨. 인라인 SVG로 자동 대체된 것이라 정상 동작이다 |
| `react-hooks/set-state-in-effect` 린트 에러 | React Compiler 규칙. 이펙트 안에서 동기 `setState` 금지. 렌더 중 파생하거나, 자식을 `key`로 리마운트하거나, 원인이 된 이벤트 핸들러로 옮긴다. `use-screening-query.ts`가 예시 |
| `aria-selected` 린트 경고 | 일반 `<button>`엔 못 쓴다. `aria-current`(스테퍼) 또는 `aria-pressed`(토글)로 |
| Tailwind 색상 유틸이 안 먹음 (`text-white`인데 글자가 검정) | `globals.css`에 기본 스타일을 **`@layer base` 밖에** 쓰면 계단식에서 레이어에 속한 모든 규칙을 이긴다. `button { color: inherit }` 하나가 모든 `text-*`를, `* { border-color }` 하나가 모든 `border-*`를 무시하게 만든다. 요소 선택자 규칙은 반드시 `@layer base` 안에 넣는다 |
| 실제 백엔드에 붙이고 싶다 | `NEXT_PUBLIC_API_MOCKING=disabled` |

## 9. 우리 팀 규칙

- **문서와 구현이 다르면 완료가 아니다.** 사용자 흐름·API 모양·권한·상태 전이·MSW 계약·환경 변수가 바뀌면 **같은 작업 단위에서** `docs/`를 함께 고친다. 기준은 [문서 운영 원칙](./README.md)
- **소스 파일은 순수 250줄 이하.** 넘으면 역할 단위로 쪼갠다
- 프런트엔드 코딩 관례는 `frontend/.agents/skills/`에 Vercel 규칙집이 들어 있다. 불리언 프롭 남발 대신 합성, `forwardRef` 금지(React 19), `useContext` 대신 `use()`
