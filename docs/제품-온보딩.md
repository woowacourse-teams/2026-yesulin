# 예술in 제품 온보딩

이 문서는 예술in을 처음 접하는 팀원과 Codex가 **서비스의 목적, 현재 기능, 사용자 흐름, 제품 방향**을 빠르게 이해하기 위한 자료다.

개발 환경, 코드 구조, 공통 개발 규칙은 이 문서에서 다루지 않는다. 해당 내용은 저장소의 `AGENTS.md`와 `design.md`를 참고한다.

## 1. 예술in은 어떤 서비스인가

예술in은 공연예술 오디션의 모집과 심사를 연결하는 서비스다.

공연사는 공연별로 공고를 만들고, 배역과 전형을 설정한 뒤, 접수된 지원자를 차수별로 검토한다. 지원자는 외부 오디션 공고에서 예술in 지원서 링크로 이동해 자신의 프로필과 자료를 제출하는 흐름을 목표로 한다.

핵심 문장은 다음과 같다.

> 지원자는 좋은 기회를 놓치지 않고, 공연사는 좋은 지원자를 더 빠르게 만날 수 있게 한다.

## 2. 지금 우리가 만들고 있는 것

현재는 공연사 관리자 화면, 지원자 공개 지원 흐름과 서비스 소개·인증 화면을 중심으로 만든 프론트엔드 프로토타입 단계다.

현재 확인할 수 있는 범위:

- 지원자용 서비스 소개 화면
- 공연사 서비스 소개 화면
- 지원자·공연사 로그인 및 회원가입 UI
- 공연 목록과 공연별 공고 목록
- 공연 추가와 공고 추가 화면
- 공고별 모집 배역 선택
- 배역별 지원자 심사 화면
- 전형 차수별 검토, 필터, 상태 변경, 메모
- 외부 오디션 공고에 붙일 지원서 링크 복사
- 공개 공고 상세, 배역 선택, 동적 지원서 작성·검토와 목 접수 완료
- 지원자 프로필, 자동 채움, 지원서 목록·상세·마감 전 수정, 비로그인 조회
- 공연사 공개 정보·담당자 설정, 공연·공고 수정 및 삭제 제한

아직 완성되지 않은 범위:

- 지원자용 전체 공고 검색·필터와 실제 지원서·파일 영속 저장
- 실제 로그인·소셜 로그인·휴대폰 인증
- 사업자등록번호 및 KOPIS 공연사 검증 API
- 실제 파일 저장과 백엔드 데이터 영속화

따라서 현재 화면은 완성된 운영 서비스라기보다, **사용자 흐름과 업무 화면을 검증하는 UI 중심 MVP**로 이해해야 한다.

## 3. 사용자는 두 종류다

### 지원자

뮤지컬·연극·앙상블·아역 등 오디션에 지원하는 사람이다.

주요 목표:

- 나에게 맞는 공연과 배역을 찾는다.
- 마감일, 조건, 전형 일정을 빠르게 비교한다.
- 기존 프로필·사진·영상·경력을 반복해서 입력하지 않는다.
- 지원 전에 제출 항목과 안내 사항을 확인한다.
- 제출한 내용과 수정 가능 시한을 확인한다. 심사 결과는 공연사가 외부 채널로 안내한다.

지원자 화면은 설명이 충분하고 다음 행동이 분명해야 한다. 정보량을 한꺼번에 보여주기보다 단계적으로 안내하는 방향을 추구한다.

### 공연사

제작사, 극단, 기획사, 창작집단의 담당자다.

주요 목표:

- 공연과 배역 조건을 관리한다.
- 공고마다 모집 기간과 모집 인원을 설정한다.
- 서류·오디션·최종 등 전형 일정을 관리한다.
- 많은 지원자를 빠르게 비교하고 검토한다.
- 검토 결과와 내부 메모를 남긴다.
- 합격자 연락에 필요한 정보를 모아 확인한다.

공연사 화면은 지원자 화면보다 정보 밀도가 높아야 한다. 예쁜 장식보다 비교·필터·상태 파악·빠른 액션을 우선한다.

## 4. 핵심 개념

예술in에서 다음 용어는 서로 다른 개념이다.

```text
공연
 └ 공고
    └ 배역
       └ 지원서
```

### 공연

뮤지컬이나 연극 작품 자체다.

공연 제목, 장소, 포스터와 재사용할 배역 조건을 가진다.

### 공고

특정 공연에 대해 실제로 게시하는 모집 단위다.

같은 공연이라도 시즌이나 모집 목적에 따라 여러 공고를 만들 수 있다. 공고마다 다음 내용이 달라질 수 있다.

- 모집 기간
- 모집 배역
- 배역별 모집 인원
- 전형 차수와 일정
- 지원서에서 받을 항목
- 지원 안내 문구

공연을 등록했다고 바로 지원자를 받는 것은 아니다. 공연에 별도의 공고를 만들어야 모집이 시작된다.

### 배역

공연에 등록한 배역 조건을 공고에서 선택하면 실제 모집 배역이 된다.

공연에 등록된 배역 원본은 재사용할 수 있지만, 공고마다 모집 인원과 모집 여부는 달라질 수 있다.

### 지원서

지원자가 공고에 제출하는 프로필·경력·사진·영상·서술형 답변이다.

공고마다 필요한 항목이 다를 수 있으므로, 공연사는 항목별 사용 여부와 필수 여부를 설정할 수 있어야 한다. 기본 항목 외에 공연사별 사용자 정의 항목도 추가할 수 있어야 한다.

## 5. 공연사 주요 흐름

### 공연 생성

공연사는 공연 제목, 장소, 포스터를 등록하고 이후 공고에서 재사용할 배역 조건을 설정한다.

배역 조건에는 다음이 포함된다.

- 배역 이름
- 한 줄 설명
- 성별 조건
- 최소·최대 나이

### 공고 생성

공연사는 특정 공연에서 어떤 모집을 할지 공고로 만든다.

공고 생성 화면은 다음 순서로 이해하면 된다.

1. 공고 제목과 모집 기간
2. 모집할 배역과 인원
3. 1차·2차·필요 시 3차 전형
4. 지원서에서 받을 항목
5. 지원 안내와 제출 유의사항

생성 후에는 외부 오디션 사이트에 붙일 공개 지원서 링크를 복사할 수 있다. 지원자는 외부 공고를 먼저 보고 예술in으로 들어오는 흐름을 전제로 한다.

### 지원자 심사

공고에 배역이 여러 개면 배역을 먼저 선택한다. 배역이 하나이거나 자유 배역 공고면 배역 선택을 건너뛰고 심사 화면으로 바로 들어간다.

심사 화면에서는 다음 행동을 한다.

- 전형 차수 선택
- 검토 대기·검토 완료 구분
- 성별·나이·조건 불일치 필터
- 지원자 상세 확인
- 합격·불합격·불참·기타 처리
- 내부 메모 작성
- 여러 지원자 상태 일괄 변경
- 합격자 연락처 모아보기

## 6. 전형과 상태에 대한 원칙

전형은 공고 전체가 아니라 **배역별로 독립적으로 진행**된다.

예를 들어 같은 공고의 남자 배우 배역은 2차 진행 중이고, 여자 배우 배역은 아직 1차 검토 중일 수 있다.

심사 결과도 지원서 전체에 하나만 저장되는 것이 아니라, 지원서와 전형 차수별로 남아야 한다. 2차 결과가 1차 결과를 덮어쓰면 안 된다.

공고 상태는 다음을 구분한다.

- 예정: 모집 시작 전
- 진행중: 모집 기간 내
- 접수마감: 모집은 끝났지만 심사가 남아 있음
- 전형마감: 모든 배역의 모든 전형이 끝남

배역 조건과 맞지 않는 지원자를 자동으로 차단하지 않는다. 조건 불일치 사유를 표시하고 공연사가 판단할 수 있도록 한다.

## 7. 우리가 추구하는 제품 방향

### 단순하지만 업무에 강한 서비스

예술in은 공연 포스터처럼 화려한 서비스가 아니라, 공연사와 지원자가 긴 시간 편하게 사용하는 업무형 서비스가 되어야 한다.

- 정보 구조는 단순하게
- 중요한 상태는 한눈에
- 다음 행동은 명확하게
- 반복 입력은 줄이기
- 장식보다 판단 속도 우선

### 지원자에게는 친절하게

지원자는 여러 공고를 비교하고 자신의 자료를 제출해야 한다. 따라서 지원자 화면에서는 안내 문구, 필수 항목, 마감일, 제출 상태가 명확해야 한다.

### 공연사에게는 효율적으로

공연사는 많은 지원자를 비교하고 빠르게 상태를 변경해야 한다. 따라서 공연사 화면에서는 카드·표·필터·배지가 장식이 아니라 업무 도구로 동작해야 한다.

### 신뢰할 수 있는 상태 표현

상태를 색상만으로 표현하지 않는다. 텍스트, 색상, 배지, 설명을 함께 사용해 사용자가 현재 상황을 오해하지 않도록 한다.

### 한 화면의 핵심 행동은 하나

공고 생성 화면에서는 `공고 추가`, 지원서 제출 화면에서는 `지원서 제출`, 심사 화면에서는 `검토 결과 변경`처럼 화면마다 가장 중요한 행동 하나를 분명하게 둔다.

### 공연사와 지원자를 연결하되 역할은 섞지 않기

공연사는 지원자를 검토하고, 지원자는 공고를 탐색하고 지원한다. 두 사용자의 목적과 정보 밀도가 다르므로 같은 화면 구조를 억지로 공유하지 않는다.

## 8. 현재 프로토타입을 볼 때의 기준

현재 데이터와 인증은 실제 운영 데이터가 아니다. 화면 흐름을 확인하기 위한 목 데이터와 가짜 계정이 사용된다.

공연사 관리자 화면을 확인할 때는 다음 계정을 사용할 수 있다.

- 아이디: `admin` 또는 `yesulin`
- 비밀번호: `1234`

새로고침하면 심사 결과, 추가한 공연, 추가한 공고가 초기화될 수 있다. 이는 현재 프로토타입의 한계이며, 실제 운영 단계에서는 백엔드 저장과 인증으로 대체한다.

## 9. 앞으로의 방향

우선순위는 다음과 같다.

1. 공연사 관리자의 공연·공고·지원자 심사 흐름 완성
2. 지원자가 외부 공고에서 들어와 지원서를 작성하는 공개 흐름 구현
3. 실제 인증과 공연사 권한 검증 연결
4. 사업자 및 공연사 정보 검증 연결
5. 실제 파일 업로드와 지원서 데이터 저장
6. 반복 공고를 위한 템플릿과 지원서 항목 재사용

기능을 추가할 때는 기존 공연 → 공고 → 배역 → 지원서 흐름을 유지해야 한다. 새로운 기능이 이 구조를 흐리거나, 사용자가 어디에서 무엇을 해야 하는지 불분명하게 만들면 다시 단순화한다.

## 10. 작업 요청을 이해하는 기준

이 프로젝트에서 UI 작업을 요청받으면 다음 질문을 먼저 확인한다.

- 이 기능은 지원자용인가, 공연사용인가?
- 공연·공고·배역·지원서 중 어느 개념에 속하는가?
- 기존 사용자 흐름을 유지하면서 어디에 배치할 수 있는가?
- 사용자가 다음에 해야 할 행동을 바로 이해할 수 있는가?
- 현재 화면에서 가장 중요한 Primary Action은 무엇인가?
- 빈 상태, 오류, 로딩, 모바일 화면에서도 같은 기능을 사용할 수 있는가?

구조와 비즈니스 규칙을 바꾸는 제안은 바로 구현하지 않고, 먼저 기존 흐름에 미치는 영향을 확인한다.
