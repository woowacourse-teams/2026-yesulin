# 공통 도메인

이 문서는 현재 구현에서 확인되는 공통 규칙만 설명한다. 세부 HTTP 계약은 [백엔드 API](../backend/docs/api.md),
미구현과 미결정 내용은 [미구현](./implementation-gaps.md)과 [미결정](./pending-decisions.md)을 따른다.

## 사용자와 인증

- 회원 유형은 `APPLICANT`, `PRODUCER`, `ADMIN`이다.
- 배우는 카카오·네이버·Google OIDC로 로그인한다. 첫 소셜 로그인에서 배우 회원과 `(issuer, subject)` 연결을 생성한다.
- 기획사/제작사는 이메일과 비밀번호로 가입·로그인한다.
- 기획사/제작사는 가입 직후 `PENDING`이며 5분 유효한 이메일 인증을 완료하면 `ACTIVE`가 된다.
- 기획사/제작사 비밀번호 재설정은 이메일로 발급한 5분 유효 일회용 링크를 확인한 뒤 새 비밀번호를 저장한다.
- 기획사/제작사 상태는 `PENDING`, `ACTIVE`다. 공연·공고·심사 API는 `ACTIVE`만 사용할 수 있고, 본인 프로필 조회·수정은 두 상태 모두 가능하다.
- MVP의 기획사/제작사 계정은 한 회사의 단일 관리자 계정이다. 여러 직원과 세부 역할은 현재 범위가 아니다.
- `ADMIN`은 개발팀 운영자다. 가입 API가 없고 서버 설정으로만 만들며 `ACTIVE` 외의 상태를 가질 수 없다.
- 운영자는 `PRODUCER` 계정의 상태만 `PENDING`과 `ACTIVE` 사이로 바꿀 수 있고, 그 결과는 감사 로그로 남는다.
  배우와 다른 운영자 계정의 상태는 바꿀 수 없다.
- 운영자의 `ACTIVE` 전환은 이메일 인증을 대신하는 수동 활성화다. 인증 메일이 닿지 않거나 토큰이 만료된 계정을
  복구할 때 사용하고, 정상 가입 흐름을 대체하지 않는다.
- 인증은 HttpSession을 사용하고 쓰기 요청은 CSRF 토큰을 검증한다.

## 공연과 공고

- 공연은 소유 기획사/제작사, 포스터 파일, 공연명, 선택 공연 장소, 공연 기간과 공연 배역을 가진다. 시작일은 필수이고 종료일이 없으면 오픈런이다.
- 공연은 연결된 공고가 없을 때만 기본 정보·포스터·배역을 수정하거나 삭제할 수 있다. 다만 기존 공고 기간 충돌을 사람이 확정할 수 있도록 공연 기간만 별도 수정할 수 있다.
- 공고는 공연을 참조하고 UUID 공개 ID, 공고명, 선택 연습 장소를 가진다. 공고 생성 시 공연의 기간을 읽어 공고·지원서 스냅샷으로 보존한다.
- 전형은 차수별 선택 오디션 장소를 가진다. 공개 공고에는 연습 장소와 각 차수의 오디션 장소를 구분해 표시한다.
- 공고 영속 상태는 `DRAFT`, `PUBLISHED`, `CLOSED`다. 현재 기본 정보 수정 로직에는 상태별 잠금 검사가 없다.
- 공고 삭제는 배역·일정·지원 폼과 그 배역의 심사 기록을 함께 지운다. 접수된 지원서가 있으면 삭제할 수 없다.
- 게시하려면 배역, 일정, 지원 폼이 모두 저장돼 있어야 하고 모집 종료 시각이 게시 시점보다 미래여야 한다.
- 공고별 배역은 공연 배역을 참조하며 모집 인원, 성별, 최소·최대 나이를 가진다.
- 한 공고는 복수 배역 지원 허용 여부를 저장한다.
- 모집 일정은 공고 게시 시 서버가 기록하는 시작 시각, 사용자가 입력하는 종료 시각과 1~5개의 전형으로 구성한다. 종료 시각은 게시 시각보다 미래여야 한다.
- 지원 폼은 기본 정보 필드, 추가 정보 필드, 사진 요구 최대 3개, 영상 요구 최대 3개, 텍스트 추가 질문 최대 10개를 가진다.

## OTR 공고

- OTR 협업 공고는 기존 공연·공고와 분리된 `OtrAudition`이다. 공연사 소유의 목록과 생성, 공개 지원을 지원한다.
- 생성 시 OTR 공고 번호(`otrId`, 숫자 1~30자), 제목, 배역명 1~20개, 마감일자를 받는다. 한 공연사가 같은 OTR 공고 번호를 중복 등록할 수 없다.
- OTR 원문 링크는 저장하지 않고 `https://otr.co.kr/audition/?vid={otrId}`로 만든다.
- 서버가 발급한 `/apply/standard/{공고 UUID}` 지원 경로는 공고 상세 없이 고정 지원 폼으로 연결된다.
- 마감일 당일 23:59:59까지 지원할 수 있고, 다음 날 00:00부터 서버가 접수를 거부한다(`Asia/Seoul`).
- OTR 지원은 `type=OTR`, 배역 하나와 기본 정보 전체를 필수로 받고 추가 정보, 서로 다른 사진 최대 3장,
  YouTube 영상 최대 3개는 선택으로 받는다. 두 개인정보 동의는 필수다.
  한 배우는 같은 OTR 공고에 한 번만 지원할 수 있다. 지원 정보는 별도 `OtrSubmission`에 저장한다.
- 공연사는 OTR 공고의 배역별 지원서를 기존 심사 관리 화면에서 목록·상세로 확인한다. OTR은 별도 전형 일정 없이
  기본 1차 서류 심사를 사용하며, 배역마다 `PENDING`·`PASS`·`FAIL`·`ETC` 결과와 내부 메모를 저장하고 마감한다.
  지원 마감 다음 날부터 배역별 심사를 종료할 수 있으며, 종료 후에는 해당 배역의 결과를 수정할 수 없다.
  OTR 마감에 따른 영속 상태 전환은 구현하지 않았다.

## 가져온 공고(메인 목록)

- 메인 페이지 `/`는 운영자가 공개했거나 기획사가 올린 `AuditionPost`를 원문 작성 최신순으로 보여 준다.
  지원 접수용 `OtrAudition`, Slack 알림 이력 `Notice`와 별개다.
- OTR과는 공고 수집 허락을 받았다. 운영(PROD) 서버는 OTR에 새 공고가 생기면 우리 공고로 검토 전 상태로 가져오고 Slack으로 알린다.
  개발(DEV)·로컬은 공고를 수집하지도 Slack으로 알리지도 않고, 운영자가 관리자 화면에서 번호로 직접 가져온다.
- 공고 상태는 검토 전(`PENDING`), 공개 중(`PUBLISHED`), 내림(`HIDDEN`)이다. 자동이든 직접이든 가져온 공고와 운영자가 쓴 공고는
  검토 전으로 시작하고, 운영자가 확인한 뒤 관리자 화면에서 공개한다. 카카오톡 채팅방 공유와 제작사 연락은 운영자가 직접 한다.
  제작사가 내려 달라고 하거나 문제가 있으면 내린다. 공개하거나 내린 공고는 검토 전으로 되돌리지 않는다.
- 공고마다 처음 만든 경로(자동 가져오기, 운영자 가져오기, 운영자 작성, 기획사 작성)를 남기며 다시 가져오거나 고쳐도 바뀌지 않는다.
- 자동 가져오기는 이미 가져온 번호를 다시 가져오지 않으므로 운영자가 정한 공개 상태를 덮어쓰지 않는다.
  자동 가져오기가 실패하면 Slack에 실패를 알리고 운영자가 직접 가져온다.
- Slack의 새 공고 알림 링크는 가져온 공고면 상태와 관계없이 `/posts/{id}?src=kakao_openchat`이다.
  가져오지 못한 공고는 경유 링크 `/otr?vid={번호}&src=kakao_openchat`를 쓰고,
  나중에 가져와 공개하면 같은 링크가 예술in 상세로 열린다.
- 공고 알림과 게시는 연극·퍼포먼스·뮤지컬·단원·기획사 분류만 다룬다. 그 밖의 분류(영화·댄스·방송·모델 등)는
  Slack 알림을 보내지 않고 가져오기도 거절한다.
- 가져올 때 제목·분류·페이·마감·작성자·작성 시각·태그와 본문(사진 포함), 첨부파일을 함께 옮긴다.
- 메인 목록은 기본으로 모집 중인 공고만 12건씩 번호 페이지로 보여 주고 "마감 포함"으로 전환할 수 있다.
  최상단에 공고 알림을 받는 카카오톡 오픈채팅방 참여 안내를 둔다.
- 공고 조회수는 상세 화면을 연 브라우저 탭마다 한 번 센다. 목록·상세·관리자 화면에 보이고 다시 가져와도 유지한다.
  공개 목록·상세는 실제 조회수와 공고 알림 오픈채팅방에서 공고를 확인했을 인원의 추정치 중 큰 값을 보여 준다. 추정치는 공고를 올린
  시각의 오픈채팅방 인원으로 계산하고, 운영자가 오픈채팅방 관리에서 지금 인원을 적으면 그 시각부터 올라오는 공고에만 적용한다.
  페이·마감은 원문 표현(`협의`, `상시` 등)을 그대로 두고, 마감이 날짜면 한국 날짜로 당일까지 모집 중이다.
- 오픈채팅방 관리에서 공고별 `오픈채팅방 링크 방문`을 기존 조회수와 따로 확인한다. 공유용 출처 표시가 있는 링크를
  브라우저에서 열었을 때만 기록하며, 공개 상세와 비공개 공고의 OTR 원문 이동을 모두 포함한다. 같은 공고는 브라우저 저장소의
  집계 표시가 남아 있는 동안 한 번만 보내고, 서버에는 방문자 식별값·방문 이력 없이 공고별 누적 숫자만 저장한다.
  관리자 로그인 상태의 방문, 분석을 끈 브라우저와 저장소를 사용할 수 없는 브라우저는 세지 않는다. 저장값 삭제·기기 변경·
  여러 탭의 동시 접근·응답 유실 후 재시도에 따라 중복될 수 있어 정확한 방 참여자 수가 아닌 대략적인 방문 지표다.
  가져오기 전 OTR 경유 링크의 숫자는 알림에 쌓고 나중에 가져오면 해당 공고와 합산한다. 수집 전 방문을 소급하지 않는다.
  관리자 통계는 한국 시간의 공고 게시일 기준 일간·주간(월~일)·월간·전체로 나누고 누적 링크 방문 수가 높은 순으로 본다.
  기간 이후에 발생한 방문도 누적 수에 포함한다. 게시일이 없는 공고는 전체 기간에만 포함한다.
  기록 실패는 공고 열람을 막지 않으며, 공개 상세 주소에서는 출처 표시를 걷어 낸다.
- 같은 출처·번호를 다시 가져오면 새 공고를 만들지 않고 원문 기준으로 내용과 파일을 교체한다. 공개 상태와 주소는 유지한다.
- 운영자는 공고의 분류·제목·페이·마감·작성자·태그·본문을 공개 여부와 관계없이 고칠 수 있다. 본문은 공개 본문과 같은 규칙으로
  다시 거르고, 이 공고의 사진(옮겼거나 운영자가 올린 사진)이 아닌 이미지는 지운다.
- 운영자는 원문 없이 공고를 직접 쓸 수도 있다. 업로드를 부탁한 업체의 공고를 대신 올리는 용도이며, 가져온 공고처럼 검토 전으로
  시작해 운영자가 공개한다. 출처 표시가 없고 원문으로 다시 가져올 수 없다. 공개 중이 아니면 보낼 원문이 없으므로 상세 주소는 없는 공고처럼 404다.
- 운영자는 쓰거나 고칠 때 본문 사진과 첨부(가져올 때와 같은 형식·크기)를 새로 올릴 수 있다. 올리고 저장하지 않은 파일은 하루 뒤 지운다.
- 이메일 인증을 마친 기획사/제작사(`PRODUCER + ACTIVE`)는 관리 화면에서 공고를 직접 올리고 고칠 수 있다. 올린 공고는 검수 없이
  바로 공개되고, 작성자는 기획사 이름으로 표시되며 기획사는 바꿀 수 없다. 지원 방법(이메일·링크 등)은 본문에 적는다.
- 기획사는 자기가 올렸거나 운영자가 연결해 준 공고만 보고 고친다. 고쳐도 공개 상태는 바뀌지 않고, 검토 전이거나 운영자가 내린 공고를
  기획사가 공개할 수는 없다. 내리기·삭제는 운영자에게 요청한다.
- 운영자는 모든 공고를 기획사 계정에 연결하거나 연결을 끊을 수 있다. 업체 대신 쓴 공고나 가져온 공고를 연결하면 그 업체가
  직접 고칠 수 있다.
- 운영자는 OTR 작성자를 기획사에 자동 연결할 수 있다. 닉네임은 바뀌거나 사칭될 수 있어 OTR 회원 번호로 연결하며, 연결하면 그
  작성자의 기존 공고 중 기획사가 없는 공고와 이후 가져오는 공고가 그 기획사에 연결된다. 운영자가 다른 기획사에 연결한 공고는 바꾸지
  않고, 공개는 계속 운영자가 한다. 자동 연결은 운영자만 걸고 풀며, 기획사가 자기 OTR 계정을 직접 등록하지는 않는다.
  회원 번호 없이 가져온 예전 공고는 운영자가 OTR에서 번호를 다시 읽어야 자동 연결 대상이 된다.
- 운영자 공고 관리에는 기획사별 공고 수와 자동 연결, 기획사에 연결되지 않은 OTR 작성자 목록을 보는 업체별 보기가 있다.
- 기획사에 연결된 공고의 작성자는 그 기획사의 지금 이름으로 보인다. 기획사가 설정에서 이름을 바꾸면 모든 공고에 바로 반영된다.
  원문 닉네임이나 운영자가 쓴 작성자는 따로 남아 있다가 연결을 끊으면 다시 보이고, 원문으로 다시 가져와도 연결된 동안은 기획사 이름이 보인다.
- 기획사가 공고를 올리면 OTR 공고 알림과 같은 형식으로, 고치면 바뀐 항목만 공고 알림 Slack 채널로 알린다. 운영자는 새 공고 알림을
  오픈채팅방에 공유하고, 부적절한 공고는 내린다. 알림이 실패해도 공고 저장은 그대로다.
- 고친 공고를 원문으로 다시 가져오려면 운영자가 덮어쓰기를 확인해야 한다. 다시 가져오면 내용이 원문 기준으로 돌아가고
  수정 표시가 지워진다. 자동 가져오기는 이미 있는 번호를 건너뛰므로 고친 내용을 덮어쓰지 않는다.
- 검토 전이거나 내린 공고는 공개 목록에서 빠지고, 상세 주소 `/posts/{id}`는 OTR 원문 공고로 이동한다. 이미 공유한 링크가
  끊기지 않게 하기 위해서다. 없는 공고만 404이고, 내린 공고는 다시 공개할 수 있다.
- 공개 중이 아닌 공고 상세를 열어 원문으로 보낸 수(`OTR 이동`)는 조회수와 따로 공고마다 누적해 관리자 공고 목록에 보여 준다.
  서버에서 이동하므로 링크 미리보기 봇의 요청도 셀 수 있다. 경유 링크 `/otr?vid=` 이동 수는 관리자 개요에서 따로 본다.
- 사진은 JPEG·PNG·GIF·WebP 20MB까지 옮기며 하나라도 실패하면 가져오기 전체를 취소한다. 첨부파일은 문서·악보·음원
  형식(pdf, doc(x), hwp(x), xls(x), ppt(x), txt, zip, jpg, png, mp3, m4a, wav) 50MB까지 옮기고, 그 밖의
  첨부는 건너뛴 뒤 운영자에게 알린다. 공개 상세에는 출처를 작은 원문 링크(`OTR ↗`)로 밝히고, 목록에는 출처를 두지 않는다.

## 공연사 정보

- 공연사(`Company`)는 공고를 올린 극단·제작사·기획사의 공개 정보다. 기획사 계정(`Producer`)과 따로 있어 계정이 없는 공연사도
  운영자가 만든다. 이름만 필수이고 대표자 이름·링크(홈페이지·SNS 최대 3개)·설립일·주소·지역·대표 연락처·소개·연혁은 비워 둘 수 있다.
  대표 사진은 한 장이고 없으면 이름 첫 글자 이미지가 보인다. 운영자와 정보 수정 요청자가 올릴 수 있고, 요청 사진은 운영자가
  적용하기 전까지 공개하지 않는다.
  입력 화면은 선택 항목마다 값을 적거나 "비공개"를 체크해야 저장된다. 비공개로 체크했거나 공개 동의가 없는 항목은 공개 화면에 "비공개"로 보인다.
- 공연사도 검토 전(`PENDING`), 공개 중(`PUBLISHED`), 내림(`HIDDEN`) 상태가 있다. 운영자가 만들면 검토 전이고, 내용을 확인한 뒤
  공개해야 보인다. 공개하거나 내린 공연사는 검토 전으로 되돌리지 않는다.
- 운영자는 공고를 공연사에 연결하거나 연결을 끊는다. 검토 전인 공연사에도 미리 연결할 수 있다. 공고 상세는 연결된 공연사가 공개 중일 때만
  이름·대표자·홈페이지·설립일·위치를 요약해 보여 주고 공연사 화면 `/companies/{id}`로 이어진다.
- 공연사 화면은 요약에 연락처·소개·주소 지도와 그 공연사에 연결된 공개 공고(마감 포함, 최근 30건)를 더한다. 공개 전이거나 내린 공연사는 없는 공연사처럼 보인다.
- 지도와 공고 카드의 위치는 공연사가 직접 알려 준 주소만 쓴다. 주소가 있으면 시·군·구까지, 없으면 지역을 보인다.
- 공개 운영 기준: 대표자 이름은 개인정보라 공연사가 공개에 동의했다고 운영자가 표시한 경우에만 보인다. 주소는 공식 사업장
  주소라고 표시한 경우에만 상세 주소와 지도를 보이고, 아니면 시·군·구까지만 보인다(집 주소일 수 있어 기본은 비공개).
  연락처는 공식 대표번호만 적고 개인 휴대폰 번호는 쓰지 않는다. 소개는 사실만 운영자 문장으로 쓰고 남의 글·사진을 옮기지 않는다.
  운영자는 정보를 어디서 확인했는지 정보 출처 메모로 남기며, 메모는 공개하지 않는다.
- 공고 상세에는 공연사 칸을 항상 둔다. 공개된 공연사가 없으면 원문 작성자 이름과 "준비 중" 안내, 정보 등록 요청 창구만 보인다.
- 운영자는 공고 목록에서 그 공고의 공연사 정보를 바로 쓴다. 이전 정보가 없으면 원문 작성자 이름으로 공연예술통합전산망(KOPIS)
  기획제작사를 찾아 이름·연락처·홈페이지·장르·최근 작품을 처음 값으로 채우고, 운영자가 후보를 고르거나 다른 이름으로 다시 찾는다.
  KOPIS 정보는 처음 값일 뿐이라 운영자가 확인해 고친 뒤 저장한다. 같은 OTR 작성자로 이전에 쓴 정보가 있으면 그 정보를 불러오고, 저장하면
  같은 작성자의 다른 공고와 이후 가져오는 공고에도 연결된다. 운영자가 직접 쓴 정보이므로 저장하면 바로 공개되지만, 운영자가 내린
  공연사는 내린 채로 둔다. 잘못 연결된 공고는 그 공고만 다른 공연사로 옮기거나 연결을 끊을 수 있다.
- 공연사 화면에서 누구나 로그인 없이 정보 수정을 요청한다. 요청자는 공개된 정보를 고쳐 요청 사유(필수)와 연락처(선택)를 함께 보낸다.
  운영자는 공고 관리의 수정 요청 탭에서 바뀐 항목을 지금 정보와 비교하고, 요청자가 바꾼 항목만 덮어쓴 정보를 다듬어 적용하거나 반려한다.
  요청자는 공개되지 않은 값을 볼 수 없으므로 바꾸지 않은 항목은 지금 정보를 그대로 둔다. 연락처는 확인 연락에만 쓰고 처리하면 지운다.
  새 요청은 Slack으로 운영자에게 알린다. 정보 삭제 요청은 예술in 카카오톡 채널로 받는다.
- OTR 공고는 원문 작성자(OTR 회원 번호)별로 공연사에 묶는다. 같은 작성자가 여러 번 올린 공고나 같은 공고를 다시 올린 글은 공고마다
  공연사를 만들지 않고 한 공연사에 모은다. 닉네임은 바뀔 수 있어 회원 번호로 묶고, 번호를 읽기 전에 가져온 공고는 번호를 읽어야 묶인다.
  운영자는 작성자를 이미 있는 공연사에 묶거나 그 닉네임으로 검토 전 공연사를 만들 수 있고, 묶지 않은 작성자를 한꺼번에 공연사로
  만들 수도 있다. 묶으면 그 작성자의 공연사 없는 공고와 이후 가져오는 공고가 연결된다. 한 공연사에 여러 작성자를 묶을 수 있고,
  작성자를 다른 공연사로 옮기면 그 작성자로 연결됐던 공고도 함께 옮긴다. 운영자가 공고마다 따로 고른 다른 공연사는 바꾸지 않는다.
- 운영자 변경 기록에는 공연사 정보 원문을 남기지 않는다.

## 무료 공연과 예매

- 무료 공연(`Show`)은 오디션 공연·공고와 분리된 모델이다. 기획사/제작사(`PRODUCER + ACTIVE`)가 자기 공연만 등록·수정·삭제하고,
  다른 기획사의 공연·회차·예매는 찾을 수 없는 것으로 다룬다.
- 공연은 공연명, 장르(뮤지컬·연극·음악), 소개, 장소, 공연 시간(분), 관람 연령, 취소·단체 문의 전화, 포스터 1장과 상세 이미지 최대 3장을 가진다.
  선택으로 주최 이름, 추가 안내(제목·내용 직접 입력, 최대 5개)와 예매 안내 외부 링크(버튼 이름 필수, http/https, 최대 3개)를 가진다.
  링크는 관객 상세의 예매 안내와 예매 완료 화면에, 추가 안내는 오시는 길 지도 아래에 입력 순서대로 보인다.
- 관객 목록·상세·예매 완료 화면에는 주최를 보여 준다. 공연에 주최 이름을 따로 적지 않으면 기획사 계정의 회사명을 쓰고,
  프로젝트 이름처럼 다르게 보여 줘야 할 때만 공연마다 바꾼다. 운영자도 운영 대시보드에서 공연의 주최 이름을 대신 고칠 수 있고,
  그 변경은 이름 원문 없이 운영자 변경 기록에 남는다.
- 잔여석 공개 여부는 공연 단위 설정이며 기본은 공개다. 비공개면 관객에게 잔여석 숫자 대신 "예매 가능"을 보여 주고
  공개 API도 숫자를 내보내지 않는다. 예매 가능 여부와 매진 표시는 공개일 때와 같고, 한 번에 고를 수 있는 매수는
  잔여석까지라 10석 미만이면 간접적으로 드러난다. 기획사 화면은 항상 잔여석을 보여 준다.
- 기획사가 등록한 공연은 예술in으로만 예매받는다. 기획사 계정이 없는 공연은 운영자가 운영 대시보드에서 직접 등록하며, 이
  공연은 네이버 폼 같은 외부 링크(http/https, 500자 이하)로만 예매받는다. 운영자 공연은 주최 이름과 외부 예매 링크가 필수이고
  잔여석 공개 설정이 없다. 관객 상세의 예매하기는 그 링크를 새 창으로 열고, 회차는 고르지 않고 일정만 보여 주며, 잔여석·1회 최대
  매수·취소 마감 안내를 내보내지 않는다. 서버는 운영자 공연의 예술in 예매를 거절한다. 회차는 정원 없이 시작 시각만 가지며
  공개·마감 규칙은 기획사 공연과 같다. 관객이 예매하기를 누르면 예술in을 거쳐 예매하러 간 기록(관객 정보 없이 공연·시각)을
  남기고, 운영자는 공연별 이동 횟수를 본다. 운영자 공연은 기획사 화면에 보이지 않고, 등록·공개·마감·숨김·숨김 해제·삭제는 운영자 변경 기록에
  남는다.
- 공연 상태는 `DRAFT`, `OPEN`, `CLOSED`다. 새 공연은 `DRAFT`이고 시작 전인 회차가 하나 이상 있어야 `OPEN`으로 공개한다.
  `OPEN`만 `CLOSED`로 마감할 수 있고, 시작 전 회차가 있으면 예매를 다시 열 수 있다. 마감 공연도 관객 목록과 상세에 남는다.
  예매 상태와 별도로 공개한 공연을 숨기거나 숨김 해제할 수 있다. 숨기면 관객 목록·상세에서 제외하고 새 예매와 외부 예매 이동 기록을 거절한다.
  숨김 해제는 기존 `OPEN`·`CLOSED`를 유지하고 회차 시각을 검사하지 않아 지난 마감 공연도 다시 표시할 수 있다. `OPEN`의 숨김을
  해제하면 시작 전 회차의 예매도 다시 가능하다. 숨긴 동안 예매를 다시 열려면 먼저 숨김을 해제한다. 초안은 숨김 변경으로 공개할 수 없다.
  숨김·마감 모두 공연 정보와 기존 예매를 유지하며, 예매 기록이 있는 공연은 삭제하지 않고 마감하거나 숨긴다.
- 회차는 시작 시각과 정원을 가진다. 시작 시각은 현재 이후여야 하고, 정원은 확정 예매 매수보다 줄일 수 없으며,
  예매 기록이 있는 회차는 삭제할 수 없다. 잔여석은 저장하지 않고 정원에서 확정 매수를 빼서 계산한다.
- 관객은 회원이 아니며 로그인 없이 예매한다. 공개 목록·상세는 숨기지 않은 `OPEN`·`CLOSED` 공연을 보여 주고
  `DRAFT`와 숨긴 공연은 찾을 수 없는 것으로 다룬다. 목록은 예매 중인 공연을 먼저, 마감 공연을 아래에 보여 준다. 좌석은 지정하지 않고 회차별 인원 수만 받는다.
- 예매는 이름, 휴대폰, 매수(1~10매)와 개인정보 수집·이용 동의를 받고 8자리 예매번호를 발급한다. 11명 이상 단체는 문의 전화로 안내한다.
- 공연 `OPEN`이고 회차 시작 전이며 잔여석이 있을 때만 예매할 수 있다. 같은 회차에서 같은 휴대폰 번호의 확정 예매는 하나뿐이고,
  취소된 번호는 다시 예매할 수 있다. 서버는 회차를 잠근 뒤 중복 번호와 잔여석을 다시 확인한다.
- 관객 본인 조회·취소 기능은 없다. 관객이 전화로 요청하면 기획사가 자기 공연의 예매를 취소하거나 매수를 바꾼다. 공연 1시간 전
  취소 마감은 화면 안내이며 서버가 막지 않는다. 매수 변경도 1~10매 안에서 정원을 넘지 않으면 회차 시작·공연 마감 후에도 할 수 있고,
  정원이 모자라면 회차 정원을 먼저 늘린다. 취소된 예매의 매수는 바꿀 수 없다.
- 기획사는 예매 관객별로 응대용 메모(300자 이하)를 남길 수 있다. 메모는 관객에게 보이지 않고 취소된 예매에도 남길 수 있다.
- 기획사는 회차별 확정 예매자의 휴대폰 번호를 한 번에(또는 체크한 예매자만) 줄바꿈으로 복사하고, 확정 예매 명단을
  엑셀(.xlsx, 예매번호·이름·휴대폰·매수·예매 시각·메모)로 내려받을 수 있다. 취소된 예매는 둘 다에서 뺀다. 파일은 브라우저에서 만든다.
  번호 복사 화면과 엑셀 맨 아래에는 복사본·다운로드 파일을 관람 회차 종료 후 3일 이내에 직접 삭제하도록 안내한다.
- 예매 확정·취소·매수 변경 시 도메인 이벤트를 발행한다. 문자 안내는 아직 이 이벤트에 연결돼 있지 않다.

## 지원서

- 일반 지원서는 `type=STANDARD`다. 기존 제출 요청·데이터에 `type`이 없으면 서버에서 `STANDARD`로 처리한다.
- 배우는 게시됐고 현재 모집 중인 공고에만 제출할 수 있다.
- 한 배우는 같은 공고에 한 번만 제출할 수 있다.
- 복수 배역 허용 공고에서는 하나의 지원서가 여러 배역을 선택할 수 있다.
- 서버는 공고의 수집 필드, 선택 배역, 사진 파일의 소유권·`READY` 상태, 질문과 영상 답변을 검증한다.
- 키와 몸무게는 정수(cm, kg)로 수집한다. 소수점은 저장 단계에서 잘리므로 입력에서 거부한다.
- 배우 프로필의 학력은 최종 학력(`NONE`·`HIGH_SCHOOL`·`UNIVERSITY`), 학교, 전공으로 저장한다. 학력 없음은 학교·전공 없이, 고등학교 졸업은 학교만, 대학교 졸업은 학교와 전공을 함께 가진다.
- 지원서에는 공고·공연·회사·포스터, 배우 정보(학력의 최종 학력·학교·전공 포함), 수집 필드, 선택 배역명과 답변을 제출 시점 스냅샷으로 저장한다.
- 제출 후 일반 수정·철회 API는 없다.
- 프로필 저장을 선택하면 프론트가 제출 성공 뒤 현재 프로필과 병합해 별도 프로필 PATCH를 호출한다. 제출 성공과 프로필 저장 성공은 하나의 트랜잭션이 아니다.
- 작성 중 지원서는 프론트의 IndexedDB에 저장한다. 현재 서버 Draft API는 없다.
- 최종 제출은 프론트가 만든 UUID 멱등 키를 요구한다. 같은 배우·키·내용의 재요청은 최초 제출 결과를 반환하고,
  같은 키의 내용이 달라지면 거부한다. 다른 키의 동일 공고 중복 지원은 기존 지원서 고유 제약으로 막는다.

## PDF 지원서 심사함

- 이메일로 받은 PDF를 공연사가 자기 심사함에 올리고 등록 배역별로 심사한다. 공고 생성·사이트 지원을 요구하지 않는다.
- 자동 처리는 원문 사실 전사와 명시된 지원 배역 연결만 수행한다. 합격·불합격·내부 메모는 담당자가 저장한다.
- 담당자가 등록 배역 연결을 바꾸면 이후 자동 추출이 그 선택이나 기존 심사 기록을 덮어쓰지 않는다.
- 미추출·애매한 프로필 정보는 미확인으로 보이고 원본 PDF를 확인한다. 자동 점수·적합성 판단은 하지 않는다.
- API와 상세 한도는 [PDF 심사 계약](../backend/docs/pdf-reviews.md)을 따른다. 아래 공고·차수 기반 심사와 별개다.

## 심사

- 심사 대상과 결과는 `(지원서, 공고 배역, 차수)` 단위다.
- 상태는 `PENDING`, `PASS`, `FAIL`, `ETC`다. `ABSENT`는 현재 계약에 없다.
- 마감된 이전 차수에서 `PASS`인 지원서만 다음 차수 심사 대상이 된다.
- 상태를 별도로 저장하지 않은 대상은 `PENDING`으로 계산한다.
- `ETC`에는 사유를 저장할 수 있고 모든 상태에는 내부 메모를 저장할 수 있다.
- 심사 마감은 공고 배역의 현재 차수 단위다. `PENDING`이 남아 있어도 마감할 수 있고, 미선택 지원자는
  `PENDING`으로 보존한다.
- 차수를 마감하면 `PASS` 지원서만 다음 차수 심사 대상이 된다. `PASS`가 없어 다음 차수 대상이 비면 이후 빈
  차수도 함께 마감하고 해당 배역 전형을 종료한다.
- 마감된 차수의 심사 결과는 수정하거나 되돌릴 수 없다. 같은 차수 마감 요청은 추가 완료 레코드를 만들지 않는다.

## 오디션 안내 문자

- 공연사가 외부에서 정한 일시를 배역·합격 기준 차수별 PASS 지원자에게 안내한다. 자동 시간 배정은 하지 않는다.
- 일반 공고와 OTR 공고에서 같은 문자 기능을 사용한다. OTR은 해당 공고·배역의 1차 합격자를 대상으로
  별도 일정을 입력한다. 일반 배역 ID와 OTR 배역 순번을 혼용하지 않으며 발송 내역도 공고별로 분리한다.
- 심사 마감 전·후 모두 허용한다. 다음 차수가 있으면 그 전형을 지정하고 마지막 차수는 별도 일정으로 안내한다.
- 전형 날짜와 다른 날짜는 경고 후 허용하고, 동일 일시는 허용한다. 한국 시간 기준 과거·현재 일시는 거부한다.
- 이름·연락처는 제출 당시 스냅샷에서 읽는다. 본문 앞에는 DB의 제작사명·공고명을 표시하고,
  이름·개인별 일시·추가 안내사항과 문의 연락처를 이어서 표시한다. 발송 전 서버가 구성한 최종 본문 전체를 확인한다.
- 공통 인증 발신번호를 사용한다. 문자 발송은 심사 결과, 마감, 다음 차수 승격을 바꾸지 않는다.
- 현재 UI는 초안을 저장하거나 불러오지 않는다. 기존 초안 API·데이터와 만료·개인정보 삭제 처리는 유지한다.
- 명시적으로 선택한 대상 모두를 검증하고 최종 본문·요금을 확인받는다. 잘못된 대상을 자동 제외하지 않는다.
- 발송 확정은 멱등 키로 중복 접수를 막는다. 업체 접수와 전달 성공을 구분하고, 불확실한 결과는 자동 재발송하지 않는다.
- 확정 실패 대상만 이전 문구·일시로 새 시도를 만들 수 있다. 동일 실패 시도에서 재발송을 중복 생성하지 않는다.
- 수신자별 개인정보는 접수 후 30일, 미발송 초안은 마지막 저장 후 30일에 삭제한다. 이는 제품 보관 정책이며 법정 보관 기간을 의미하지 않는다.
- 관리자 지원서 삭제는 해당 수신자 기록과 그 지원서를 포함한 초안 전체를 함께 지운다. 이미 외부 업체에 요청한 문자는 취소되지 않는다.
- 개인정보를 제외한 배치 식별자·멱등 해시·집계는 중복 요청 방지용으로 남긴다. 외부 업체 기록·백업 파기는 별도 운영 확인이 필요하다.

## 오디션 일정표

- 오디션 일정표는 공연·공고·OTR과 분리된 독립 모델이다. 회원 로그인 없이 기획사는 관리 링크, 배우는 개인 링크의
  열쇠(128비트 난수, URL-safe 22자)로만 접근한다. 배우 링크는 문자에 넣기 좋게 `/t/{열쇠}`로 짧게 둔다. 링크를 가진 사람은 누구나 같은 권한을 가지며, 열쇠는 API 경로가 아닌 헤더로 보낸다.
- 일정표는 작품명, 단체명(배우 문자에 들어감), 담당자 휴대폰(필수), 선택 담당자명·장소·안내 사항, 1인당 소요 시간(5분 단위 5~240분),
  칸 정원(1~50명)과 날짜별 시간대(바운더리)를 가진다. 시간대는 5분 단위 1~200개이며 같은 날 겹칠 수 없고 맞닿는 것은 허용한다.
- 시간 칸은 시간대 시작부터 소요 시간 간격으로 만들고 끝이 시간대를 넘는 칸은 만들지 않는다. 날짜·시각은 한국 시간이다.
- 배우는 이름과 휴대폰(필수)으로 한 명씩 또는 여러 명을 한 번에 등록한다. 한 일정표에 같은 번호는 한 번, 최대 300명이다.
- 상태는 `DRAFT`, `PUBLISHED`다. 확정하려면 배우가 한 명 이상이고 모두 시간이 정해져 있어야 하며, 확정하면 모든 배우에게
  합격·일정 안내 문자를 보낸다. 확정 뒤에도 기획사는 시간대와 배정을 고칠 수 있다.
- 한 번 저장한 시간대는 줄이거나 바꿀 수 없고 늘리기만 한다. 날짜·시간대를 더하거나 끝 시각을 늦추는 것은 되지만
  기존 시간 칸이 하나라도 사라지면 거절한다. 1인당 소요 시간은 바꿀 수 없고 칸 정원은 늘리기만 한다.
- 기획사는 보드에서 시간 늘리기와 배정을 고친 뒤 한 번에 저장한다. 저장 뒤 모든 배정은 바운더리 안에 있고
  칸마다 정원 이하여야 한다. 저장 요청은 옮긴 배우와 화면이 본 이전 시간을 함께 보내며, 그사이 배우가 직접 바꿨으면 거절한다.
  자동 배정은 저장 전 화면 편집 기능으로, 시간이 비어 있는 배우를 등록 순서대로 가장 이른 빈 칸부터 채운다.
  배우를 등록하면 방금 등록한 배우만 이 방식으로 미리 배정해 보여 주고 기존 배우의 시간은 바꾸지 않는다.
- 일정표는 시간대를 먼저 만들고 합격자를 나중에 등록한다. 확정 뒤에 등록한 배우는 추가 합격자로 표시하며, 시간을 받아
  저장하면 1차 합격자와 같은 합격·일정 안내를 받는다. 추가 합격자를 위해 일정표를 따로 만들지 않는다.
- 확정 뒤 안내를 받은 배우는 미배정으로 둘 수 없다. 기획사가 안내한 배우를 옮기면 일정 변경 안내를, 새로 시간을 받은
  배우에게는 첫 안내를 보낸다. 명단에서 뺀 배우의 링크는 열리지 않고 이미 보낸 문자는 취소되지 않는다.
- 시간은 기획사만 정한다. 배우는 링크에서 시간을 직접 바꿀 수 없고, 바꿔야 하면 시간 변경 문의(300자 이하)를 남긴다.
  배우마다 열린 문의는 하나이며 다시 보내면 내용을 바꾼다. 기획사가 그 배우를 옮겨 저장하거나 처리 완료로 닫으면 문의가 닫힌다.
- 배우는 링크에서 참석·불참을 알린다(처음엔 미응답, 다시 고를 수 있음). 기획사는 보드에서 배우별 응답과 참석·불참·미응답
  수를 본다. 기획사가 배우의 시간을 옮기면 응답은 미응답으로 돌아간다.
- 확정한 일정표는 현장용 표로 출력할 수 있다. 날짜별로 시간 칸마다 이름·연락처·비고를 적고, 비고에는 기획사가 그때 적은
  준비물 체크 항목과 불참 표시를 넣는다. 저장하지 않은 변경이 있으면 저장한 뒤 출력한다.
- 배우 링크는 확정 뒤 안내를 받은 배우만 열 수 있고, 다른 배우의 이름·번호와 칸별 인원은 보여 주지 않는다.

## 일정표 문자

- 기획사 화면은 문자가 자동으로 간다고 안내한다. 실제로는 발송 대기열에 넣고, 운영자가 관리자 화면에서 한 사람씩 번호와
  본문을 채운 문자 앱을 열어(`sms:` 링크) 직접 보낸 뒤 발송 완료로 표시한다. 한 문자에 여러 번호를 넣지 않는다.
  완료 표시는 운영자 변경 기록에 번호·본문 없이 남는다.
- 문자는 관리 링크(일정표를 만들 때 담당자에게), 시간 변경 문의 알림(담당자), 합격·일정 안내(배우마다 한 번),
  일정 변경 안내(기획사가 안내한 배우를 옮겼을 때)다.
- 본문은 모두 `[예술인] {제목}` 머리말, 인사(배우는 "지원자 {이름}님", 담당자는 "{단체명} {담당자명}님"이고 담당자명이 없으면 "{단체명} 담당자님"), 내용,
  `▶ {링크 이름}`과 링크, `[주의]` 공유 금지 문구, 마지막 줄 `예술인 {예술인 주소}` 순서다. 문자 업체로 바꿔도 깨지지 않도록
  이모지 대신 일반 특수문자를 쓴다. 합격 안내의 인사·내용은 기획사가 직접 쓸 수 있다(1000자 이하).
  `{이름}`·`{작품명}`·`{단체명}`·`{오디션일시}`·`{장소}`·`{안내사항}` 자리에 배우마다 값이 들어가고, 모르는 자리는 그대로 둔다.
  쓰지 않으면 기본 문구 "지원자 {이름}님, 안녕하세요. {단체명} 오디션에 합격하셨습니다. 아래 링크에서 '{작품명}' 오디션 일정을
  확인해 주세요."를 쓴다. 머리말·배우 링크·주의 문구·예술인 주소는 직접 쓴 문구에도 항상 붙는다.
- 받는 사람은 링크에서 항상 최신 일정을 본다. 그래서 아직 보내지 않은 안내·변경 문자가 있는 배우에게는 변경 문자를 더
  쌓지 않고 그 문자를 바뀐 일정으로 고치며, 아직 보내지 않은 문의 알림이 있는 일정표에는 문의 알림을 더 쌓지 않는다.
  문구나 작품 정보를 바꾸면 아직 보내지 않은 합격 안내도 새 내용으로 고친다.
- 대기열에 문자가 들어오면 스케줄 알림 Slack에 환경, 작품명·건수와 대기열 링크만 보낸다. 받는 사람 이름·번호와
  개인 링크는 보내지 않는다.
- 명단에서 뺀 배우의 미발송 문자와 요청은 함께 지운다. 문자의 번호는 넣을 때의 값으로 고정하고, 보낸 문자는 고치지 않는다.

## 파일과 보관함

- 공연 포스터는 JPEG·PNG·WebP, 최대 30MB다.
- 배우 사진은 JPEG·PNG·WebP, 최대 20MB다.
- 업로드 요청으로 presigned URL을 받은 뒤 객체 업로드와 완료 요청을 순서대로 수행한다.
- 완료 시 서버는 저장소의 Content-Type과 크기를 요청 메타데이터와 비교한다.
- 배우 거주 지역은 시·도와 시·군·구까지만 수집한다. 읍·면·동과 상세 주소는 받지 않는다.
- 배우 사진 보관함은 최대 3장이고 대표 사진은 표시 순서의 첫 항목이다.
- 배우 영상 보관함은 YouTube URL 최대 3개다.
- 보관함 항목 삭제는 soft delete이며 제출 스냅샷의 파일 참조와 분리된다.
