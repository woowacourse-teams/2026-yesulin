# 작업 평가와 PR 기록

## 규칙의 계층

최상위 `AGENTS.md`의 의무 → 대상 도메인 `docs/AGENTS.md`의 세부 기준 순서로 적용한다.
도메인 규칙은 공통 의무를 생략하지 않고 강화할 수 있다. 도메인의 `docs/README.md`가 필수 입구이며 같은 폴더의 `AGENTS.md`를 연결한다.
`docs/CLAUDE.md`는 `@AGENTS.md`로 그 규칙을 참조한다. 코드 영역 자동 적용을 가정하지 않고 명시적으로 읽는다. 최상위 CLAUDE만 같은 위치의 AGENTS를 불러온다.
하위 레이어·패키지에 규칙과 README를 흩어 놓지 않는다.

## 매 작업의 필수 절차

1. 공통 문서 라우터에서 대상 도메인의 `docs/README.md`를 찾아 연결된 `docs/AGENTS.md`와 해당 기능의 `docs/flows/`, `docs/policies/`를 읽는다.
   아직 없으면 이번 작업 범위의 최소 문서를 도메인 루트의 `docs`에 만든다. 공통 규칙 작업은 이 문서를 기준으로 한다.
2. 수정 전에 평가표를 만든다. 항목 ID, 흐름 단계, 실패 조건, 기대 결과, 검증 방법, 필수 여부를 적는다.
   정상·실패·중복·중단/복구·권한·수동 수정 보호 중 해당하는 경계를 검토하고, 제외 항목에는 사유를 적는다.
3. 구현·문서·필요한 검증을 마친 뒤 별도 평가 에이전트에게 변경 diff, 흐름·정책, 평가표와 검증 근거를 전달한다.
   작업자가 Codex면 Claude, Claude면 Codex를 우선한다. 대체 도구를 사용할 수 없으면 같은 종류의 별도 에이전트를 쓴다.
   실행할 수 없으면 평가 미실시로 보고하고 완료로 주장하지 않는다. 평가자는 읽기 전용으로 검토하며 평가자를 다시 만들지 않는다.
4. 기본 평가는 **한 차례**다. 평가자가 발견한 문제를 판별·수정하고 수정 부분을 표적 검증한다.
   이는 두 번째 전체 평가를 뜻하지 않는다. 추가 평가 횟수·조건은 도메인 규칙에서 명시한다.
5. 평가표와 문제 목록을 도메인 `docs/reviews/`에 남기고, 사용자에게 결과·수정·미확인 범위를 보여준다.
   PR 생성/갱신 시 아래 집계와 같은 문제 ID를 반드시 본문에 기록한다. PR을 만들지 않는 작업도 기록을 보존하고
   다음 PR에 포함한다. PR이 없으면 게시했다고 말하지 않는다.

## 필수 정리 점검

평가자는 이번 작업의 추가·수정·이동·삭제 파일을 기준으로 미사용 코드·파일·설정·의존성·문서와 깨진 링크를 확인한다.
참조 검색에 더해 DI, 리플렉션, 진입 스크립트, 빌드 패키징, 운영 계약을 확인한다. 참조가 없다는 이유만으로 삭제하지 않는다.
남기는 호환 코드·실험 경로는 소비자, 유지 이유와 제거 조건을 기록한다. 범위 밖 전체 저장소 정리를 강제하지 않는다.

## 판정과 근거

- 항목 결과: `PASS`(기대 결과를 확인한 근거), `FAIL`(재현 가능한 불일치), `UNVERIFIED`(실행/증거 부족),
  `N/A`(적용하지 않는 이유). 코드 열람으로 확인할 수 있는 기준과 실행이 필요한 기준을 구분한다.
- 근거에는 파일/심볼·테스트명·명령/실행 결과·환경·날짜를 남긴다. 추측, 작성자의 설명, 테스트 통과 건수만으로
  해당하지 않는 흐름까지 PASS로 처리하지 않는다. 비밀·지원서 원문은 기록하지 않는다.
- 검증률은 `필수 PASS / (필수 PASS + FAIL + UNVERIFIED)`다. N/A는 사유와 함께 제외한다.
  필수 항목이 없으면 비율은 N/A다. 이 비율은 검증 범위이며 무장애 확률·모델 정확도가 아니다.
- P0(보안/데이터 유실 등 즉시 차단)·P1(핵심 흐름 고장)은 미해결이면 완료 판정을 하지 않는다.
  필수 UNVERIFIED가 있으면 조건부 결과로 표시한다. PR 초안이나 미검증 사실 공개를 막는 규칙은 아니다.
- 모델 정확도·처리량이 필요한 도메인은 표본·정답·측정 환경·성공 정의를 별도로 정한다.
  테스트 수나 에이전트 동의 수를 품질 점수로 대체하지 않는다.

## 문제와 집계

- 작업 ID는 `YYYY-MM-DD-domain-topic`, 문제 ID는 `<작업 ID>-F01` 형식으로 고정한다.
- 문제마다 심각도(P0~P3), 유형(`FLOW/POLICY/CODE/UNUSED/DOC/TEST`), 유입(`INTRODUCED/EXISTING`),
  근거, 조치, 상태(`FIXED/OPEN/REJECTED`), 수정 후 검증 결과를 적는다. 알 수 없는 유입은 `UNKNOWN`이다.
- 발견 경로는 `PRECHECK`(구현자 사전점검), `INDEPENDENT_REVIEW`(별도 평가), `POST_FIX_CHECK`(수정 후 검증),
  `EXTERNAL` 중 하나로 고정하고 최초 확정 시각(ISO 8601, +09:00), 최초 기록 PR, 해결 시각을 문제별로 남긴다.
  재검증 발견 건수는 INDEPENDENT_REVIEW와 POST_FIX_CHECK를 별도로 합산하고 PRECHECK와 섞지 않는다.
  PR 생성 전 최초 기록 PR은 `PENDING`이며, 처음 게시할 때 실제 번호로 연결한다.
- 확정 문제만 발견 수에 포함한다. 오탐(REJECTED)과 미확인 항목은 별도로 센다.
  이미 다른 PR에 기록된 문제는 기존 ID로 참조하고 신규 발견 수에 더하지 않는다.
  재발·다른 근본 원인의 문제는 새 ID와 관련 ID를 남긴다. 같은 문제의 여러 증상·재평가는 한 건이다.
- 한 문제는 주 유형 하나로만 집계한다. `발견 = 해결 + 미해결`, `발견 = P0 + P1 + P2 + P3`를 맞춘다.
  미확인 항목 수는 평가표 UNVERIFIED 수이며 결함 수에 더하지 않는다.
- 발견·해결·재개·오탐 확정은 문제별 추가 전용 이력에 사건 ID, 문제 ID, 사건 종류
  (`CONFIRMED/FIXED/REOPENED/REJECTED`), 발생 시각(+09:00), 근거·관련 PR을 새 행으로 남긴다.
  기존 사건을 덮어쓰지 않는다. 정정은 앞 사건 ID를 참조하는 정정 행을 추가하고 취소·대체 대상을 명시한다.
  PR 본문의 현황 표는 갱신할 수 있지만 저장소 평가 기록의 과거 이력은 보존한다.
- 기간별 집계는 대상 PR 집합에서 문제 ID를 중복 제거한다. 각 PR의 신규 발견 수와 누적 문제 현황을 섞지 않는다.
  발견은 최초 CONFIRMED 시각, 해결은 FIXED 사건 시각으로 집계한다. PR 생성·최종 갱신 시각을 대신 쓰지 않는다.
  기간 말 미해결은 보존된 사건을 순서대로 적용해 재구성한다. 정정된 사건은 집계에서 제외한다.
  PR 없는 작업은 기간 PR 통계에 아직 포함하지 않고, 이후 게시해도 실제 최초 확정 날짜를 바꾸지 않는다.
  기간 해결 건수는 그 기간 FIXED 사건이 있는 고유 문제 ID 수이며, 같은 기간 반복 해결은 한 번만 센다.
  REOPENED 건수와 기간 말 미해결은 별도 지표다. 과거 기간을 재집계할 때도 동일한 보존 이력을 쓴다.
  PR 수·변경 규모·평가표 버전·필수 항목 수도 함께 보며, 결함 수가 적다는 이유만으로 품질이 높다고 결론내리지 않는다.

## PR에 반드시 남길 형식

`.github/pull_request_template.md`를 사용한다. 필수 요약은 작업 ID, 평가일, 도메인·평가표 버전, 평가 1회 여부,
필수 PASS/FAIL/UNVERIFIED/N/A, 신규 확정 문제의 발견/해결/미해결/P0~P3, 발견 경로별 건수, 오탐,
문제별 최초 확정/해결 시각·최초 PR·상태 사건 이력 링크, 미확인 범위다.
여러 작업이 한 PR에 들어가면 작업별 요약을 유지한다. 없었던 문제를 채우거나 과거 발견을 이번 발견으로 꾸미지 않는다.
평가 도구 이름은 PR에 쓰지 않고 `독립 평가 1회`와 근거를 적는다. 도구 선택·대체 사유는 내부 평가 기록에 남긴다.
