# 이슈와 프로젝트 보드 워크플로

## 계기

이슈 제목과 라벨이 작업마다 즉흥적으로 갈렸고, 어떤 작업을 먼저 할지 판단할 기준도 없었다.

## 결정

- 이슈 제목은 커밋과 같은 `{type}: {summary}` 형식을 쓴다.
- `type:*` 라벨 8개를 브랜치·커밋 타입과 1:1로 두고 최소 하나 붙인다.
  `frontend/`·`backend/`에 걸치면 `scope:frontend`, `scope:backend`도 붙인다.
- `priority:p1`(MVP 필수), `priority:p2`(중요), `priority:p3`(후순위) 중 하나를 붙인다.
- 조직 프로젝트 보드 `woowacourse-teams/2026-yesulin`(#131)을 재사용하고
  `Status`는 `Todo` → `In Progress` → `Done` 세 단계만 쓴다.
- 이슈는 생성과 동시에 보드에 올리고 만든 사람에게 배정한다.
  PR 본문의 `Closes #123`이 병합 시 이슈를 닫고 보드를 `Done`으로 옮긴다.
- `.github/ISSUE_TEMPLATE/`에 `버그 신고`와 `기능/작업` 템플릿을 둔다.

## 이유

브랜치·커밋·라벨이 같은 어휘를 쓰면 이슈에서 PR까지 새로 배울 것이 없다.
보드를 세분화하지 않는 것은 팀 규모가 작아 관리 비용만 늘기 때문이고,
이미 있는 조직 표준 보드를 쓰면 별도 생성·관리 부담이 없다.

우선순위 라벨은 처음에 "팀 규모가 작아 트래킹 비용만 는다"는 이유로 도입하지 않기로 했으나
이슈가 20개를 넘기면서 MVP 필수와 후순위를 구분할 기준이 필요해졌고,
실제로 23개 이슈에 사용 중이라 결정을 뒤집어 정식 규칙으로 확정한다.

## 영향

세부 규칙은 [Git 컨벤션](../convention/git-convention.md)에 있고
에이전트가 읽는 경로는 `AGENTS.md`에 노출한다. 이후 모든 이슈는 이 규칙을 따른다.
