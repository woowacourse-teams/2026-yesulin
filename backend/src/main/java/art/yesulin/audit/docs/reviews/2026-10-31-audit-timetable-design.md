## 현재 코드로 확인한 범위

- PDF 심사: 소유 공연사의 지원자 판정·배역·메모. 합격자 연락처 화면은 PDF 추출 텍스트로 이름/전화/이메일을 조회하며 확인한 연락처를 별도 저장하지 않는다.
- 독립 일정표: 로그인 없이 관리 열쇠로 접근. 날짜·시간·정원 설정, 이름+휴대폰 등록, 자동 배정 미리보기/수동 배정, 저장, 확정, 참석·불참 응답, 변경 문의, 출력이 있다.
- 배우는 개인 링크로 자기 일정만 보고, 시간을 직접 바꾸지 않고 문의를 남긴다. 참석 응답은 당일 실제 출석 체크가 아니다.
- 일정표 배우는 휴대폰 필수, 같은 일정표에서 번호 유일, 최대 300명. 이메일·배역·PDF 지원자 참조·공연사 소유 연결은 현재 모델에 없다.
- 확정은 등록 배우 전원 배정 필요. 확정 뒤 추가 등록 가능. 확정 뒤 새 배정/시간 변경을 저장하면 안내 문자를 대기열에 넣는다.
- 실제 문자 업체 자동 발송은 미구현. 운영자가 대기열에서 직접 발송하고 완료 표시한다. `invited`는 대기열 등록을 뜻하므로 발송 완료로 표시하면 안 된다.
- 저장한 시간 설정은 확장만 가능하다. 칸 길이 변경/정원 축소는 현재 불가하므로 새 화면에서도 설정 전에 설명한다.
- 근거: `frontend/src/features/timetables/types.ts`, `frontend/src/components/timetables/manage/timetable-manager.tsx`, `backend/src/main/java/art/yesulin/timetable/application/TimetableService.java`, `backend/docs/api.md`의 오디션 일정표, `docs/domain.md`의 오디션 일정표/문자, `docs/implementation-gaps.md`.

## 제안하는 화면 흐름

심사함 내부에 `지원서 심사 / 합격자 명단 / 오디션 일정` 세 진입을 제공한다. 판정 버튼·PDF 배치는 유지한다. 기존 합격자 연락처 화면을 명단 탭으로 활용한다. 명단에는 선택 체크박스·배역 필터·일정 상태와 `선택한 N명 일정에 추가` 버튼을 붙인다. 합격자의 이름/전화/이메일/PDF 보기 구성은 유지한다.

1. PDF에서 합격 처리. 이 시점에는 일정 생성·문자 등록을 하지 않는다.
2. 합격자 명단에서 대상을 선택한다. 자동 추출 값은 초안이며 담당자가 원문으로 확인·수정한다. 연락처 읽기 실패/여러 개/이름 미확인은 구분하고, 확인된 인원만 진행한다. 이메일은 선택이다.
3. 연결 일정이 없으면 작품/담당자/장소, 날짜, 시간대, 1인 소요 시간, 칸 정원을 입력한다. 제목과 회사 이름만 가능한 범위에서 미리 채우고 필수 휴대폰 등을 추정하지 않는다. 날짜별 시간대를 나누어 점심/휴식 구간을 비워 둔다.
4. 연결 일정이 있으면 `기존 일정에 추가`로 진행한다. 첫 버전 UI는 심사함당 일정표 하나이며 생성 요청 중복에도 서버가 하나만 만든다. 내부 관계는 심사함 1:N 일정 연결이 가능하게 두되 복수 차수 기능은 후속 제안이다.
5. `이미 등록 / 추가 가능 / 연락처 확인 / 중복 번호 / 정원 한도 초과` 미리보기 후 선택한 인원을 등록한다. 이름 30자·작품명 60자 등 기존 일정 API 길이 제한도 미리 표시하고 임의 잘라 저장하지 않는다. 이름·전화 필수, 이메일 선택. 기존 칸 잔여 정원과 300명 상한은 별도로 표시한다.
6. 기존 일정 보드를 재사용한다. 배역 필터와 PDF 원문 이동을 추가하고, 새로 가져온 사람만 이른 빈 시간부터 배정 미리보기를 한다. 기존 배정은 그대로 두며 자리가 모자란 사람은 미배정으로 남긴다. 저장 전에 배정 결과를 확인한다.
7. `일정 확정·안내 요청`에서 대상/문구/시간·장소를 보여 준 뒤 확정한다. 현재 구조에 맞게 발송 대기라고 표시한다. 확정된 일정에서 추가 배정·변경 저장 역시 발송 대기열이 생김을 저장 직전 표시한다.
8. 배우 응답·변경 문의는 기존 기능으로 관리한다. 담당자는 문의를 보고 직접 재배정한다. 인쇄는 기존 현장용 표를 쓴다. 실제 체크인·현장 점수·최종 합격은 이번 범위에 넣지 않는다.

[지원서 심사] [합격자 명단] [오디션 일정]

합격자 명단                         [선택한 6명 일정에 추가]

## 데이터와 경계 제안

- 심사(Audit): 원본 PDF·지원자 ID·배역·판정·내부 메모의 정본 유지.
- 일정(Timetable): 날짜·배정·참석 응답·변경 문의·안내 요청의 정본 유지. 심사 상태와 출석 의향을 합치지 않는다.
- 연결 데이터: `reviewId ↔ timetableId`, 일정 참가자별 `sourceApplicantId ↔ timetableActorId`. 이름/확인된 전화/이메일/배역은 등록 시 스냅샷으로 기록한다. 후보 이름이 같다고 동일인으로 판단하지 않는다.
- `(timetableId, sourceApplicantId)` 유일성과 기존 `(timetableId, normalizedPhone)` 제약을 함께 사용한다. 같은 출처를 다시 가져오면 기존 등록으로 응답한다. 번호가 같고 출처가 다르면 자동 병합하지 않고 사용자가 대표 지원서를 선택하도록 막는다. 여러 지원서를 한 배우로 합치는 기능은 후속이다.
- 가져오기 요청은 출처 ID와 담당자가 확인한 연락처를 보낸다. 서버는 실제 로그인 공연사 소유의 원본·일정인지, 해당 출처가 현재 PASS인지, 문자열 형식·길이·중복·상한을 다시 검증한다. 클라이언트가 보낸 합격 여부/소유자 값은 신뢰하지 않는다. 연락처는 추출 사실이 아닌 담당자 확인 값으로 저장한다.
- 미리보기 뒤 판정이 바뀌면 등록을 거절하고 재확인을 요청한다. 원본 상태 검증과 등록은 동일 트랜잭션 안에서 일관되게 처리한다. 일정 잠금/DB 유일성으로 동시 클릭을 막고, 검증 실패 시 요청 배치는 전부 취소한다. 이미 등록된 동일 출처는 건너뛰므로 응답 유실 후 재시도도 중복이 생기지 않는다.
- 일정 생성과 배우 가져오기를 분리한다. 생성만 성공하고 가져오기가 실패하면 연결된 초안으로 다시 진입해 재시도한다. 후보 선택·확인 값은 서버 성공 전 화면에 보존하고 실패 인원을 명시한다. 원문/연락처는 URL·분석 이벤트·브라우저 영구 저장소로 전달하지 않는다.
- 합격 이후 보류/불합격 변경, 연락처 재추출, 배역 변경을 일정에 자동 반영하지 않는다. 기존 배정과 안내를 보존하고 `심사 정보 변경·확인 필요`를 표시한다. 담당자가 취소/유지 등을 확인하기 전에는 대상의 새 안내 요청을 막는다. 취소 문자 기능은 현재 없으므로 제외 시 별도 연락이 필요함을 알린다.
- 발송된 안내 이력과 미발송 큐는 분리한다. 연결된 지원자가 확인 필요 상태가 되면 기존 PENDING 안내도 보류하고 새 큐 등록을 막는다. 판정 변경과 보류 표시가 함께 반영되도록 서버에서 처리하며, 운영자 큐 조회뿐 아니라 문자 앱을 열기 위한 최신 본문 요청에서도 출처 상태·보류 여부를 재검증한다. 담당자가 일정 참가 유지로 확인하면 해당 확인 버전에 대해 최신 배정/문구로 재개하고, 명단 제외 시 미발송 큐를 폐기한다. 판정이 다시 바뀌면 재확인이 필요하다. 이를 위한 보류 상태/확인 버전/문자 열기 전 검증 API는 신규 구현 범위다. 이미 문자 앱에 전달했거나 실제 발송한 내용은 회수할 수 없으므로 확인 필요로 바뀌었다는 운영자 경고와 별도 연락 절차를 제공한다. 수동 외부 발송과 내부 DB를 하나의 원자적 작업으로 보장한다고 주장하지 않는다.
- 등록된 이름·휴대폰은 현재 엔티티에서 변경 불가하다. 첫 버전에서는 가져오기 전 수정만 지원하고, 가져온 뒤 연락처 정정은 별도 API·배우 링크·미발송 큐 재검증 설계가 필요하다. 재가져오기로 덮어쓰지 않는다.
- 이메일은 명단·일정 담당자 조회용으로 전달하되 이메일 발송 기능으로 확대하지 않는다. 이메일만 있는 사람은 원본 명단에 남기고 휴대폰 확인 전 일정 등록하지 않는 것이 첫 버전 제안이다. 번호 없는 등록은 기존 모델 변경이 필요하다.

## 인증 연결 제안

기존 익명 일정표는 유지하고 PDF 심사에서 생성한 일정은 로그인 공연사 소유로 구분한다. 공개 관리 링크를 로그인 페이지에 단순 저장하는 방식은 사용하지 않는다.

- 새 owner 기반 API/라우트를 둔다. 후보 예: `/producers/pdf-reviews/{reviewId}/timetable`, `/api/v1/pdf-reviews/{reviewId}/timetables` 및 등록/배정/확정 하위 동작. 실제 HTTP 계약은 구현 때 확정한다.
- 서버에서 원본·일정의 소유권을 모두 검증한다. 공유할 수 있는 관리 열쇠를 브라우저 응답이나 분석에 내보내지 않는다.
- owner 관리 일정은 기존 익명 관리-key API로 접근하지 못하게 명확히 차단한다. 기존 익명 일정 연결/소유권 이전은 첫 버전에서 제외한다.
- 기존 생성 이벤트가 담당자 관리 링크 문자를 만드는 점을 주의한다. owner 일정은 익명 관리 링크를 만들거나 큐에 넣지 않고 로그인 기반 관리 경로를 사용한다. 배우 개인 링크는 기존처럼 자기 일정 정보만 제공한다.
- 도메인 배정/충돌 검사·배우 개인 응답·메시지 큐를 재사용하고 접근 제어 어댑터를 분리한다. 모든 actor/request ID는 해당 일정 소속인지 검증한다.

## 상태 표시 제안

| 상태 축 | 예시 | 주의 |
| --- | --- | --- |
| 서류 판정 | 합격 / 보류 / 불합격 | 오디션 최종 합격으로 해석하지 않음 |
| 시간 배정 | 미등록 / 미배정 / 배정 완료 | 연락처 확인 필요는 별도 가져오기 상태 |
| 안내 | 안내 전 / 발송 대기 / 확인 필요·발송 보류 / 운영자 발송 완료 | 기존 invited를 발송 완료에 쓰지 않음, 수신 보장은 아님 |
| 참석 응답 | 미응답 / 참석 예정 / 불참 | 당일 출석 체크 아님 |

안내 상태를 공연사에 보여 주려면 현재 관리자 큐 상태를 owner 응답에 필요한 범위만 투영하는 API가 추가로 필요하다. 현재 구현된 상태라고 표시하지 않는다.

## 첫 구현 범위와 보류

1. 공연사 소유 일정 연결·권한, 심사함에서 일정 재진입.
2. 합격자 선택·연락처 확인·중복/한도 미리보기와 멱등 가져오기.
