# 부하 테스트 시나리오와 면접 설명 안내

2026-10-12 작성. 처음 부하 테스트를 설계하는 사람을 위한 참고 자료다.
공개 사례는 출처에 나온 과거 경험이며, 아래 교육용 예시와 면접 질문은 이 문서에서 구성했다.
예술in의 실제 성능·병목·개선 결과를 측정했다는 뜻은 아니다.
실행 조건은 [측정 계획](./load-testing-sprint2-plan.md), 실제 실행 사실은 [첫 확인 기록](./load-testing-sprint2-first-check.md)을 따른다.

## 1. 무엇부터 정하는가

시나리오는 “누가, 어떤 상황에서, 무슨 일을 하는가”다.
부하는 “그 일을 얼마나 빠르게, 얼마나 오래 반복하는가”다.
가게라면 “손님이 메뉴를 보고 주문한다”가 시나리오이고, “1분마다 주문 30개가 들어온다”가 부하다.
같은 시나리오를 낮은 부하·평상시 부하·집중 부하에서 각각 확인할 수 있다.

다음 순서로 설계하면 된다.

1. 중요한 사용자 장면을 하나 고른다. 공고 목록 조회, 공연 예매, 지원서 제출 같은 장면이다.
2. 호출할 API, 데이터 양과 분포, 요청률 또는 가상 사용자 수, 지속 시간을 정한다.
3. 빠르다는 기준과 올바르게 동작한다는 기준을 정한다.
4. 작은 부하로 주소·데이터·응답 검사·관측·중단 조건을 확인한다.
5. 목표 조건을 측정하고, 원인을 조사할 추가 조건은 따로 기록한다.
6. 병목 하나를 바꾼 뒤 동일 조건에서 다시 측정하고 기능 회귀도 확인한다.

API 한 개부터 사용자 흐름으로 범위를 넓히는 접근은 [k6 API 부하 테스트 안내](https://grafana.com/docs/k6/latest/testing-guides/api-load-testing/)를 참고한다.

## 2. 공개된 실제 사례

### 우아한형제들: 포인트 시스템 전환

2018년 공개 사례에서 포인트 API의 성능 목표를 **주말 피크 주문량의 5배에 해당하는 TPS**로 잡았다.
포인트 적립·가용 포인트 조회가 주문량과 관계있다는 점을 근거로 사용했다.
nGrinder로 부하를 만들고 Pinpoint와 DB 지표로 병목을 확인했으며, JVM 예열을 비교에서 구분했다.
출처: [신규 포인트 시스템 전환기 #2 – 오픈 준비 단계](https://techblog.woowahan.com/2588/).

우리에게 적용할 점은 사용자 행동과 요청량을 연결하는 근거, 자원과 요청 추적을 함께 보는 방식이다.
이 회사의 배수·TPS·서버 규모를 우리 서비스의 목표나 안전 조건으로 그대로 사용하지 않는다.

### 카카오: 온라인 코딩 테스트 서버

과거 공개 사례에서 약 700명의 참가자와 토큰별 초당 50개 요청 제한을 이용해 35,000건/초를 예상 부하로 계산했다.
이 값의 약 2~3배에도 대응하도록 준비했다고 설명하며, 실제 최고 트래픽은 약 6,000건/초였다고 기록했다.
출처: [카카오 신입 공채 2차 코딩 테스트 문제 해설](https://tech.kakao.com/posts/347).

이 계산은 모든 참가자가 요청 제한에 가깝게 동시에 호출한다는 상한에 가까운 시나리오다.
예상치와 실제 관측치는 다를 수 있으며, 계산 근거를 밝히는 것이 중요하다는 참고 사례로 사용한다.
이 숫자는 일반적인 웹 서비스의 표준 부하가 아니다.

## 3. 서비스별로 구성해볼 수 있는 시나리오

아래 표는 특정 회사가 수행한 실험을 인용한 것이 아니라, 설계를 이해하기 위한 교육용 예시다.

| 서비스 | 사용자 장면 | 실험 조건을 바꾸는 방법 | 확인할 것 |
| --- | --- | --- | --- |
| 게시판·쇼핑몰·공고 | 목록을 보고 상세를 연다 | 같은 데이터에서 요청률을 올린다. 자료 양을 늘리는 실험은 별도로 한다 | p95/p99, 오류, SQL 시간·횟수, CPU, DB 연결 대기 |
| 쿠폰·티켓 | 정해진 오픈 시각에 같은 상품을 신청한다 | 짧은 순간에 같은 대상의 쓰기 요청을 집중한다 | 지연·잠금 대기, 발급/예매 수량, 중복·초과 처리 |
| 검색 | 검색어와 필터를 바꾸며 자료를 찾는다 | 인기 검색어와 다양한 검색어, 데이터 양, 첫 페이지와 깊은 페이지를 구분한다 | 검색 시간, 읽은 행, 실행계획, 조건에 맞는 결과 |
| 지원·신청 | 마감 직전에 신청하고 실패한 요청을 다시 보낸다 | 여러 사람의 제출과 동일 사람의 재시도를 구분한다 | 처리량·대기, 중복 저장, 재시도와 멱등성 |
| 장시간 사용하는 서비스 | 일정한 요청이 계속 들어온다 | 일정 부하를 긴 시간 유지한다 | 메모리·GC, 연결 반환, 시간이 지나며 응답이 느려지는지 |

목록 실험은 서로 다른 공고를 찾는 요청도 있어야 특정 페이지·ID만 반복한 캐시 효과에 치우치지 않는다.
반대로 인기 공고 하나의 조회수 쓰기 경합을 조사한다면 같은 ID에 집중하는 것이 실험 목적에 맞다.
쓰기 실험에는 고유 사용자·키와 준비된 상태가 필요하며, 예상되는 재고 소진·중복 거절과 시스템 오류를 구분해야 한다.
실제 결제·SMS·이메일 같은 외부 작업은 테스트용 연동과 목적을 먼저 정한다.

## 4. 요청 수를 정하는 계산 예시

아래는 가상의 서비스이며 실제 예술in 통계가 아니다.

- 이벤트 링크를 받은 100명이 1분 안에 방문한다고 가정한다.
- 한 명이 목록 API를 2번, 상세 API를 3번 호출한다고 가정한다.
- 계산상 GET 요청은 `100 × (2 + 3) = 500`건이고, 1분 평균은 `500 / 60 ≈ 8.3 RPS`다.
- 여유를 두어 합계 GET 10 RPS를 후보로 삼을 수 있다. 실제 1초 최대량을 관측한 값은 아니다.
- 이를 5분 유지하면 계산상 3,000건의 GET을 만드는 추가 용량 실험이다. 원래 100명의 방문을 그대로 재현한 것은 아니다.

혼합 GET 10 RPS를 위 호출 비율로 나누면 목록 약 4 RPS, 상세 약 6 RPS다.
목록 API만 10 RPS로 검사하면 단일 API 성능 실험이며, 위 방문 흐름과는 다른 조건이다.
조회수 기록·로그인 확인 등 추가 호출을 포함하려면 계산과 스크립트에 따로 반영한다.
사람들이 읽고 고민하는 간격도 방문 흐름에서는 필요하다.

가상 사용자(VU)는 요청을 보내는 가짜 사람 수이며 요청률(RPS)과 단위가 다르다.
고정된 가상 사용자가 응답을 기다렸다가 다음 요청을 보내는 방식에서는 응답이 느려지면 새 요청도 줄어들 수 있다.
일정한 요청률을 검증하려면 요청 도착률을 정하는 방식과 실제 전송·완료·누락 수를 함께 확인한다.
참고: [k6의 open/closed 부하 모델](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/).

## 5. 예술in에서 먼저 적용할 범위

현재 추천 장면은 **공고 링크를 공유받은 사람이 목록과 상세를 보러 오는 상황**이다.

먼저 공개 목록 `GET /api/v1/public/audition-posts`를 단독 측정하면 결과를 해석하기 쉽다.
병목이 의심되는 SQL과 같은 시각의 자원·요청 지연을 연결하고, 개선 한 건을 동일 조건에서 비교한다.
이후 공개 목록 → 상세 흐름으로 범위를 넓힐 수 있다. 이 후속 스크립트를 이미 구현하거나 실행한 것은 아니다.

조회수 기록은 별도의 `POST /api/v1/public/audition-posts/{postId}/views`다.
현재 단독 GET 실험은 이 쓰기를 재현하지 않는다. 조회수 경합까지 검증하려면 별도 조건과 동작 검사가 필요하다.

OTR 2023년 월간 캡처는 성장 참고 자료이며, 피크와 API 호출량을 관측한 값은 아니다.
기존 10 RPS 초기 목표안과 30 RPS 성장 후보를 실제 유입·확정 합의·성능 측정 결과로 설명하지 않는다.
자료가 부족한 부분은 가정으로 밝히고, 요청률과 자료 양을 한꺼번에 바꿔 원인 해석을 어렵게 만들지 않는다.
현재 DEV 지속 부하·데이터 적용·개선 전후 비교는 미실행 상태다.

## 6. 면접에서 설명을 확인할 수 있는 예상 질문

아래 질문은 특정 회사의 실제 기출이나 공통 면접 기준이 아니다.
이 프로젝트의 부하 테스트 경험을 검토하기 위해 구성한 연습 질문이다.
측정하지 않은 수치를 답변 예시로 만들어 성과라고 사용하지 않는다.

| 예상 질문 | 확인하려는 내용 | 준비할 근거 |
| --- | --- | --- |
| 왜 공고 목록을 골랐나요? | 사용자 장면과 테스트 대상의 연결 | 공유 링크 유입, 공개 조회의 중요성, 다른 후보보다 우선한 이유 |
| 왜 그 요청률과 시간을 정했나요? | 실측·가정·목표를 구분할 수 있는가 | 출처·기간, 방문 행동 계산, 순간 집중 가정, 목표 유지 시간 |
| 100 VU와 100 RPS는 무엇이 다른가요? | 부하 생성 방식을 이해하는가 | 가짜 사람 수와 초당 호출 수, 대기 시간, 실제 요청량·누락 |
| 평균이 빠른데 왜 p95를 봤나요? | 일부 사용자에게 긴 지연이 생기는지 확인하는가 | 전체 응답 분포, p95/p99, 오류와 timeout. p95는 평균이 아니다 |
| DB가 병목이라는 근거는 무엇인가요? | 느린 응답과 원인을 구분하는가 | 같은 시각의 SQL 시간·횟수·실행계획, DB 자원·대기. CPU 하나로 확정하지 않는다 |
| 원인은 서버가 아니라 부하 생성기 아닌가요? | 설정한 압력을 실제로 만들었는가 | 생성기 CPU·메모리·네트워크, 실제 시작·완료 수와 dropped iterations |
| 개선 덕분에 빨라졌다는 것을 어떻게 확인했나요? | 비교 조건을 통제했는가 | 서버·DB·데이터·API·요청률·시간·예열·로그 수준 고정, 변경 SHA, 반복 결과 |
| 다른 해결책은 왜 선택하지 않았나요? | 해결책과 부작용을 비교했는가 | 쿼리·응답 변경, 인덱스, 캐시 등 검토한 대안과 비용. 실제 검토한 내용만 말한다 |
| 데이터가 작거나 캐시가 따뜻해서 빠른 것 아닌가요? | 실험이 확인한 범위를 아는가 | 데이터 수·분포·본문 크기, ID/페이지 선택, 예열과 캐시 조건 |
| 테스트 서버 결과를 운영에도 적용할 수 있나요? | 환경 차이와 결과의 한계를 아는가 | 서버·DB 사양과 설정 차이, 공유 자원·동시 작업. 선형 환산으로 운영 용량을 보장하지 않는다 |
| 빨라지면서 동작이 바뀌지는 않았나요? | 성능과 정확성을 함께 검증했는가 | 응답 내용·정렬·필터·공개 상태, CI 기능 회귀 테스트 위치와 실행 결과 |
| DB를 바꿨다면 어떻게 배포하나요? | 스키마 변경을 재현할 수 있는가 | 실제 마이그레이션 파일·도구·검증 결과와 prod ddl-auto 설정 |

기능 회귀 테스트는 변경 전후 응답과 비즈니스 규칙을 검증한다.
부하 테스트는 정한 조건에서의 성능과 오류를 측정한다. 일반 기능 테스트 통과만으로 목표 RPS 달성을 주장하지 않는다.
매 PR마다 큰 부하 테스트를 수행해야 한다는 뜻도 아니다. 성능 비교는 환경·데이터·실행 시점을 관리해야 한다.
환경과 실행 주기를 구분하는 방법은 [k6 자동 성능 테스트 안내](https://grafana.com/docs/k6/latest/testing-guides/automated-performance-testing/)를 참고한다.

## 7. 면접 설명을 준비하는 순서

다음 여섯 가지를 측정 기록에서 찾아 자기 말로 연결한다.

1. 사용자에게 중요한 장면과 그 API를 선택한 이유.
2. 부하 조건을 계산한 근거와 아직 확인하지 못한 가정.
3. 개선 전 지표와 원인을 판단한 증거.
4. 선택한 변경과 그 선택의 이유·부작용.
5. 같은 조건으로 확인한 개선 후 결과와 CI 기능 회귀 검증.
6. 운영 환경 적용 시 남은 한계.

현재는 준비 단계이므로 “실험 조건을 설계했다”, “안전 장치를 확인했다”까지만 설명한다.
실제 실행 후 요청량·지연·오류·원인 지표와 전후 결과를 채운다.
