# 스프린트 2 부하 테스트: 처음 이해하기

2026-10-12 기준 설명이다. 아래 요청률과 데이터 수는 계획·계산 예시이며 실제 측정 결과가 아니다.
실행 사실은 [첫 확인 기록](./load-testing-sprint2-first-check.md), 선정 근거는 [측정 계획](./load-testing-sprint2-plan.md)에 남긴다.

## 지금까지 한 것

- 실제 DEV에 지속 부하를 보내는 실험은 아직 하지 않았다.
- DEV 공개 목록에 단일 GET을 보내고, AWS 접속으로 환경·배포 버전·DB 공고 수·스키마를 조회했다.
- 가짜 공고 SQL을 로컬 파일로 만들었다. DEV DB에 적용하지 않았다.
- 내 컴퓨터의 가짜 API로 k6의 요청·응답 검사·중단 장치를 검증했다. 이는 실제 서버 성능 결과가 아니다.
- 40건 SQL은 최소 점검용으로 생성만 했고, 본 실험 데이터는 1,000건으로 시작하는 계획을 추천한다.

## 부하 테스트는 무엇인가

가게에 가짜 손님을 보내 주문이 많아졌을 때 직원이 얼마나 잘 처리하는지 보는 실험이다.
이 프로젝트에서는 주문 하나가 **“공고 목록 보여줘”라는 HTTP 요청 하나**다.
k6가 사람 대신 이 요청을 정한 속도로 반복해서 보낸다. 실제 회원 1,000명을 만드는 것은 아니다.

## 서로 다른 두 숫자

| 숫자 | 쉬운 뜻 | 이번 계획에서의 역할 |
| --- | --- | --- |
| 공고 1,000건 | 창고에 쌓인 상품 1,000개 | DB에 저장할 합성 데이터 수 |
| 초당 10건, 10 RPS | 1초마다 들어오는 주문 10개 | 서버에 요청을 보내는 속도 |

10 RPS로 5분이면 계산상 `10 × 300 = 3,000`번 요청한다.
실제 보낸 수·끝난 수·실패 수·못 보낸 수는 실행 결과로 따로 확인한다.
10 RPS는 방문자 10명과 같지 않다. 한 사람이 여러 화면을 누르면 여러 요청이 생긴다.

목록 응답에는 공고 12개만 담긴다. 다만 서버는 모집 중인 공고를 고르고 정렬하고 전체 개수도 계산한다.
저장된 공고가 많아졌을 때 이 과정의 비용이 커지는지를 살펴볼 수 있다.
데이터 1,000건과 10 RPS는 실제 성장 예측이나 안전 보장이 아니라 이번 실험 조건안이다.

## 운영과 DEV는 무엇을 맞춰야 하는가

운영과 DEV는 각자의 앱 서버와 DB를 유지한다.
DB를 맞춘다는 것은 DB 엔진·버전·테이블·인덱스·설정과 실험에 필요한 데이터 특성을 확인한다는 뜻이다.
DEV를 운영 DB에 연결하거나 운영 데이터를 그대로 복사해야 한다는 뜻은 아니다.

실험 목적을 먼저 구분한다.

| 목적 | 필요한 조건 | 말할 수 있는 결과 |
| --- | --- | --- |
| 특정 변경의 개선 전후 비교 | 같은 DEV 환경·데이터·요청 조건에서 비교한다. 변경 코드는 개선 한 건을 기준으로 하고, 필요한 스키마 변경은 migration으로 관리한다 | 명시한 DEV 조건에서 해당 변경의 효과를 관측했다 |
| 운영에서 목표 트래픽을 감당하는지 검증 | 테스트할 릴리스와 관련 스키마·설정, 앱/DB 사양·구성, 데이터 특성·주요 경로 등을 운영에 가깝게 재현하고 차이를 평가한다 | 재현한 조건과 확인한 차이의 범위에서 운영 용량을 판단한다 |

같은 연습용 차량으로 부품 교체 전후를 비교할 수는 있다.
그 결과를 사양이 다른 차량의 최고 속도까지 보장하는 근거로 사용하지 않는 것과 같다.
운영과 다른 환경에서도 전후 비교를 할 수 있지만, 병목과 개선 폭이 운영에서도 같다고 단정하지 않는다.
[k6 공식 안내](https://grafana.com/docs/k6/latest/testing-guides/automated-performance-testing/)도 테스트 환경의 규모를 고려한 부하와 동일 조건 비교를 안내한다.

이번 스프린트에서는 **DEV에서 병목 한 건과 개선 효과를 확인하고, 운영과의 차이를 함께 기록하는 범위**를 먼저 잡는다.
관련 테이블·인덱스·MySQL 버전과 주요 설정을 확인하고, 합성 데이터와 실험 조건을 고정한다.
운영의 절대 처리량을 보장하려면 운영을 대표할 수 있는 별도 검증이 필요하다.

현재 확인 기록과 아직 확인할 것을 혼동하지 않는다.

- 앞선 AWS 확인 기록에는 앱과 DB가 환경별로 분리돼 있고, 배포 코드가 다르다고 남아 있다.
- DEV 공개 공고는 2026-10-12 조회 당시 0건이었다. 비어 있는 목록만으로 공고 조회 성능을 평가하지 않는다.
- DEV MySQL은 당시 8.4.11, 앱·DB 사양은 t4g.micro로 확인했다.
- 운영의 앱/DB 사양·MySQL 버전·주요 설정·실제 테이블과 인덱스는 모두 비교한 상태가 아니다.
- 별도 서버·DB를 쓴다는 사실 자체로 사양과 엔진 버전도 다르다고 결론내리지 않는다.

위 내용은 [확인 당시의 기록](./load-testing-sprint2-first-check.md)이다. 이번 설명에서 AWS 상태를 새로 조회한 것은 아니다.
실험 직전 배포·설정·데이터를 다시 확인하고, 운영과의 차이를 남긴다.
전후 고정 조건은 [측정 계획](./load-testing-sprint2-plan.md)의 실행과 전후 비교 순서를 따른다.

## OTR 자료를 참고해도 되는가

참고할 수 있다. 큰 가게의 과거 주문량을 보고 우리 가게가 앞으로 얼마나 처리할지 목표를 세우는 식이다.
다만 사용자 제공 2023년 10월 OTR 자료는 **한 달 합계**다. 시간별 최대량은 없다고 확인했다.
월 페이지뷰 2,790,239건을 31일의 모든 초로 나누면 평균 약 **1.04페이지뷰/초**다.
한 달 합계가 수백만이라고 해서 같은 순간에 수백만 명이 들어온 것은 아니다.

페이지뷰는 화면을 본 횟수이고, RPS는 API에 요청을 보내는 속도라서 직접 같다고 할 수 없다.
“화면 한 번에 핵심 조회 1회, 바쁜 순간은 평균의 10배”처럼 우리가 둔 가정을 적어 연결해야 한다.
OTR의 과거 월 PV 2배를 장기 목표로 가정하면 이 모델에서는 약 20.84 RPS가 나온다.
이를 바탕으로 30 RPS를 성장 목표 후보로 제안할 수 있지만 실제 OTR의 최대 부하를 알아낸 것은 아니다.

우리의 사용자 수가 작아도 k6가 우리 DEV에 가짜 요청을 보낼 수 있고, 공고 데이터도 합성해 준비할 수 있다.
공고 1,000건은 DB 데이터 양을 따로 살펴보는 실험용 숫자다. 월 페이지뷰에서는 공고 보관량을 알 수 없다.
계산과 한계는 [측정 계획의 OTR 성장 시나리오](./load-testing-sprint2-plan.md)에 기록한다.

사용자가 말한 일주일 분석은 우리 서버가 아니라 OTR의 기록을 분석하자는 뜻이다.
현재는 위 월간 캡처만 보유하고 있으므로 일주일 기록을 분석했다고 쓸 수 없다.
일주일 자료를 구할 때까지 실험을 기다릴 필요는 없다. 현재 자료를 참고하고 모르는 부분은 가정이라고 적는다.
공고 옆 누적 조회수를 매일 적어도 하루 증가량만 알 수 있고, 목록을 본 횟수나 순간적으로 몰린 요청 수는 알 수 없다.

“화요일 저녁 8시에 사람들이 온다”까지 맞힐 필요는 없다.
“공고 링크가 공유돼 요청이 짧은 시간에 몰리는 상황에 대비한다”처럼 장면과 실험 조건을 정한다.
앞서 제안한 피크 10배·성장 2배는 통계로 확인한 비율이 아니라 실험용 가정이다.
현재 예상량을 확인하는 조건과 성장 목표·병목 탐색 조건을 구분해서 기록한다.

## 처음에는 왜 적게 보내는가

| 단계 | 조건안 | 확인할 것 |
| --- | --- | --- |
| Smoke, 첫 확인 | 공고 1,000건을 고정하고 1 RPS·30초 | 주소·응답·기록·중단 장치가 맞는가 |
| 목표 용량 측정 | 같은 데이터에서 10 RPS·5분 | 우리가 정한 성능 목표를 달성하는가 |
| 단계별 병목 탐색 | 같은 데이터에서 5 → 10 → 20 → 50 RPS | 요청이 늘 때 어디서 대기가 커지는가 |

1 RPS를 스프린트의 본 실험으로 끝내지는 않는다. 첫 확인을 통과한 뒤 다음 조건으로 넘어간다.
각 단계의 실제 예열·측정 시간을 기록하고, 앞 단계의 오류·서버 상태·회복을 확인한 뒤 요청률을 올린다.
단계별 짧은 탐색과 개선 전후의 5분 측정 결과는 구분한다.
[k6 공식 문서](https://grafana.com/docs/k6/latest/testing-guides/test-types/)도 작은 Smoke부터 시작해 더 큰 부하로 진행하는 흐름을 안내한다.

## 병목과 지표 읽기

병목은 주문이 한곳에 쌓여 기다리는 부분이다. 직원이 계산하느라 바쁠 수도 있고,
직원은 한가한데 창고에서 물건을 가져오는 과정이 느릴 수도 있다.
서버에서는 CPU, DB 쿼리, DB 연결 대기 등을 같은 시간의 응답 지연과 연결해 원인을 판단한다.
“요청이 느리다”는 결과만으로 DB가 원인이라고 단정하지 않는다.

- **응답 시간:** 목록을 요청한 뒤 답을 받는 데 걸린 시간.
- **p95:** 응답 시간 분포에서 약 95%가 이 값 이하인 경계. 평균이 아니다. 목표안 500ms는 0.5초다.
- **오류율:** 요청 중 정상 응답을 받지 못한 비율. 본문이 엉뚱하면 HTTP 200이어도 응답 검사는 실패한다.
- **실제 요청 수와 누락:** 설정한 속도만 믿지 않고 k6가 실제로 보냈는지 확인하는 숫자.
- **서버 자원·SQL:** 느려진 시각에 CPU·메모리·쿼리·대기에 어떤 변화가 있었는지 보여주는 근거.

서버를 죽여야 병목을 찾은 것은 아니다. 정상 동작 중에도 비용이 큰 처리를 찾아 개선할 수 있다.
다만 코드만 보고 가능성을 찾은 것과 실제 측정으로 원인을 확인한 것은 구분한다.

## 이번 실험의 끝

먼저 원래 상태를 같은 조건에서 측정한다. 병목 한 건을 개선한 뒤 서버·데이터·API·요청률·시간을 맞춰 다시 측정한다.
빨라진 수치뿐 아니라 오류·실제 요청 수·기능 회귀 테스트도 함께 확인한다.
이를 통해 **“이 변경 때문에 같은 일을 더 빠르게 처리한다”**는 근거를 남긴다.

실행은 DEV에 한정하지만 운영과 ALB를 공유한다. 낮은 단계부터 관찰하며 진행하고,
응답 오류·timeout·서버 상태 이상이 나타나면 추가 요청을 중단한다.
중단해도 서버에서 이미 처리 중인 요청이나 SQL이 즉시 사라지는 것은 아니다.
안전 조건은 [안전 점검](./load-testing-sprint2-first-check.md)을 따른다.

앞으로 각 단계에서 **무엇을 하는지 → 왜 필요한지 → 어떤 결과인지 → 그 결과가 무엇을 뜻하는지**를 함께 설명하고 기록한다.
