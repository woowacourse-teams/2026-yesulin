## 1. 추천: 공개 오디션 공고 목록부터 측정한다

첫 대상은 `GET /api/v1/public/audition-posts?page=0&size=12&includeClosed=false`다.
상세 `GET /api/v1/public/audition-posts/{postId}`도 따로 측정해 비교한다.

사용자가 예상한 집중 장면은 “공유 링크를 타고 공고 목록·상세를 보러 온다”이고,
팀에 별도 개발·테스트 서버가 있다. 로그인 없이 반복할 수 있고, 조회 결과를 전후 비교하기 쉽다.
목록에는 **카드에 쓰지 않는 본문을 읽는 비용**, **반복 집계 비용**이라는 구체적인 조사 후보가 있다.
현재 코드만으로 실제 병목이라고 확정하지 않는다.

단일 요청을 확인한 뒤 합의한 예상·목표 트래픽을 유지하는 Load 테스트부터 한다.
이어서 링크 공유 직후의 집중을 모델링한 Spike 테스트와,
초당 요청을 `1 → 5 → 10 → 20 → 50건`으로 늘리는 한계 탐색을 구분해 수행한다.
각 단계는 같은 데이터와 서버에서 측정한다. 50건/초는 예상 사용자 수를 뜻하지 않는다.
다음 단계 진행은 오류·응답 지연과 서버 상태를 보고 결정한다.

## 2. “10명 부하 테스트”는 무엇을 뜻할까?

부하 도구는 서버에 주문을 보내는 가짜 손님이다. 손님 수뿐 아니라 **주문하는 속도**가 중요하다.

| 표현 | 뜻 | 판단 |
| --- | --- | --- |
| 5분 동안 10명 방문 | 드문드문 들어오는 사람 10명 | 현재 규모 확인에는 유용하지만 병목 탐색에는 약하다 |
| 가짜 사용자 10명이 계속 요청 | 10명이 응답을 받자마자 다음 요청 | 응답 속도와 쉬는 시간에 따라 요청량이 달라진다 |
| 초당 10건 요청(10 RPS) | 1초마다 요청 10개를 보내도록 설정 | 개선 전후에 같은 압력을 주기 쉽다 |

예를 들어 가짜 사용자 10명이 각각 응답을 0.1초 만에 받고 쉬지 않고 다음 요청을 보내면,
단순 계산으로 약 100건/초가 된다. 같은 10명이어도 5분에 한 번 방문하는 것과는 전혀 다르다.
서버가 느려지면 이 방식의 요청량도 줄어들므로 전후 비교에는 초당 요청량을 고정하는 방식을 권한다.

**방문자 수, 동시에 진행 중인 요청 수, RPS는 서로 다른 숫자다.**

## 3. 대상 선택에 쓴 판단 기준

### 먼저 구분할 병목 종류

“계산하느라 바쁜가, 다른 일을 기다리는가, 같은 일을 처리하려고 줄을 서는가”를 나눠 본다.
DB·외부 API는 I/O에 속하므로 아래 항목은 서로 겹칠 수 있다.
한 API에도 여러 부담이 섞인다. “웹 API는 대부분 기다림에서 막힌다”를 이 프로젝트의 측정 결론으로 쓰지 않는다.

| 종류 | 쉬운 설명 | 프로젝트 후보 | 확인할 관측 |
| --- | --- | --- | --- |
| CPU | 직원이 계산하느라 바쁨 | BCrypt, 일반 심사의 반복 명단 검사, 큰 응답 직렬화 | CPU, 프로파일, 서비스 시간 |
| DB I/O·연결 대기 | DB 답 또는 빈 연결을 기다림 | 공고 목록·집계, 심사 조회 | SQL 시간·횟수, pool 대기, 실행계획 |
| 외부 네트워크·디스크 | 다른 서버 또는 파일을 기다림 | S3 파일 조회·업로드 완료, SMTP, 로그 읽기 | 외부 호출 시간, 디스크 I/O, 요청 중 대기 |
| 메모리·GC | 큰 짐이 쌓여 정리 시간이 늘어남 | 파일 전체 byte 배열, 대량 지원자 응답 | heap, 할당량, GC 시간 |
| 락 경합 | 같은 자원을 처리하려고 줄을 섬 | 조회수 UPDATE, 예매 회차, 일정표 변경 | DB 잠금 대기, POST/PUT 지연, 처리량 |

| 기준 | 쉬운 질문 | 이 프로젝트에서 보는 것 |
| --- | --- | --- |

## 5. 예상 트래픽과 목표 용량을 구분한다

사용자가 제공한 사실은 “오픈채팅 약 60명, 지금은 10명 방문도 많은 편”이다.
“5분에 10명”이라는 시간 구간은 대화에서 제안한 모델이며 방문 로그로 검증된 통계는 아니다.
현재 수치를 수백·수천 명의 실제 유입으로 바꿔 제출하지 않는다.

초기 읽기 모델은 한 사람이 **목록 2번 + 상세 2번 = GET 4번**을 보낸다는 가정이다.
실제 방문 행동으로 확인한 값은 아니므로 첫 실행 전 팀과 합의하고, 이후 로그로 보정한다.

| 구분 | 조건 | 계산·의미 |
| --- | --- | --- |
| 현재 규모 확인 모델 | 10명이 5분 동안 GET 4번씩 | 40 / 300 ≈ 0.13 RPS. 병목 탐색의 주 실험으로 쓰기에는 약하다 |
| 목표 용량 제안 | 채팅방 60명이 보낸 GET 240건이 짧은 30초에 집중된다고 가정 | 240 / 30 = 8 RPS. 여유를 두어 **10 RPS**를 첫 목표로 제안 |
| 안정성 측정 | 위의 10 RPS를 5분간 유지 | 순간 집중보다 더 오래 유지하는 보수적인 조건. 실제 예상 방문 60명과 같다는 뜻은 아니다 |
| 한계 탐색 | 1·5·10·20·50 RPS 단계 측정 | 병목이 드러나는 조건 조사. 실제 예상 트래픽과 별도 기록 |

60명 전원의 짧은 시간 집중과 GET 4번은 **아직 팀이 합의하지 않은 목표 용량 가정**이다.
팀 합의 후에만 제출문의 확정 조건으로 쓴다. 100명의 동시 사용자 같은 다른 숫자로 바꾸지 않는다.
10 RPS가 충분히 빠르더라도 한계 탐색·데이터 증가 실험으로 비용이 커지는 지점을 확인할 수 있다.

### 2023년 OTR 월간 통계를 성장 시나리오에 참고한다

사용자가 제공한 NAVER Analytics 화면에는 사이트 `오티알 (http://otr.co.kr/)`, 기간 `2023-10-01~2023-10-31`이 표시돼 있다.
현재 OTR의 트래픽이나 우리 서비스의 실측 유입이 아니다. 사용자는 시간별 최대 수치 없이 이 월간 합계만 있다고 확인했다.

사용자가 제안한 일주일 분석의 대상은 **우리 운영 서버가 아닌 OTR의 조회 기록**이다.
2026-10-12 확인 결과 현재 보유 자료는 위 캡처뿐이며, OTR의 최근 일주일·시간대별 기록은 확보하지 못했다.
따라서 일주일 관측을 완료했다고 쓰거나 우리 AWS 로그를 OTR 기록으로 대신 사용하지 않는다.
추가 통계 확보를 실험의 필수 선행 조건으로 두지 않고, 현재 자료와 명시한 가정으로 성장 시나리오를 정한다.
나중에 OTR 통계를 확보하면 관측 기간과 시간 단위, 집계 정의를 확인한 뒤 가정을 보정한다.
공개 공고의 누적 조회수만 매일 수집하면 해당 공고의 하루 증가량을 알 수 있지만,
목록 조회량·API 요청량·짧은 순간의 최대 부하는 알 수 없으므로 이를 전체 트래픽으로 사용하지 않는다.
정확한 요일·시각을 예측하는 대신, 링크 공유 등 요청이 집중되는 장면과 요청률·지속 시간을 실험 조건으로 명시한다.

| 화면의 항목 | 표시 값 | 사용 범위 |
| --- | --- | --- |
| 방문자수 | 1,525,232 | 화면의 명칭 그대로 기록. 집계 정의를 확인하지 않았으므로 월간 순사용자(MAU)로 단정하지 않는다 |
| 방문횟수 | 1,707,808 | 월간 방문 집계의 참고 값. 동시 접속 수가 아니다 |
| 페이지뷰 | 2,790,239 | 월간 페이지 조회량을 성장 시나리오의 참고 값으로 사용한다 |

`2,790,239 / 31 ≈ 90,007.71 PV/일`, `2,790,239 / (31 × 24 × 60 × 60) ≈ 1.0418 PV/초`다.
이 평균은 하루 24시간에 고르게 나눈 계산값이며 실제 가장 바쁜 순간을 보여주지 않는다.
페이지뷰와 백엔드 API 요청은 같은 단위가 아니다. 한 페이지의 API 호출 수·캐시·기능 구성이 다르면
같은 페이지뷰에서도 백엔드 작업량이 달라진다. 봇·반복 방문의 포함 여부도 이 화면만으로 판단하지 않는다.

성장 시나리오는 다음처럼 **외부 참고 수치·우리 목표·미확인 가정**을 각각 명시한다.

| 시나리오 후보 | 계산 가정 | 계산상 핵심 조회 요청률 |
| --- | --- | --- |
| 과거 OTR 월 PV와 같은 규모 | 전체 PV를 공개 조회 페이지로 간주, 페이지당 핵심 GET 1회, 피크를 월 평균의 10배로 가정 | `1.0418 × 1 × 10 ≈ 10.42 RPS` |
| 과거 OTR 월 PV의 2배라는 장기 목표 | 위 가정을 유지하고 월 PV 목표만 2배로 가정 | `1.0418 × 2 × 1 × 10 ≈ 20.84 RPS` |

피크 10배·페이지당 핵심 GET 1회·공개 조회 페이지 비율 100%·2배 성장 모두 실측값이 아니다.
특히 OTR의 전체 페이지에는 공고 조회 이외의 기능도 포함될 수 있다. 모든 PV를 공개 조회로 놓는 것은
단일 조회 API 용량을 진단하기 위한 단순화이며 실제 방문 흐름 재현이라고 표현하지 않는다.

기존 10 RPS는 초기 기준선과 목표안으로 유지한다. 위 2배 성장 모델을 추가로 검증한다면 계산값보다 높은
**30 RPS를 성장 용량 목표 후보**로 둘 수 있다. 10 → 20 → 30 RPS로 앞 단계의 정상 응답·자원·회복을 확인한 뒤
진행하고, 50 RPS는 별도의 한계 탐색 후보로 둔다. 30 RPS는 아직 팀 합의·안전 검증이 끝난 실행 조건이 아니다.
본 비교는 선택한 요청률에서 예열·5분 측정·반복 횟수·데이터·서버 조건을 전후 동일하게 고정한다.

합성 공고 1,000건은 DB 데이터 증가를 확인하는 별도의 실험 조건이다. 위 월 PV에서 공고 보관량을 계산할 수 없으며
이를 OTR의 실제 공고 수나 우리 서비스의 확정 성장 예측이라고 쓰지 않는다.
작은 현재 서비스에서도 우리 DEV의 같은 API에 합성 데이터와 가짜 요청을 보내 이 조건을 실험할 수 있다.

이번 스프린트에서 확인하는 것은 **명시한 조건에서 공개 조회 API가 어떻게 동작하고 병목 한 건을 어떻게 개선했는지**다.
이 한 API의 결과로 OTR 전체 서비스의 최대 처리량·모든 기능·장애 대응보다 우수하다고 인증하지 않는다.
API 한 개부터 시작하고 실제 흐름으로 범위를 넓히는 접근은 [k6 API 부하 테스트 안내](https://grafana.com/docs/k6/latest/testing-guides/api-load-testing/)를 참고한다.

제출문에 사용할 근거 문장 초안은 다음과 같다. 실제 수치와 개선 결과는 실행 후 별도로 채운다.

> 현재 서비스의 유입 자료가 적어 사용자 제공 2023년 10월 OTR 월간 페이지뷰 2,790,239건을 성장 시나리오의 참고 자료로 사용했다.
> 월 평균은 약 1.04 PV/초이며, 시간별 최대량과 페이지당 API 호출 수는 확인하지 못했다.
> 따라서 성장 배수·피크 배수·핵심 GET 호출 수는 실측과 구분한 가정으로 명시하고, 공개 조회 API의 목표 조건과 단계별 진단 조건을 정한다.
> 현재 DEV 성능 수치·병목·개선 전후 비교는 아직 미측정이다.

## 6. 첫 시나리오와 목표 수치

### 목적에 맞는 테스트 유형

| 유형 | 답하려는 질문 | 이번 계획에서의 쓰임 |
| --- | --- | --- |
| Smoke | 요청 스크립트가 올바르게 동작하는가? | API별 1 RPS·30초 확인 |
| Load | 합의한 예상·목표 트래픽에서 목표 속도를 유지하는가? | 현재 규모 모델과 팀이 합의한 목표 10 RPS를 각각 측정. 목표 조건은 5분 유지 |
| Spike | 공유 직후 갑자기 몰렸다가 줄어도 버티고 회복하는가? | 공고 목록·상세·조회수 기록 흐름의 순간 집중 |
| Stress·한계 탐색 | 예상량을 넘으면 어디서 문제가 드러나는가? | 1·5·10·20·50 RPS 단계별 측정 |
| Soak | 오래 유지할 때 자원이 계속 쌓이는가? | 누수 의심이 생길 때 별도 장시간 실험 |

Load만으로 병목이 안 드러날 수 있고 Stress만으로 실제 예상량을 검증했다고 할 수도 없다.
이번 미션에서는 예상 트래픽의 Load 결과와 병목을 관측한 실험 조건을 모두 남긴다.
단계적으로 한계를 찾는 실험은 k6 문서의 breakpoint 유형과도 목적이 겹친다.
[k6 테스트 유형 공식 문서](https://grafana.com/docs/k6/latest/testing-guides/test-types/)를 참고한다.

### 2026-10-12 실행 단계와 부하 선정 이유

팀에서 첫 조건의 부하가 약하다는 피드백을 받았다. 1 RPS·30초는 요청과 중단·기록 장치를 확인하는 Smoke다.
이 단계만 끝내고 병목 탐색이나 스프린트 완료로 제출하지 않는다.

첫 DEV 실행을 위해 합성 40건 SQL을 로컬에 생성했지만 DB에는 적용하지 않았다.
40건은 모집 중 공고 24건을 확보하는 최소 점검용 구성이다. 본 실험은 **합성 공고 1,000건**으로 데이터를 고정하고
Smoke도 같은 데이터에서 먼저 실행하는 것을 추천한다. 태그·파일 없는 본문 2,048자 조건의 범위를 함께 기록한다.

| 단계 | 조건안 | 판단 목적 |
| --- | --- | --- |
| Smoke | 합성 1,000건, API별 1 RPS·30초 | 대상·계약·데이터·결과 저장·중단 장치 확인. 성능 목표 달성이나 병목 발견의 근거로 단독 사용하지 않는다 |
| 목표 용량 측정 | 같은 데이터에서 API별 10 RPS·5분, 별도 2분 예열 | 측정 구간 약 3,000건에서 p95 500ms·p99 1,000ms·오류율 1% 미만·누락 0을 확인. 10 RPS는 실제 유입 통계가 아닌 목표안이다 |
| 단계별 진단 | 같은 데이터에서 5 → 10 → 20 → 50 RPS | 처음에는 각 단계 60초의 짧은 탐색으로 지연·오류·자원 변화를 본다. 안전 조건 충족·회복 확인 후 다음 단계를 정한다 |
| 원인·전후 비교 | 목표 조건과 병목 근거가 있는 안전한 조건을 각각 고정 | 진단용 짧은 실행을 본 비교에 섞지 않고 2분 예열·5분 측정을 같은 조건으로 전후 각 3회 수행한다 |
| 데이터 증가 진단 | 앞 단계에서 여유가 있으면 합성 10,000건으로 별도 데이터 세트를 구성 | 우선 안전하게 확인한 같은 요청률에서 비교한다. 데이터와 요청률을 동시에 바꾸어 증가 원인을 혼동하지 않는다 |

짧은 단계 진단에서 시간을 바꾸면 실제 예열·측정 시간도 원본에 남긴다.
1,000건과 10,000건의 동일 seed를 겹쳐 적용하지 않는다. 현재 생성기는 같은 `(source, external_id)`를 만들므로
1,000건이 있는 DB에 10,000건 전체 SQL을 그대로 실행하면 고유 제약으로 실패한다.
확장 시에는 기존 데이터를 보존하는 추가분 또는 별도 데이터 세트를 먼저 준비·검증한다.

병목 후보는 요청률 상승에 따른 p95/p99·처리량 변화와 같은 시각의 SQL 횟수/시간·CPU·대기를 연결해 고른다.
성능 목표를 넘거나 서버가 죽어야만 개선할 수 있는 것은 아니다. 목표를 통과해도 특정 처리의 비용이 커지는 증거와
그 비용을 줄인 동일 조건의 전후 수치가 있으면 개선 근거로 기록할 수 있다.
50 RPS 상한을 임의로 풀거나 바로 100·1,000 RPS로 올리지 않는다. 공유 ALB·운영 상태와 실험 서버의 여유를 먼저 확인한다.

테스트 유형의 구분은 [k6 공식 문서](https://grafana.com/docs/k6/latest/testing-guides/test-types/)를 따른다.
위의 요청률·데이터 건수·측정 시간은 이 프로젝트의 조건안이지 공식 문서가 보장하는 안전 수치가 아니다.

### API별 측정

도구는 **k6**를 추천한다. 작은 JavaScript로 API 요청과 합격 기준을 표현할 수 있다.
`constant-arrival-rate`로 요청 시작 속도를 고정한다.
이 설정의 rate는 **반복(iteration) 수**이므로, API 한 건 비교에서는 **반복 1회 = HTTP 요청 1건**으로 만든다.
한 반복에 GET 4개를 넣은 방문 모델의 rate를 그대로 RPS라고 부르면 안 된다.
설정 동작은 [k6 공식 문서](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/constant-arrival-rate/)에서 확인했다.

| 실험 | 요청 조건 | 목적 |
| --- | --- | --- |
| 목록 단독, 첫 비교 대상 | `page=0&size=12&includeClosed=false` 고정 | 가장 자주 열 첫 목록의 비용을 추적 |
| 상세 단독 | 미리 정한 공개 공고 ID 목록을 같은 순서로 순환 | 본문이 필요한 조회와 비교 |
| 목록 추가 진단 | `includeClosed=true`, 실제 존재하는 뒤쪽 페이지 | 모집 중 필터와 페이지 위치의 영향 분리 |
| 방문 흐름 후속 확인 | 목록 2회, 상세 2회, 공고별 탭 세션당 views POST 1회 | 실제 흐름에서 읽기와 쓰기가 함께 있을 때 재확인 |

첫 실험은 백엔드 JSON API를 측정한다. 화면 렌더링, 이미지 다운로드와 프론트 서버 비용은 포함하지 않는다.
GET 상세는 조회수를 올리지 않는다. 화면은 별도 `POST /{postId}/views`를 보내므로,
읽기 실험에 이를 포함하지 않았음을 기록하고 후속 실험에서는 POST 지표를 분리한다.
같은 공고를 같은 탭에서 다시 열어도 정상적으로 기록된 views POST는 다시 보내지 않는다.
단독 API 실험의 10 RPS는 해당 API만 초당 10건이라는 뜻이다.
방문 흐름의 목표 합계 GET 10 RPS와 구분해 결과에 표시한다.
views POST에는 CSRF cookie와 `X-CSRF-Token` 준비가 필요하고 204 성공을 검사한다.
GET의 200과 POST의 204를 따로 확인한다. 빠른 403 응답을 정상 처리로 세면 안 된다.

### 링크 공유 Spike와 조회수 경합 진단

Spike의 첫 목표안은 “채팅방 60명이 30초에 들어온다”다. 기존 방문 모델에 맞춰 새 방문자는
목록 2회·서로 다른 공고 상세 2회·공고별 views POST 1회씩 요청한다.
반복 1회는 새 탭의 방문 1명으로 모델링하며 HTTP 요청은 최대 6개다.
예열 후 낮은 방문률에서 **분당 120명 시작률로 급증해 30초 유지**하고 낮은 방문률로 돌아온다.
이는 새 방문 시작 총 60명을 계획하는 것이며 항상 60개의 요청이 동시에 진행 중이라는 뜻은 아니다.
실제 요청 시작·완료·실패 건수와 지연·회복 시간을 기록하고, 낮은 구간의 방문률도 전후 고정한다.

별도 원인 진단에서는 같은 총 요청률·GET/POST 비율·본문·파일 구성으로
**같은 공고 집중**과 **여러 공고 분산**을 비교한다.
같은 탭이 반복 POST를 보내는 대신 새 방문을 모델링하거나 POST 단독 진단임을 명시한다.
분산했을 때 빨라졌다는 사실만으로 락 병목을 확정하지 않는다.
캐시 효과도 섞일 수 있으므로 조회수 POST 지연과 DB 잠금 대기를 함께 확인한다.

공개된 테스트 공고를 사용하고 자동 redirect는 끈다(`redirects: 0`).
숨김 공고는 302로 외부 OTR 주소를 반환하므로 따라가면 다른 서비스를 측정하게 된다.
상세 GET 자체는 외부에서 본문·사진을 받아오는 요청이 아니라 저장된 DB 데이터와 URL을 반환한다.

아래 수치는 **10 RPS에서의 팀 합의 전 목표안**이다. 기존 서비스가 이미 이 수치를 달성했다는 뜻은 아니다.

| 지표 | 목표안 | 쉬운 뜻 |
| --- | --- | --- |
| API별 p95 응답 시간 | 500ms 미만 | 요청 100개 중 약 95개가 0.5초 안에 끝나는 수준 |
| API별 p99 응답 시간 | 1,000ms 미만 | 느린 쪽 요청도 살펴본다 |
| HTTP 실패율 | 1% 미만 | HTTP 오류·통신 실패가 전체 요청의 1% 미만 |
| 정상 응답 확인 | 예상 200과 핵심 응답 필드 검사 통과 100% | 빨라도 엉뚱한 답이면 실패다 |
| `dropped_iterations` | 0 | 계획한 요청을 부하 도구가 못 보낸 경우가 없어야 한다 |
| 실제 요청량 | 목표와 실제 시작·완료·실패 건수를 함께 기록 | 설정에 10 RPS를 적은 것만으로 부하 달성을 주장하지 않는다 |

p95/p99는 평균과 다르다. 평균만 보면 일부 사람이 오래 기다리는 일을 놓칠 수 있다.
표본이 적은 현재 규모 실험의 백분위는 불안정하므로 전체 요청 건수도 함께 남긴다.
k6의 실패율과 응답 시간 기준은 [thresholds 공식 문서](https://grafana.com/docs/k6/latest/using-k6/thresholds/)를 참고한다.
요청 누락은 가짜 사용자 수 부족 또는 서버 지연 때문일 수 있으므로 부하 발생기 CPU·메모리와 설정도 확인한다.
[dropped iterations 공식 문서](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/dropped-iterations/)를 참고한다.

## 7. 사람 수만큼 중요한 테스트 데이터

빈 DB에서 빠른 조회는 공고가 쌓였을 때의 성능을 설명하지 못한다.
팀 테스트 DB의 현재 공고 수와 상태·마감 분포, 본문 크기, 사진·첨부 수를 먼저 집계한다.

| 데이터 세트 | 용도 |
| --- | --- |
| 현재 테스트 DB의 고정 스냅샷 | 현재 규모에서의 기준 측정 |
| 합성 공고 1,000건 | 첫 데이터 증가 실험 제안 |
| 합성 공고 10,000건 | 1,000건에서 차이가 안 보일 때의 추가 진단 |

1,000·10,000건은 실제 사용자·공고 수나 확정 성장 예측이 아니다. 데이터 증가 민감도를 보는 실험용 숫자다.
합성 데이터는 전용 테스트 DB에 준비하고 실제 외부 공고 가져오기 API를 반복 호출해서 만들지 않는다.
공개·숨김, 마감 전·후·상시, 작성 시각 동일·null, 사진 없음·있음, 첨부 없음·복수를 포함한다.
구성 비율과 본문 길이 분포는 한 번 정해 전후 동일하게 보존한다.
긴 본문 가설 진단은 **공고 수·다른 조건을 고정하고 본문 크기만 변경하는 별도 실험**으로 한다.
최대 허용 길이 500,000자를 일반 공고의 평균 길이라고 가정하지 않는다.

현재 로컬 seed는 제작사 계정 하나만 생성한다. 부하용 공고 데이터는 별도 준비가 필요하다.
로컬 seed에는 과거 데모 데이터를 지우는 부분도 있으므로 팀 테스트 DB에 그대로 실행하지 않는다.

## 8. 실행과 전후 비교 순서

이번 비교는 명시한 DEV 조건에서의 개선 효과를 확인한다. 운영의 절대 처리량을 보장하는 실험과 구분한다.
앱과 DB는 환경별로 분리해 유지하고, 관련 DB 버전·스키마·인덱스·설정과 데이터 특성을 확인한다.
운영과의 모든 차이가 비교된 상태는 아니므로 차이·미확인 항목을 실행 기록에 남긴다.
목적별 환경 조건은 [처음 이해하기의 운영/DEV 설명](./load-testing-sprint2-beginner-guide.md)을 참고한다.

실행 전 [안전 점검](./load-testing-sprint2-first-check.md)의 조건을 충족한다.
2026-10-12 확인 결과 DEV와 PROD는 요청 입구(ALB)를 공유한다. DEV 이름만으로 운영 영향이 없다고 가정하지 않는다.
공유 자원·관측·중단·복구 조건이 준비되기 전에는 데이터 추가나 원격 부하를 실행하지 않는다.
아래 요청률 단계는 실험 후보이며 안전이 검증된 수치가 아니다.

1. 테스트 서버 주소, 백엔드 배포 SHA, 독립 테스트 DB 여부와 서버·DB 사양을 확인한다.
2. 단일 요청으로 응답과 테스트 공고 데이터를 확인한다. 목록·상세 JSON을 비교 기준으로 보관한다.
3. 각 API를 1 RPS·30초로 시험해 요청이 올바른 대상에 도착하는지 확인한다.
4. 각 측정 전 동일 조건으로 2분 예열한다. 예열 결과는 본 측정에서 제외한다.
5. 목록·상세 단독의 합의한 Load 조건을 측정하고, Spike와 1·5·10·20·50 RPS 한계 탐색을 별도 수행한다.
6. 한계 탐색은 단계별 5분 측정한다. 오류·timeout, 합의한 중단 기준 또는 운영 이상이 나타나면 부하를 중단하고 원인을 조사한다.
   관측이 끊겨도 중단한다. 현재 스크립트는 단일 응답 2초 이상을 중단하지만 CPU·메모리를 자동 감시하지 않는다.
7. 병목 후보 한 건을 정하고 **개선 전** 선택 조건에서 3회 반복 측정한다. 원시 결과와 로그를 남긴다.
8. 동작 회귀 테스트를 먼저 보강하고 개선 한 건을 적용한다. 여러 변경을 한꺼번에 섞지 않는다.
9. **개선 후** 같은 조건에서 3회 반복한다. 목표 10 RPS와 병목이 관측된 조건 모두 비교한다.
10. CI 결과·migration 적용 결과와 함께 제출문을 작성한다.

전후 고정 항목: 서버·DB 사양과 버전, 인스턴스 수, JVM·메모리·connection pool 설정,
데이터 스냅샷, API·파라미터·ID 순서, 본문·파일 구성, 요청률·시간·예열, 부하 발생기와 네트워크 경로,
로그 수준과 관측 설정. 스케줄 작업·다른 팀의 테스트·배포가 끼었으면 기록하고 비교에서 분리한다.
마감이 날짜에 따라 바뀌므로 실험 사이 모집 중 대상이 변하지 않도록 테스트 날짜와 마감도 관리한다.

세 번의 개별 결과를 남기고 대표값으로 중앙값을 비교한다. 서로 다른 실행의 p95를 평균내서 하나의 p95로 쓰지 않는다.
개선율은 `(개선 전 - 개선 후) / 개선 전 × 100`으로 계산하고, 오류율과 실제 처리량 악화 여부도 같이 확인한다.

50 RPS에서도 문제를 못 찾았다면 “병목 발견”으로 제출하지 않는다.
측정 증거를 보고 데이터 실험 또는 심사 후보로 옮긴다. 숫자를 끝없이 올리는 것이 완료 조건은 아니다.

## 9. 원인을 찾기 위해 확보할 관측

현재 `HTTP_REQUEST` 로그에 endpoint·status·elapsedMs·request ID가 있다.
1초 이상 요청은 WARN, 500ms 이상 application service는 `SLOW_SERVICE` WARN이다.
빠른 서비스는 DEBUG이므로 기본 로그에서 모든 서비스 시간이 보이는 것은 아니다.

| 관측 | 목적 | 현재 준비 상태 |
| --- | --- | --- |
| k6 API별 지연·오류율·처리량 | 사용자가 느끼는 API 지연 확인 | 스크립트·로컬 실행 검증 완료, DEV 지속 부하 미실행 |
| 요청·느린 서비스 로그 | 같은 시간에 어느 경로가 느렸는지 확인 | 코드 구현 있음, 팀 서버 로그 접근 확인 필요 |
| SQL 횟수·시간, 실행계획 | 본문 과조회·COUNT·필터 가설 확인 | 테스트 서버 MySQL에서 별도 확보 필요 |
| 애플리케이션·DB CPU와 메모리 | CPU 계산 또는 DB 자원 한계 확인 | 팀 서버의 기존 관측 수단 확인 필요 |
| connection pool 사용·대기 | DB 연결 기다림과 쿼리 실행 구분 | 현재 저장소에서 수집 설정 미발견 |

Actuator는 현재 health만 웹으로 노출한다. DB 상태 검사 스크립트의 `SELECT 1`은 병목 관측을 대신하지 못한다.
CloudWatch 로그 수집 여부도 저장소 코드만으로 확인되지 않는다.
새 관측 설정이 필요하면 개선 전부터 적용하고, 상세 SQL 진단과 성능 본 측정의 로그 수준을 구분한다.

### 넓은 후보 표를 읽을 때 주의할 코드 차이

- 업로드 요청은 서명 URL 생성·DB 저장이다. 파일을 서버가 S3에 업로드하는 경로로 해석하지 않는다.
  업로드 완료는 파일 행을 잠근 뒤 동기 S3 HEAD 요청을 보내므로 대기·락이 겹치는 후보다
  ([FileService](../../src/main/java/art/yesulin/application/file/FileService.java) 38~45, 59~67행).
- 파일 내용 조회는 S3 `getObjectAsBytes`로 전체 파일을 읽는다. 메모리 가설은 타당하지만 실제 동시 요청·크기로 확인해야 한다
  ([S3ObjectStorage](../../src/main/java/art/yesulin/infrastructure/storage/s3/S3ObjectStorage.java) 103~110행).
- 일정표 배우 GET은 일반 읽기이고 시간 변경 PUT이 일정표 행을 잠근다. 두 API를 모두 락 경합으로 묶지 않는다
  ([ActorTimetableService](../../src/main/java/art/yesulin/application/timetable/ActorTimetableService.java) 39~51, 78행).
- 문자 POST는 검증·발송 대기 기록 후 202를 응답한다. 외부 전송은 worker가 수행하므로 접수 응답 시간과 큐·발송 시간을 따로 본다
  ([NoticeWorker](../../src/main/java/art/yesulin/application/auditionnotice/NoticeWorker.java) 59행).
- SMTP는 동기지만 가입 메일은 AFTER_COMMIT 이벤트다. 요청 완료의 기다림과 가입 DB 트랜잭션의 보유 시간을 구분한다
  ([ProducerSignUpEventHandler](../../src/main/java/art/yesulin/presentation/event/auth/ProducerSignUpEventHandler.java) 16~18행).
- 일반 지원 제출에는 멱등 키가 있고, OTR 제출에는 같은 키 계약이 없다. 공고 행의 명시적 잠금도 OTR 경로에 해당한다.
  경로별로 [API 계약](../api.md)을 확인한다.
- `/api/v1/health`는 DB `SELECT 1`을 한다. 실제 ALB·배포 검사는 Actuator readiness를 사용한다.
  건강 상태는 부하 중 보조 관측이고 사용자 흐름의 대표 성능 측정은 아니다
  ([HealthApiController](../../src/main/java/art/yesulin/presentation/api/HealthApiController.java) 12~34행).

## 10. 회귀 테스트·CI·스키마 관리

기존 조회 동작 검증은 별도 `AuditionPostServiceTest`가 아니라
[AuditionPostImportServiceTest](../../src/test/java/art/yesulin/application/auditionpost/AuditionPostImportServiceTest.java)에 있다.

| 기존 근거 | 검증 내용 |
| --- | --- |
| `listsOpenPostsByDefaultAndCountsBoth` | 기본 모집 중 목록, open/all count, totalElements·totalPages |
| `hiddenPostLeavesPublicListAndDetailPointsToOriginal` | 숨김 목록 제외와 상세 원문 주소 |
| `missingPostIsNotFound`, `rejectsOutOfRangePageSize` | 없는 공고, 음수 페이지·size 초과 거절 |
| [AuditionPostTest](../../src/test/java/art/yesulin/domain/auditionpost/AuditionPostTest.java)의 `keepsDeadlineTextAndParsesOnlyIsoDate` | 마감 당일까지 모집 중, 다음날 마감, 상시 공고 |

조회 개선 시 application 테스트로 **정렬(작성 시각·동일 시각 ID·null), 여러 페이지 중복·누락,
마지막·빈 페이지와 집계, 첫 사진 thumbnail·첨부 수**를 보강한다.
최적화 전에도 통과하는 동작 기준을 세우고 최적화 후 같은 결과를 확인한다.
성능이 빨라야만 통과하는 시간 단정 테스트를 일반 CI에 추가하는 대신, 동작 회귀와 성능 측정을 구분한다.
새 테스트는 현재 저장소 지침에 따라 domain/application에 작성한다.

[CI](../../../.github/workflows/ci.yml)는 `./gradlew build --no-daemon`으로 테스트와 Checkstyle을 실행한다.
위 application 테스트는 H2·`create-drop`·Flyway disabled다. MySQL 인덱스 효과와 migration 적용을 대신 검증하지 않는다.
DB 변경이 있으면 별도 MySQL 테스트 DB에서 Flyway 적용과 변경 쿼리를 확인하고 결과를 남긴다.
이 문서 작성 중 로컬 테스트·최신 CI 결과는 확인하지 않았다.

스키마 도구는 **Flyway**다. SQL은 `backend/src/main/resources/db/migration/`에서 관리한다.
인덱스를 바꾸면 새 버전 migration을 추가하며 이미 적용된 파일을 수정하지 않는다.
projection·중복 집계 제거만으로 해결되어 DB 변경이 없으면 제출문에 “DB 변경 없음”을 적는다.
성능 개선이라고 반드시 스키마를 바꿀 필요는 없다.

[application.yml](../../src/main/resources/application.yml) 13~19행의 기본 설정은
`spring.jpa.hibernate.ddl-auto=validate`, `spring.flyway.enabled=true`다.
별도 `application-prod.yml`은 없고 배포 env를 사용한다.
확인한 config의 prod env에는 이 값을 덮어쓰는 설정이 없었지만 **현재 운영 프로세스의 최종 적용값은 미확인**이다.
제출 전 배포 설정·프로세스 적용값으로 prod의 validate를 확인한다.

## 12. 실제 실행 전에 답할 쉬운 질문

- 가짜 손님을 보낼 테스트 서버 주소는 어디인가?
- 그 서버의 DB도 실험 전용인가, 다른 사람이 쓰는 데이터를 함께 사용하는가?
- 서버가 느려지면 확인할 그래프나 로그를 누가 볼 수 있는가?
- “채팅방 링크가 잠깐 몰려도 초당 10건을 처리한다”를 팀의 첫 목표로 삼아도 되는가?

문서상 DEV 직접 API는 `https://dev-api.yesulin.art`이고 단일 요청은 응답했다.
실험 대상의 테스트 전용 DB 여부·데이터 준비·서버 관측 접근은 팀 확인이 필요하다.
합성 SQL 생성기와 k6 스크립트는 준비했으며 DB 적용과 지속 부하는 아직 실행하지 않았다.

## 조사 시 저장소 상태

- main·dev를 fetch한 뒤 dev를 fast-forward pull했다. 조사 시 HEAD와 origin/dev 차이는 0이었다.
- 이 시점 main과 dev의 백엔드 파일 내용은 같았고 dev에 최신 프론트 변경이 있었다.
- 기존 개인 문서와 config 로컬 상태를 보존했다. config checkout은 `dddd5df`, 상위 저장소 기대 pin은 `a01e9cc`다.
  팀 테스트 서버의 코드·config 버전은 별도로 기록해야 한다.
