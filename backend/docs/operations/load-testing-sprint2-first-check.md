## 2026-10-12 안전 점검

**현재 판단: 상태 조회는 진행했고, 데이터 추가·지속 부하·한계 탐색은 실행하지 않는다.**
DEV라는 이름과 AWS 로그인 성공만으로 실험의 영향 범위가 보장되지는 않는다.

이 문구는 미실행 상태 기록이다. 사용자는 이후 실제 DEV 실험을 요청했고, 안전 조건·데이터·관측을 준비하는 중이다.
2026-10-12 팀 피드백을 반영해 1 RPS·30초를 Smoke로 명확히 구분하고, 본 실험은 합성 1,000건과
10 RPS·5분 목표 측정 및 5·10·20·50 RPS 단계별 진단으로 계획한다. 조건과 근거는 [선정 문서](./load-testing-sprint2-plan.md)에 있다.
최소 점검용 합성 40건 SQL도 로컬에 생성했지만 DB에 적용하지 않았다. 본 실험 데이터로는 1,000건을 우선 추천한다.

이번 점검은 기존 권한으로 접속해 상태·설정 일부·공고 개수·백업 작업 결과를 읽었다.
SSM 접속 이력과 조회 요청 로그는 생길 수 있다. 서버 재시작·배포·AWS 자원 생성/삭제·보안 설정 변경,
공고 INSERT/UPDATE/DELETE는 수행하지 않았다. 합성 SQL은 로컬 파일만 만들었다.

### 스크립트의 보호 범위

- 알려진 운영 도메인 세 개를 거절하고, 원격 origin을 명시하게 한다. 다른 운영 주소나 잘못 연결된 DB까지 자동 판별하지 않는다.
- 공고 GET만 보내며 redirect를 따라가지 않는다. 응답 오류·계약 불일치·데이터 부족이면 중단한다.
- 이번 점검에서 요청 timeout을 10초에서 **2초**로 줄이고, 완료된 응답도 **2,000ms 이상이면 추가 부하를 중단**하게 했다. 사전 확인·예열·측정 모두 적용한다. 예열 뒤 종료 대기도 2초다.
- 2,000ms는 이번 첫 실험의 보수적인 중단 기준이지 보편적인 안전 수치가 아니다. 성능 목표 p95 500ms와 구분한다.
- 중단은 추가 요청 발생을 멈춘다는 뜻이다. 이미 서버에서 처리 중인 요청이나 SQL이 즉시 취소되는 것은 아니다.
- CPU·메모리·DB 연결·운영 상태·비용을 관찰하는 자동 중단 기능은 없다. 현재 성능 목표 threshold도 종료 시 판정하며 CPU 포화를 막는 장치로 볼 수 없다.
- `RPS` 상한 50은 입력 제한이다. **50 RPS까지 안전하다는 검증 결과가 아니다.**

### 실행 전에 남은 조건

1. 확인한 DEV 배포 SHA를 실험 기준으로 기록하고 해당 버전의 동작·스키마와 테스트 스크립트를 맞춘다.
   PROD 앱의 DB host·schema가 DEV와 다른 것은 확인했다. 실행 직전 배포가 바뀌었는지도 확인한다.
2. 담당자와 실험 시간을 정하고 앱·DB CPU/메모리, readiness, DB 연결 대기 및 공유 ALB의 운영 상태를 관찰할 수 있게 한다.
   관찰을 못 하게 되면 부하를 시작하거나 올리지 않는다.
3. 데이터 추가 전 사용 가능한 백업을 확인하고, 합성 데이터의 식별자·삽입 건수·정리 방법을 준비한다.
   백업 복원으로 팀의 다른 변경까지 덮어쓰지 않도록 복구 범위를 정한다. 현재 SQL의 실제 MySQL 적용·정리 절차는 미검증이다.
4. 부하 없는 상태를 먼저 기록한다. 첫 실행은 목록 **초당 1건·30초**, 관찰자가 보는 동안 한 번만 실행한다.
5. 첫 실험의 중단 기준안은 다음과 같다. 담당자와 실행 전에 확정하고 기록한다.
   - 응답 오류·계약 실패 또는 단일 응답 2초 이상: 스크립트 중단.
   - 앱/DB CPU 80% 이상이 30초 지속, 메모리 사용률 85% 이상, readiness 실패, 운영 오류 증가: 관찰자가 즉시 부하 중단.
   - 실행 전부터 위 상태이거나 관측이 끊김: 시작하지 않는다. 지표 정의·관측 간격을 함께 기록한다.
6. 중단 뒤 상태가 실험 전 수준으로 돌아오는지 확인한다. 회복하지 않으면 담당자에게 상황을 전달하며,
   서버 재시작이나 AWS 설정 변경을 자동으로 하지 않는다. 5·10·20·50 RPS는 낮은 단계의 결과를 보고 별도로 판단한다.

추가 과금 가능성은 [AWS Unlimited mode 안내](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/burstable-performance-instances-unlimited-mode.html)를 따른다.
실제 CPU credit 잔액·추가 청구 여부·계정 예산은 아직 확인하지 않았다.

## 준비 상태

- k6 2.3.0 공식 macOS arm64 바이너리를 내려받고 GitHub 배포 자산의 SHA-256과 일치하는지 확인했다.
- 로컬 도구 위치: `/private/tmp/yesulin-load-tools/k6-v2.3.0-macos-arm64/k6`.
- GET 전용 시나리오의 실행 방법은 [스크립트 README](../../../scripts/load-test/README.md)를 따른다.
- AWS CLI는 접속 문제로 사용하지 못했지만 2026-10-12 SSM 웹 터미널로 백엔드·DB에 접속해 공고 상태를 조회했다. 부하 중 CPU·SQL 관측은 아직 준비 단계다.
- 합성 공고 1,000건의 SQL 파일을 생성했다. 공개 800건·숨김 200건이며 모집 중은 600건, 본문은 각 2,048자다. DB에는 아직 적용하지 않았다.
- 지속 부하 실행·병목 확정·개선 전후 비교와 CI 회귀 검증은 아직 하지 않았다.

중단 시 여러 요청이 이미 진행 중일 수 있음을 확인했다. 위 요청 수에는 실패 요청도 포함하며
DEV 성능 수치나 CI 회귀 검증 결과로 쓰지 않는다. 로컬 가짜 서버는 검증 종료 후 정지했다.

상세의 예정 요청은 3건이지만 k6 종료 시각 경계에서 1건이 추가 시작됐다. 스크립트는 예정 수~예정 수+1을
허용하고 실제 요청 수를 보존한다. 요청 누락은 허용하지 않는다.
예열이 있는 경우 k6 counter의 `rate`는 전체 실행 시간을 분모로 사용하므로 본 측정 RPS로 읽지 않는다.
원시 측정 표본·설정 시간·실제 요청 수를 함께 확인한다.

검증 결과와 합성 SQL은 `scripts/load-test/results/`에 보관하고 Git에서 제외했다.
SQL 파일 `posts-1000.sql`의 SHA-256은 `6d8f49a23d3b7a240f54f42cd07cb05ec25ff5eb4522d0a7c3481720bc9dae4c`다.
실제 MySQL 적용은 아직 검증하지 않았고, 테스트 전용 DB 확인 뒤 담당자가 적용한다.

## 팀원에게 전달할 요청

아래 내용을 그대로 전달할 수 있다. 이 문서 작성 과정에서 팀원에게 메시지를 보내지는 않았다.

> 스프린트 2에서 DEV 공고 목록·상세의 부하 테스트를 하려고 해.
> 지금 DEV 공개 목록은 0건이라 데이터 준비부터 필요해.
>
> 1. `dev-api.yesulin.art`는 DEV EC2와 `yesulin_staging`으로 연결되는 걸 확인했어. PROD가 DEV DB를 함께 쓰지 않는지 확인해줘. ALB는 공유하므로 운영 상태도 함께 관찰해줘.
> 2. 현재 백엔드 commit SHA, 애플리케이션·DB 사양/버전, connection pool 설정을 기록해줘.
> 3. 10월 12일 DEV DB는 숨김 공고 1건, 공개 공고 0건이었어. 10월 8일 PROD 공개 공고 28건은 당시 값이야. 실험 데이터는 운영 공고를 자동 복사하지 않고 별도로 준비하려고 해.
> 4. 원인을 확인한 다음 부하 테스트 데이터 준비 방법을 알려줘. 합성 공고 SQL 1,000건은 만들어뒀지만 아직 적용하지 않았어.
> 5. 실험 시간대의 애플리케이션·DB CPU/메모리, 요청·서비스 로그, SQL 횟수/시간·실행계획을 확인할 수 있게 해줘.
> 6. 조회수 쓰기까지 진행하면 connection pool 대기와 DB 잠금 대기도 함께 봐줘.
>
> 나는 k6 요청률·시간·공고 ID를 고정하고 p95/p99·오류율·실제 요청 건수를 기록할게.
> 안전 조건을 확인하고 첫 smoke 결과를 본 뒤 다음 단계 부하를 정하자. 개선 전후 같은 조건을 각 3회 비교할 예정이야.
