# PDF 지원서 심사 화면

합격자 연락처에서 대상을 선택해 오디션 일정 명단으로 가져올 수 있다. 계정의 기존 일정을 선택하거나 제목만으로
새 초안을 만들고 이름·선택 전화/이메일을 확인해 등록한다. 이름만 등록한 뒤 연락처 수정이 가능하다.
같은 일정에 여러 심사함의 합격자를 모으며 동일 출처 재등록은 건너뛴다. 원본 판정·메모·배역은 유지된다.
`오디션 일정 명단` 버튼으로 다시 들어가 연락처를 수정하거나 명단에서 제외할 수 있다.
개인별 날짜/시간 입력과 선택 인원 동일 시간 일괄 적용·해제를 제공한다. 변경은 배정 저장으로 반영하고 실패하면 입력을 유지한다. 확정·발송은 후속이다. API는 `/api/v1/producer-timetables`이며
MSW에서도 실제 서버로 통과한다. 연락처·선택 값을 URL/영구 저장소/분석 이벤트에 전달하지 않는다.

공연사가 심사 제목과 배역을 만들고, 지원서 PDF를 여러 개 올려, 배역별로 정리된 지원 항목에 메모와 결정을 남기는 화면이다.
실제 HTTP 계약은 [백엔드 API](../../backend/docs/api.md)가 정본이며, 이 문서는 프론트가 그 계약을 쓰는 방식만 적는다.

| 경로 | 설명 |
| --- | --- |
| `/producers/pdf-reviews` | 공연사 세션으로 쓰는 화면 |
| `/dev/pdf-reviews` | `PDF_EXTRACTION_LOCAL=true`이고 `VERCEL`이 없을 때만 열리는 로컬 확인 화면. 그 외에는 404 |

로컬 화면의 "로컬 테스트 계정으로 시작"은 가상 공연사 계정(`pdf-local@example.test`)으로 기존 세션 로그인을 호출한다. 인증을 생략하지 않는다.
실행 방법은 [PDF 추출 확인](./api-integration.md#pdf-추출-확인)의 로컬 확인과 같다.

## 구조

| 위치 | 책임 |
| --- | --- |
| `features/pdf-reviews/types.ts` | 심사·지원 항목 타입, 라벨, 배역 필터, 배역 입력 파싱 |
| `features/pdf-reviews/api.ts` | `/api/v1/pdf-reviews` 호출 |
| `features/pdf-reviews/use-pdf-reviews.ts` | 심사 목록과 선택한 심사를 DB 기준으로 조회. 늦게 온 오래된 응답은 버린다 |
| `features/pdf-reviews/use-review-uploads.ts` | 다중 파일 선택·업로드·재시도 |
| `features/pdf-reviews/use-review-progress.ts` | 심사별 처리 집계 폴링과 종료·복귀 시 재확인 |
| `features/pdf-reviews/use-extraction-events.ts` | 기존 추출 확인 워크벤치의 SSE 구독 |
| `components/pdf-reviews/` | 화면 조립(`pdf-review-workbench`)과 생성 폼·목록·업로드·지원 항목·상세 |

공연사 데스크톱·모바일 관리 메뉴의 `PDF 지원자 심사`에서 내 심사함 목록으로 진입한다.
메뉴의 `+`는 `/producers/pdf-reviews?create=1`로 같은 생성 다이얼로그를 연다.

## 흐름

1. 내 심사함 목록의 `심사함 추가하기` 또는 관리 메뉴의 `+`를 누르면 이름과 배역 입력 다이얼로그를 연다.
   배역은 쉼표·줄바꿈 입력, 최소 1개, 중복 불가다. 생성 후 해당 심사함으로 이동하고,
   상단 `심사함 > 제목`의 `심사함`을 누르면 목록으로 돌아온다.
2. 심사함 제목 아래 `PDF 일괄 업로드`에서 여러 파일을 고르거나, `폴더 선택` 또는 폴더·파일 드롭으로 바로 업로드한다.
   한 선택에 PDF 최대 300개, 파일당 25MiB, 동시에 2개다. 한 심사의 800건 상한은 서버가 중복 제외 뒤 적용한다.
   업로드 워커가 원본 바이트의 SHA-256을 계산해 접수한다. 같은 심사의 같은 내용은 이름이 달라도 기존 항목을 쓴다.
   이미 업로드된 원본은 전송을 생략하고 '중복 제외'로 표시한다. 미확인 작업은 같은 jobId로 이어 올리고,
   한 묶음에서 같은 jobId가 겹치면 전송 Promise를 공유한다. 중복은 새 upload 성공 분석을 만들지 않는다.
   이번 작품의 검증 기준은 300명이다. 폴더 안의 PDF만 수집하며 이미지·다른 문서는 제외한다.
   하위 폴더를 포함하고 디렉터리의 여러 반환 묶음을 끝까지 읽는다. 300개 초과는 부분 접수하지 않는다. ZIP 해제는 지원하지 않는다.
   기존 URL 발급 → S3 PUT → 업로드 완료 확인을 유지한다. 개별 실패는 파일별 재시도로 복구한다.
   선택·업로드 완료·실패·진행/대기·제외 개수를 표시한다. 접수한 파일 대기열은 컴포넌트가 해제되어도
   현재 브라우저 안에서 계속 처리하며, 처리 중 탭을 닫거나 새로고침하면 이탈 경고를 표시한다.
   파일은 메모리에만 있으므로 브라우저가 종료되면 남은 대기열을 자동 복구하지는 못한다.
3. 전체 배역·등록 배역·미배정 필터와 대기/합격/보류/불합격 탭, 한 명씩/카드/표 보기를 제공한다.
   대기(PENDING)와 보류(HOLD)는 겹치지 않는다. 판정 완료 수는 PASS/FAIL만 센다.
   `미배정`은 roleId가 없는 지원서다. 추출/분석 상태와 독립이며 운영자가 직접 배정한다.
   카드와 표는 제목·배역·판정·메모만 표시하고, 원본 심사에서는 현재 지원서만 조회한다.
   등록 배역 추가 버튼은 없으며, 배역 설정은 개별 또는 목록에서 최대 300명씩 처리한다.
4. 기본 심사 화면은 PDF.js로 그린 원본 PDF와 배역·내부 메모·판정이다. 자동 추출한 사진·경력·나이·키를 심사 자료로 재구성하지 않는다.
   추출이 실패해도 원본 업로드가 확인되면 열람한다. 페이지 이동·확대·축소·주소 재발급·원본 다운로드를 제공한다.
5. 카드·표는 지원서 제목·배역·판정·메모를 표시하고 선택한 지원서의 원본 심사로 연결한다. 사진·프로필을 미리 조회하지 않는다.
   개별 배역과 선택한 최대 300명의 배역은 디자인된 드롭다운에서 선택 즉시 기존 API로 저장한다.
   저장 실패 시 기존 배역과 메모를 유지하며 다시 선택할 수 있다. 미저장 메모는 배역 변경으로 현재 필터에서 빠질 때도 이동 확인으로 보호한다.
6. 원본은 상세 API(`includeResult=true`)에서 새 S3 서명 URL을 받아 PDF.js로 연다.
   현재 계약은 원본 URL과 추출 결과 포함 여부가 묶여 있어 이 요청은 결과 payload도 동반할 수 있다. 별도의 사진·프로필 선조회는 없다.
   원본 전용 조회 계약 분리는 후속이다. 브라우저/앱 보기 전환 없이 PDF.js 하나로 표시한다. 새 창·다운로드는 대체 경로다.
   `predev`·`prebuild`가 설치된 PDF.js 버전의 디코더·글꼴·CMap·ICC 파일을 `public/pdfjs/`에 복사한다.
   이 생성 경로는 Git과 lint에서 제외한다. PDF.js는 원본을 표시하며 QR 인식은 이번 변경에 포함하지 않는다.
7. 원본 옆 불합격/보류/합격 버튼은 메모와 결정을 기존 PATCH로 저장한다. 저장한 지원자가 현재 분류에서 빠지면 같은 위치의 다음 지원자로 이동한다.
   고정 하단 바는 쓰지 않는다. 데스크톱에서는 남은 화면 높이에 사진을 맞춘다. 좁거나 낮은 화면은 세로 스크롤한다.
   별도 메모 저장은 현재 결정을 유지한다. 보류는 사유 입력 없이 HOLD로 저장한다. 다음 버튼은 지원자만 바꾸고 결정을 저장하지 않는다.
   단축키는 A 합격/S 보류/D 불합격/N 다음이다. Ctrl/Cmd/Alt 조합과 키 반복은 심사 단축키로 처리하지 않는다.
8. 입력 중 메모를 두고 지원자·필터·보기를 바꾸려 하면 확인한다. 업로드 대기 파일/저장 전 메모가 있을 때 탭 이탈도 알린다.
   늦게 온 목록 갱신은 방금 저장한 결과를 덮어쓰지 않는다.

프로필 데이터는 `result.applicantInfo.profile`이며, 프론트에서 모델을 호출하거나 정보가 없다고 추정값을 채우지 않는다.
API·근거 규칙은 [백엔드 계약](../../backend/docs/pdf-reviews.md)이 정본이다.

## 원본 업로드 상태 갱신

- 원본 심사는 업로드 중이거나 서버에서 업로드 확인 중인 항목이 있을 때만 progress를 조회해 목록을 동기화한다.
- 추출·AI 종료 여부는 원본 열람이나 심사를 막지 않는다. 브라우저의 파일별 업로드·재시도·중복·오류 알림을 유지하고 추출/AI 진행률은 이 화면에 표시하지 않는다.
- 업로드 확인이 끝나면 조회를 멈춘다. 파일 처리 상태 API와 기존 파이프라인은 남아 있고, 합격자 연락처/독립 추출 화면은 각각의 기존 조회 경로를 사용한다.
- 진행 요청은 기존처럼 직렬·취소·401 경계를 유지한다. 세션 만료 시 고른 파일과 화면을 보존하고 재로그인을 안내한다.

`/dev/pdf-extractions`의 기존 추출 확인 워크벤치는 별도 기능으로 SSE와 `GET /pdf-extractions` 목록 병합을 유지한다.
병합은 `jobId`로 기존 행에 합치며 선택 파일, 업로드 중·실패 행, 재시도용 `pendingJobId`를 잃지 않는다.

## 저장과 개인정보

지원자 이름·메모·파일 내용은 localStorage·sessionStorage에 저장하지 않는다. 입력 중인 메모는 목록이 다시 읽혀도 유지된다.

## 합격자 연락처

- 선택한 사람이 있으면 해당 인원, 없으면 전체 합격자의 이름·배역·전화·이메일을 탭 구분 텍스트로 복사한다. 미확인/여러 값은 안내 문구를 유지한다. 로딩·빈 명단·조회 오류에서는 복사할 수 없다. 클립보드 쓰기가 거절되면 읽기 전용 텍스트를 직접 복사한다. 복사 내용은 서버·분석·영구 저장소에 전송하지 않는다.

- 심사함의 `합격자 연락처`에서 현재 배역·판정 필터와 관계없이 해당 심사함의 전체 `PASS` 항목을 모아 이름·배역·전화번호·이메일을 표시한다.
  진입과 새로고침 때 기존 심사 상세 API로 최신 판정을 읽는다. 미저장 메모가 있으면 기존 이탈 확인을 거친다.
  연락처 화면에서는 개별 지원자 심사 화면을 해제해 연락처를 보는 시간을 심사 시간에 더하지 않는다.
- `use-passed-contacts.ts`는 합격 항목의 기존 추출 상세 결과만 최대 4개씩 조회한다. `contact-phone.ts`는 저장된
  `result.pages[].text`의 국내 전화번호와 +82 표기를 정규화한다. 동일 번호의 반복은 하나로 취급하고,
  서로 다른 번호가 여러 개면 임의 선택 없이 `번호 여러 개 · 원문 확인`으로 표시한다.
- `contact-email.ts`는 같은 본문에서 연속해서 적힌 일반 영문 이메일 주소를 읽는다. 도메인 대소문자만 통일하고 같은 주소의 반복은 합친다.
  서로 다른 주소는 `이메일 여러 개 · 원문 확인`, 없으면 `이메일 미확인`으로 표시한다. URL 안의 값·잘못된 주소의 일부·줄바꿈으로 끊긴 주소는 추정하지 않는다.
  전화번호와 이메일은 독립적으로 표시하며 확인 인원도 따로 센다. 이메일 때문에 추가 API 조회를 만들지 않는다.
- 이름이 없으면 `이름 미확인`, 번호가 없거나 이미지에만 있으면 `번호 미확인`으로 남긴다. 소속사·보호자 등 번호의 명의는 판별하지 않는다.
  PDF 처리 중·처리 실패·조회 실패는 별도로 안내한다. `PDF 보기`는 기존 원본 뷰어를 열며, 원문에 있는 번호인지 확인할 수 있다.
- 조회 실패는 다른 행을 막지 않는다. 이탈·심사 변경 시 요청을 중단하고 늦은 응답을 버리며, 401이면 명단을 지우고 재로그인을 안내한다.
  전화번호·이메일은 화면 메모리에만 두고 저장소·분석 이벤트에 넣지 않는다. 전체 추출 본문·이미지는 이 화면의 상태에 보관하지 않는다.
- 기존 읽기 API와 권한을 재사용한다. 재업로드·재분석이나 추출 payload 변경은 없으며, 연락처 수정·일괄 문자·파일 다운로드는 제공하지 않는다.
  기존 분석 이벤트의 의미·분모·중복 방지 기준은 바꾸지 않는다.

## MSW

`/api/v1/pdf-reviews/**`와 `/api/v1/pdf-extractions/**`(SSE 포함)는 `mocks/handlers.ts`에서 명시적으로 `passthrough()`한다.
가짜 추출 성공이나 심사 기록을 만들지 않는다.

## 로컬 전용 안내

AI 설정 여부는 Lambda 환경에 따른다. AI가 없으면 기존 레이블 기반 동작을 유지하고,
AI가 있으면 원문과 등록된 배역으로 지원 정보를 정리한다. 실제 처리 여부는 개별 PDF 결과에서 확인한다.
이 한계는 `/dev/pdf-reviews` 안내에만 적고, 공연사 화면에는 구현 용어를 노출하지 않는다.

- S3 업로드·Lambda·AI 작업은 아직 기존 백엔드 흐름이다. 이 UI 변경만으로 자동 처리가 중지되지는 않는다.
- 합격자 연락처는 현재 저장된 추출 본문에서 후보를 찾는다. 일정 명단의 이름·전화번호·이메일 확인·수정은 유지한다.
  합격자만 원본을 읽어 번호를 추출하는 처리 시점 변경과 OCR 대체는 후속이며, 자동 발송을 추가하지 않는다.
- 배우 프로필 가져오기·독립 PDF 추출 확인 화면은 기존 소비자로 유지한다. 심사에서 사용하지 않는 사진 표시 컴포넌트는 제거한다.
- 기본 심사 조작과 저장의 분석 이벤트는 기존 의미·성공 지점을 보존한다. 원본 열람도 로딩 대기를 포함하는 관측이며 업무시간 절감으로 해석하지 않는다.

## 원본 뷰어 정리와 제목 편집 (2026-11-05 로컬 검토)

지원서 이동은 뷰어 위에서 `이전 지원서/다음 지원서`, PDF 페이지 이동·선택·확대는 뷰어 도구 막대에서 구분한다.
지원서 제목은 상단 수정 버튼에서 편집하고 별도 PATCH로 저장한다. 취소/저장 실패 시 원본 파일명과 현재 메모는 유지한다.
저장하지 않은 제목·메모는 지원서/필터/배역 이동 전에 확인한다. 제목 작성 중에는 판정 저장을 막고 제목 저장/취소를 안내한다.
주요 배역은 생성 화면에서 직접 입력하고 드롭다운으로 배정한다. `미배정` 필터는 추출 상태와 무관하게 roleId가 없는 항목을 표시한다.
제목을 파일명·지원자 이름·연락처로 추정하거나 분석 이벤트에 보내지 않는다.
