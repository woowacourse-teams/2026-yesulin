# PostHog 연결과 팀 사용 안내

## 현재 준비 상태

2026-10-29 운영에 수집 코드·PDF 연결·내부 테스트 화면·분석 안내를 배포했다(PR #436).
개발 반영 PR #438도 병합했다. 미국 리전의 예술in 프로젝트(695875)에 대시보드 5개와 차트 24개가 있다.
운영 공고 조회·오픈채팅 유입·다른 공고 탐색·첨부 클릭의 실제 수신과 내부 표시를 확인했다.
분석을 끈 상태로 다른 공고에 이동하면 거부 설정이 유지되고 해당 테스트 이벤트가 들어오지 않는 것을 확인했다.
설치만으로 과거 GA나 관리자 DB를 가져오지 않는다. 로그인 계정 연결과 PDF·예매의 실운영 완료 흐름은
이번 배포 검증에서 수행하지 않았으며 코드·자동 테스트 검증과 구분한다.

Vercel `yesul-in/yesulin-frontend`에 공개 프로젝트 키·수집 주소, 운영/개발 환경 표시, 환경별 서버 식별자
보호 값을 저장하고 `POSTHOG_COLLECTION_ENABLED=true`로 활성화했다. 첫 운영 이벤트는 2026-10-29
17:57 KST에 수신됐다. 대시보드 첫 화면에 시작일을 표시했다. 수집 이전 기간은 실적 0으로 해석하지 않는다.

운영 `POSTHOG_FORM_ATTACHMENTS={"175":[0],"179":[0]}`를 등록했다. 두 공고의 첫 HWP 첨부를 실제로
열어 빈 지원서 본문임을 확인했다. 다른 첨부는 계속 `unknown`이며 다운로드 클릭은 점검 화면에 남지만
양식 전환율에는 포함되지 않는다. 새 공고·첨부 교체 시 확인해 목록을 추가하고 재배포한다.
`POSTHOG_INTERNAL_MEMBER_IDS`와 `POSTHOG_TEST_OBJECTS`의 실제 목록은 아직 제공받지 않았다.
관리자 자동 제외와 브라우저 내부 표시는 동작하므로 팀원은 아래 링크에서 먼저 표시한다.

작업 폴더의 `.env.posthog.production.local`, `.env.posthog.development.local`은 같은 설정의 비공개 사본이다.
Git에서 제외되며 Next.js가 자동으로 읽는 파일 이름도 아니다. 서버 보호 값을 문서·채팅·커밋에 옮기지 않는다.

## 계정과 환경

1. 팀이 계속 관리할 업무용 이메일로 PostHog에 가입하고 예술in 조직을 만든다. 팀원은 각자 계정으로 초대한다.
2. 무료 요금제의 프로젝트 1개 제한에 맞춰 `예술in` 프로젝트 하나를 사용한다. 프로젝트 키는 공유하되
   `NEXT_PUBLIC_POSTHOG_ENV`와 허용 호스트로 운영/개발을 구분한다. 운영 차트에는 production 필터를 고정하고
   개발은 `개발 전용 · 측정 점검` 대시보드에서만 확인한다. 이는 저장소·접근 권한의 물리적 격리가 아니라 집계 분리다.
3. 예술in은 미국 리전을 선택했다(2026-10-29). 수집 주소는 `https://us.i.posthog.com`이다.
   같은 날 기본 수집·사용자 거부 방식을 유지하기로 결정했다. `/privacy/analytics`에 미국 리전·수집 범위·
   현재 무료 요금제의 1년 보관 기준과 거부 방법을 안내한다. 이 운영 결정은 법적 근거 검토 완료를 뜻하지 않는다.
4. Vercel의 운영/개발 환경에 `.env.example`의 PostHog 설정을 각각 입력한다. 서버 전용 값은
   `NEXT_PUBLIC_`로 바꾸거나 저장소에 커밋하지 않는다. 공개 키는 비밀 API 토큰과 다르다.
5. `POSTHOG_IDENTITY_SECRET`은 환경마다 다른 32자 이상의 난수다. 회전하면 로그인 사용자의 기존 시계열이
   새 식별자로 나뉘므로 장애·유출 대응 외에는 유지한다. 내부 계정 ID와 테스트 자료 ID를 서버 설정에 등록한다.
6. 양식 전환율을 켜기 전에 `POSTHOG_FORM_ATTACHMENTS`를 채운다. 예: `{"175":[0],"166":[]}`는 175의 첫 첨부만
   지원 양식, 166의 첨부는 모두 참고 자료라는 **형식 예시**다. 실제 파일을 확인하지 않고 복사하지 않는다.
7. 적용할 처리방침 반영 뒤 `POSTHOG_COLLECTION_ENABLED=true`로 설정하고 배포한다. 공개 변수는 빌드 시
   포함되므로 환경 변수만 바꾸고 기존 배포가 자동 변경됐다고 가정하지 않는다.

PDF는 이 변경과 함께 개발에 배포하고 이후 운영에 포함시키면 다시 계측할 필요가 없다.
기능 파일만 따로 가져가고 analytics 모듈을 누락하지 않는다. PDF 포함 개발 코드를 확인했으며 최신 `origin/main`에 통합해 검증했다.

2026-10-30 배포부터 유입 경로 분류 v1을 수집한다. ‘공고를 본 사람들은 어디서 들어오나요?’ 표는 선택 기간의
사용자별 첫 공고 조회 출처를 한 번만 세며 이전 이벤트는 ‘측정 시작 전’으로 표시한다. 상세 계약과 공유 링크 예시는
[분석 계약](./analytics.md#유입-경로-분류-v1-2026-10-30-배포-이후)을 따른다. 예전 기록의 출처를 복원하지 않는다.

첫 화면은 핵심 지표를 먼저, 모든 차트는 한국어 질문형 제목과 분모·제외·해석 설명을 표시한다.
이번 주는 진행 중, 리텐션 미성숙 구간은 관측 중이다. 미출시 PDF의 빈 차트와 실제 이용 0건을 구분한다.
비로그인은 브라우저 기준이고 분석 거부·차단 사용자는 빠진다.

코드 기준으로 동일한 대시보드를 생성/갱신한다. 먼저 네트워크 없이 정의를 검토한다.

```sh
node scripts/posthog/setup.mjs --dry-run
```

연결 시에는 `POSTHOG_MANAGEMENT_HOST`(eu.posthog.com 또는 us.posthog.com HTTPS origin),
`POSTHOG_PROJECT_ID`, `POSTHOG_ENVIRONMENT`(production/development), `POSTHOG_PERSONAL_API_KEY`를
현재 프로세스 환경으로만 제공하고 `node scripts/posthog/setup.mjs`를 실행한다. 토큰을 명령 인수·문서·채팅에 넣지 않는다.
필요 권한은 대상 프로젝트의 project 읽기/쓰기, dashboard 읽기/쓰기, insight 읽기/쓰기, query 실행이다.
이 스크립트가 만든 이름+태그의 대시보드만 갱신한다. 실제 API에서 쿼리 검증에 실패하면 중단한다.
프로젝트 키는 이 관리 API의 인증키로 사용할 수 없다.

## 팀원 제외와 확인

팀원은 운영 `/analytics/internal`과 개발 `/analytics/internal`에 각각 들어가 내부 테스트 표시를 켠다.
서버의 내부 계정 목록은 로그인 시 적용되며 관리자 역할은 자동으로 내부 처리한다. IP로만 제외하지 않는다.
기기/브라우저/시크릿 모드가 달라지면 표시를 다시 켠다. 등록하기 전 익명 방문은 자동 제외할 수 없다.

1. 개발 전용 점검 대시보드에서 테스트 공고 조회·다른 공고 탐색·첨부 3회 클릭을 확인한다.
2. 내부 표시를 켠 테스트는 점검 화면에만 나타나고 성과 차트에서는 제외되는지 확인한다.
3. 배우 PDF 업로드→추출→적용→저장, 공연사 PDF 업로드→추출→지원자 검토→저장을 확인한다.
4. 분석 끄기 후 새 이벤트와 SDK 전송이 없는지 확인한다. 연락처·파일명·URL·PDF 내용이 없는지도 확인한다.
5. 운영 배포 뒤 environment=production이며 운영 차트에만 집계되는지 확인하고 실제 수집 시작 날짜를 대시보드 설명에 적는다.

확정 예매·취소·심사 전체 현황은 **관리 화면을 실제 조회한 때의 서버 스냅샷**만 연결했다. 관리 화면을 안 열어도
전체 현황이 갱신되려면 별도 DB/서버 정기 동기화가 필요하다. 이 수치를 실시간 전사 DB 합계로 표시하지 않는다.
PDF 전체 작업의 백그라운드 성공률·순수 처리 시간도 서버 결과 이벤트/동기화 없이는 확인할 수 없다.
