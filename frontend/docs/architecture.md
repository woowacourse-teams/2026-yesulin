# 프론트엔드 구조

## 기술과 실행 모드

- Next.js 16 App Router, React 19, TypeScript strict, Tailwind CSS 4
- 실제 API가 기본 실행 모드다.
- `NEXT_PUBLIC_API_MOCKING=enabled`일 때만 MSW와 `/dev/scenarios`를 사용한다.
- 작성 중 지원서는 IndexedDB에 저장하고 서버 Draft로 동기화하지 않는다.

## 소스 책임

```text
src/app/                 URL과 layout, 화면 컴포넌트 조립
src/features/            도메인 타입, API client, request/response 변환
src/components/          화면, form, provider와 사용자 상호작용
src/mocks/               seed 데이터, MSW handler와 메모리 상태
src/config/              환경 변수 해석
```

- 라우트는 비즈니스 규칙을 소유하지 않는다.
- 백엔드 response와 화면 모델의 차이는 feature API adapter에서 변환한다.
- 브라우저 API는 같은 origin의 `/api/**`를 호출한다. Next.js가 `API_ORIGIN`으로 rewrite한다.
- UUID 공고와 숫자 배역은 실제 백엔드 경계를 사용한다. `seed_*` ID는 MSW 전용이다.

## 주요 사용자 영역

- 메인 `/`: 모집 중인 공개 공고 최대 3개와 무료 공연·FAQ를 소개한다. 상단 오디션 메뉴,
  전체 보기와 분야·모집 상태 링크는 오디션 전용 목록으로 이동한다. 메인에서는 목록을 펼치거나 페이지를 나누지 않는다.
  서버에서 공고를 미리 읽고 목 환경·조회 실패 시 브라우저에서 다시 조회한다.
  과거 홈 목록 주소 `/?page=2&closed=1`은 조건을 유지한 `/auditions?closed=1&page=2`로 이동한다.
  콘텐츠의 공통 최대 폭은 1080px이고, 데스크톱·중간 화면 좌우 여백은 최소64px, 모바일은20px다.
  최상단에는 로고와 별 마스코트를 포함한 PC·모바일 이미지 배너(`AuditionAlertBanner`)를 둔다. 고정 배너는 공고 알림·배우 정보
  공유방 2개이고, 그 사이에 운영자가 이벤트 글에서 노출을 켠 이벤트 배너(공개 API, 최대 5개)를 넣는다. 고정 배너는 각 외부
  목적지를 새 창으로, 이벤트 배너는 같은 창에서 이벤트 상세로 연다. 메인 서버 렌더링이 이벤트 배너를 읽고, 목 환경에서는
  브라우저가 읽는다. 읽지 못하면 고정 배너만 보인다. 7초마다 가로 슬라이드로 전환한다.
  이미지 안쪽 하단 가운데 선택 표시·양옆 이전/다음·마우스 드래그·모바일 스와이프를 제공한다. 가로로 충분히 민 뒤 놓으면
  방향에 따라 전환하고, 드래그 뒤에는 배너 링크를 열지 않는다. 모바일 세로 스크롤·확대와 일반 클릭·탭은 유지한다.
  드래그 중이거나 마우스·키보드 포커스가 배너 안에 있거나
  탭이 숨겨지면 자동 전환을 멈춘다. 동작 감소 설정에서는 자동 전환·애니메이션을 사용하지 않는다.
  고정 배너의 문구·이미지·링크는 `features/landing/home-banners.ts`에서 관리한다. 기간이 정해진 모집 배너는 코드에 넣지 않고
  이벤트 글의 배너 노출(노출 종료일)로 올린다. 이벤트 배너 이미지는 저장소 공개 주소를 Next 이미지 최적화 없이 쓴다.
  재생/정지 버튼은 두지 않는다. PC 배너 비율은 3.2:1, 모바일은 4:3이다. 넘김 표시는 이미지 안쪽 양옆에, 선택 표시는 대비가 높은 짙은 배경 위에 둔다.
  아래에는 공개 API의 무료 공연 최대 3개와 FAQ가 이어지고 FAQ 옆에는 모바일 알림 배너를 재사용한다.
  공연 조회 장애는 공고를 가리지 않고 공연 영역에서
  재시도를 제공한다. `/about`은 서비스 소개이며 공개 공고와 무료 공연, 기획사 서비스로 연결한다.
  상세는 열릴 때 조회를 한 번 기록하고
  (`sessionStorage`로 탭당 한 번), 서버 렌더링에서는 세지 않는다. 상세 `/posts/{id}`는
  서버가 정리한 본문 HTML·첨부·태그와 작은 출처 링크(`OTR`)를 보여 준다. 공개 중이 아닌 공고는 서버 렌더링에서 백엔드의 302
  `Location`을 읽고, 원문 이동 수 POST를 한 번 보내고(1.5초를 넘기면 기다리지 않는다) 원문 공고로 `redirect()`한다.
  링크는 `features/audition-posts/types.ts`의
  `auditionPostRoutes`로만 만든다. 기존 배우용 소개 화면은 제거했다.
  상세의 메타데이터·본문은 같은 서버 조회 결과를 공유하며, 실제 404만 `notFound()`로 처리한다. 서버 오류는 오류 화면으로
  전파하고 정상(200) `noindex`로 바꾸지 않는다. 목 환경·서버 API 미설정 시에만 상세를 브라우저에서 조회한다.
  `/sitemap.xml`은 마감 포함 공개 목록을 48건씩 모든 페이지에서 읽어 `/posts/{id}`를 자동 포함한다. 공개 중이 아닌 공고는 제외하며,
  어느 페이지든 조회에 실패하면 공고 URL을 일부만 담은 정상 사이트맵 대신 오류를 반환한다.
- 공개 헤더의 계정 링크는 비로그인 시 로그인, 배우 세션은 내 지원서, 기획사 세션은 기존 공연 관리로 연결한다.
  배우 작업 화면의 상단 공고 찾기는 공개 오디션 목록으로 돌아간다.
- 공개 헤더·모바일 메뉴·푸터의 이벤트 메뉴는 `/events`로 간다. 목록은 운영자가 공개한 이벤트를 최근 순으로 보이고, 상세
  `/events/{id}`는 기간·단계(예정·진행 중·마감)·대표 이미지·줄바꿈 본문과 신청 버튼(새 창, 마감되면 숨김)을 보인다. 두 화면은
  서버가 미리 읽고 목 환경·서버 API 미설정 시 브라우저에서 읽는다. 링크는 `features/events/types.ts`의 `eventRoutes`로만 만든다.
  FAQ는 홈 섹션과 푸터에 남긴다.
- 공고 상세 아래에는 연결된 공연사가 공개 중일 때만 공연사 요약 카드(`CompanySummaryCard`)가 붙고, "공연사 정보 전체보기"로
  `/companies/{id}`에 간다. 공연사 화면은 정보·소개·연혁, 공연사가 알려 준 주소의 지도(`PublicVenueGuide`를 "공연사 위치"로)와 그 공연사의
  공개 공고를 보여 주며, 상세와 같이 서버에서 미리 읽고 실제 404만 `notFound()`로 처리한다. 링크는 `companyRoutes`로만 만든다.
- `/auditions`와 `/auditions/{musical|theater|performance|troupe|agency}`: 전체·뮤지컬·연극·퍼포먼스·단원·기획사의 공개 공고 전용 목록이다.
  조건은 주소(`?page=2&closed=1`, page는 1부터)에 두고 12건씩 번호 페이지로 나눈다. 기본은 모집 중이며,
  "마감 포함"으로 전환할 수 있다. 분야·모집 상태·번호 페이지 링크는 기존 조건을 유지한다.
  검색은 현재 조회한 페이지의 공고명·작성자를 대상으로 한다. 메인의 홍보 배너·무료 공연·FAQ는 포함하지 않는다.
  각 목록은 분야·페이지·마감 조건에 맞는 제목과 canonical을 제공하고, 각 목록의 기본 주소는 사이트맵에 포함한다.
  실제 서버 조회 실패는 오류로 전파하며, 목 환경·API 미설정 시에만 브라우저에서 조회한다.
- `/rss.xml`: 원문 작성 최신순 공개 공고 최대 48건(마감 포함)과 공개 공연의 본문을 RSS 2.0으로 제공한다.
  목록 조회 후 비공개 또는 삭제된 상세는 제외하며, 조회 장애·서버 API 미설정은 캐시하지 않는 `503`으로 응답한다.
  정상 피드는 공유 캐시에서 5분간 유지한다. 공고는 실제 원문 게시일을 쓰고 공연은 게시일 정보가 없어 `pubDate`를 생략한다.
  XML 전체를 9MB 이내로 유지하며, 용량을 넘는 항목은 본문을 자르지 않고 제외한다. 항목 링크·GUID는 예술in 상세 주소다.
  홈·분야별 목록의 HTML head에 RSS 주소를 제공한다. 배포 후 네이버 서치어드바이저의 RSS 제출에
  `https://yesulin.art/rss.xml`을 등록한다. 피드 제공 자체가 색인이나 상위 노출을 보장하지는 않는다.
- `/admin/posts`: 운영자가 공고 알림의 OTR 번호나 주소를 넣어 검토 전으로 가져오고, 확인한 뒤 공개하거나 제작사 요청으로
  내린다. 상태 표시는 검토 전·공개 중·숨김 세 가지이며 목록에서 상태·분류·검색어를 함께 적용하고 20건씩 나눠 본다.
  제목은 새 창에서 공개 중이면 공개 상세, 그 외에는 원문을 연다. 원문 없는 비공개 공고는 관리자 전용
  `/admin/posts/{id}/preview`에서 본문·첨부·태그를 읽고 조회수를 기록하지 않는다. 수정·공연사 정보·원문 다시 가져오기는
  카드 오른쪽 위 더보기에 모은다. 목록은 처음 만든 경로(`createdVia`)로 "자동 수집"·"직접 작성"·
  "기획사 등록"을 표시한다. 고친 공고는 "수정됨"으로 표시하고, 원문으로 다시 가져오려 하면 덮어쓸지 한 번 더 묻는다.
  `/admin/posts/new`에서 원문 없는 공고를 검토 전으로 직접 쓰고, `/admin/posts/{id}/edit`에서 분류·제목·페이·마감·작성자·태그와
  본문, 사진·첨부를 고친다. 두 화면은 같은 폼(`AuditionPostForm`)을 쓴다. 본문 편집기(TipTap)는 이 화면에서만 브라우저로
  불러온다. 고칠 때 본문을 건드리지 않으면 본문 없이 저장해 서버가 원래 본문을 그대로 둔다. 사진·첨부는 공통 ‘파일 추가’ 버튼이나 사진·첨부파일 영역에 끌어 놓기로 받고,
  본문에 직접 사진 파일을 붙여 넣거나 끌어 놓으면 바로 본문에 넣는다. 글자와 그림이 함께 복사된 경우(Word·Excel 등)는 글자를 붙여 넣는다. 끌어 놓은 사진은 놓은 자리에, 파일 추가로 넣은 사진은 커서 자리(본문을 누르기 전이면 끝)에 넣는다. 파일은 `safeUpload`로 저장소에 바로 올리고 응답의 공개 주소를 본문·첨부 목록에 넣는다. 확정은 저장할 때 서버가 한다.
  파일 추가나 첨부 영역에 이미지를 놓으면 업로드 전에 본문 사진/다운로드 용도를 고른다. 본문 사진은 기존 IMAGE 업로드, 다운로드는
  ATTACHMENT 업로드를 사용한다. 대표 이미지를 따로 저장하지 않으며 첫 본문 사진이 기존 목록 썸네일이 된다.
  원문 없이 쓴 공고는 공개 상세에 출처를 표시하지 않는다. 고치기 화면에서 공고를 기획사 계정에 연결하거나 끊고,
  목록은 기획사가 올린 공고를 "기획사 등록"으로, 연결된 기획사 이름을 함께 보여 준다. `?view=owners`는 업체별 보기로
  기획사별 공고 수·자동 연결된 OTR 작성자와 연결 안 된 OTR 작성자를 보여 주고, OTR 작성자를 기획사에 자동 연결하거나 회원 번호를
  OTR에서 다시 읽는다. `?owner={id}`는 그 기획사에 연결된 공고만 서버에서 받아 보여 준다. 고치기 화면에서 기획사를 연결할 때
  OTR 회원 번호가 있는 공고는 같은 작성자의 공고도 자동 연결할지 고른다.
  `?view=companies`는 공연사 정보를 만들고 고치고 공개·내리는 화면이다. 폼은 링크를 최대 3개까지 추가하고 연혁을 따로 받는다. 공개 화면은 비운 항목을 "비공개"로 보인다. 폼에서 대표자 이름 공개 동의와 공식 사업장 주소(상세 주소·지도
  공개) 여부를 따로 체크하고, 운영자만 보는 정보 출처를 남긴다. 아래 "OTR 작성자별 묶기"는 OTR 회원 번호별로 공고를 모아 작성자를
  공연사에 묶거나 새 공연사로 만들고(한꺼번에도 가능), 번호가 없는 예전 공고는 OTR에서 번호를 읽게 한다. 전체 공고 목록의 각 공고에서
  "공연사 정보 쓰기"로 그 공고의 공연사 정보를 바로 쓴다(같은 OTR 작성자의 이전 정보를 불러오고, 없으면 원문 작성자 이름으로 KOPIS
  기획제작사를 찾아 `draftFromKopis`로 처음 값을 채운다. 후보 고르기·다른 이름으로 다시 찾기가 있고, 저장하면 바로 공개하되 내린
  공연사는 내린 채로 둔다). 같은 폼 위에서 이 공고만 다른 공연사로 옮기거나 연결을 끊는다. 공고 상세는
  공개된 공연사가 없으면 원문 작성자 이름과 정보 등록 요청 링크만 있는 "준비 중" 카드를 보인다. 공연사 화면 아래의 "정보 수정 요청"은
  `/companies/{id}/edit-request`로 가며, 공개 정보로 채운 폼을 고쳐 사유·연락처와 함께 보낸다(삭제 요청은 카카오톡 채널).
  운영자 폼과 수정 요청 폼은 `CompanyProfileFields`와 `features/companies/profile-draft`를 같이 쓰며, 선택 항목마다 값을 적거나 "비공개"를
  체크해야 저장된다. 대표 사진은 `features/companies/photo-image`가 브라우저에서 긴 변 1600px JPEG로 줄인 뒤 `safeUpload`로
  올리고(운영자는 공개 주소, 수정 요청은 업로드 키), 없으면 `CompanyAvatar`가 `companyInitial`의 첫 글자를 보인다. `?view=edit-requests`는 처리할 수정 요청을 바뀐 항목 비교와 함께 보이고, 바꾼 항목만 덮어쓴 폼으로 적용하거나 반려한다.
- `/producers/audition-posts`: 기획사가 자기 공고 목록을 보고 `/new`에서 올리고 `/{id}/edit`에서 고친다. 운영자와 같은
  `components/audition-posts/editor/AuditionPostForm`을 쓰고 업로드 함수만 바꿔 끼운다(`features/audition-posts/producer-api.ts`).
  작성자는 기획사 이름으로 고정이라 입력하지 않는다. 올리면 바로 공개되고, 연결된 공고 중 검토 전이거나 운영자가 내린 공고는 상태와 안내 문구로 구분해 보여 준다.
- 배우: 공개 공고, 단계별 지원서, 최종 검토·제출, 프로필·보관함, 지원 이력
- 기획사/제작사: 가입·세션, 회사 프로필, 공연·공고, 배역별 심사
- OTR 협업 공고: `/producers/otr-auditions`의 독립 트리와 생성·목록 화면. `/apply/standard/{id}`는 기존 단계형
  지원서 UI를 재사용하되 배역·기본 정보는 필수, 추가 정보·사진 최대 3장·영상 최대 3개는 선택인 고정 폼이다.
  제출은 `type=OTR`로 기존 공연·공고와 분리한다. 배역별 1차 서류 심사는 기존 보드·상세 화면을 재사용하고
  OTR 전용 API에 결과와 마감을 저장한다.
- 무료 공연: 관객은 `/shows`에서 로그인 없이 공연 목록·상세를 보고 회차를 골라 1~10매를 예매한다. 기획사/제작사는
  `/producers/shows`에서 자기 공연(포스터·상세 이미지 최대 3장·장르)과 회차를 관리하고, 공개·마감하며, 회차별 예매자를
  찾아 전화 요청에 따라 취소한다. 공연 링크는 `features/shows/types.ts`의 `showRoutes`로만 만든다.
  기획사 계정이 없는 공연은 운영자가 운영 대시보드 무료 공연 탭에서 외부 링크 공연으로 등록하고 `/admin/shows/{showId}`에서
  관리한다. 공연 폼·상세 화면은 기획사 화면을 그대로 쓰고 `ShowManagementApiProvider`로 운영자 API(`features/admin/show-api.ts`)만
  바꿔 끼운다. 외부 링크 공연의 관객 상세는 회차를 일정으로만 보여 주고 예매하기가 외부 예매 주소를 새 창으로 열며, 그때
  이동 기록 API를 기다리지 않고 보낸다. 운영자 공연의 회차는 정원 없이 시작 일시만 입력한다.
  목록은 서버에서 미리 읽어 공연명·상세 링크를 최초 HTML에 담고, 목 환경·서버 API 미설정 시에만 브라우저에서 조회한다.
  `/sitemap.xml`은 요청마다 공개 목록 API의 공연과 `/shows`를 포함한다. 목록·상세의 서버 조회 실패는 오류로 전파하고,
  실제 상세 404만 `notFound()`로 처리한다. 일시적인 서버 오류를 공연 삭제나 정상(200) `noindex` 응답으로 바꾸지 않는다.
- 오디션 일정표: 로그인 없이 `/timetable/new`에서 만들고, 기획사는 관리 링크 `/timetable/manage/{열쇠}`의 보드에서
  3단계 안내(합격자 등록 → 시간 배정 → 확정)를 따라간다. 보드는 날짜별 열·시간 칸 줄의 타임테이블이며 빈 칸을 눌러 배우를
  고르거나 이름을 눌러 옮기고, 데스크톱에서는 끌어다 놓는다. 최초·추가 합격은 색과 "추가" 표시로 구분하고, 시간은
  "시간 늘리기"로 더하기만 한다. 확정 뒤에는 `/timetable/manage/{열쇠}/print`에서 날짜·시간별 현장용 표를 인쇄한다.
  배우는 문자로 받은 `/t/{열쇠}`에서 일정을 보고 참석·불참을 알리며, 시간 변경이 필요하면 담당자에게 문의를 남긴다. 주소가 열쇠이므로 `noindex`와 `no-referrer`를 적용한다. 운영자는 `/admin/messages`에서
  일정표 문자를 직접 보내고 완료로 표시한다.
- 운영자: `/admin`에서 DB 현황, 기획사 목록과 수동 활성화, 공고별 지원서 목록·상세, 변경 기록을 본다.
  공고 관리는 개요 다음에 두고, 변경 기록·파일·로그는 운영 도구로 묶는다. 회원 메뉴에서 회원 현황과 기획사·제작사 관리를
  전환한다. 기존 `/admin?tab=producers` 주소는 회원 메뉴의 기획사·제작사 화면으로 유지한다.
  공고 목록에는 작성과 OTR 가져오기, 검색과 공개 상태 필터를 제공한다. 작성·수정은 파일 업로드가 끝난 뒤 저장할 수 있고,
  미저장 상태에서 화면 안의 링크로 이동하면 내용을 버릴지 확인한다. 새로고침·창 닫기는 브라우저 이탈 안내를 사용한다.
  `/admin`과 모든 하위 경로는 Proxy에서 실제 서버의 `ADMIN` 세션을 확인한다. 비로그인·일반 계정·세션 조회 오류는
  운영 화면이나 로그인 폼을 렌더링하지 않고 캐시하지 않는 404를 반환한다. MSW 모드도 운영자 검사를 생략하지 않는다.
  운영자는 `/login`의 기획사/제작사 이메일 로그인에서 들어온다. 관리자 세션이 만료되거나 로그아웃하면 현재 경로를
  다시 요청해 접근 검사를 받으며, 관리자 화면 안에서는 로그인 폼을 제공하지 않는다. API의 기존 ADMIN 권한 검사는 유지한다.
  개요에는 현재 서버의 OTR 공고 링크 이동 통계를 별도 조회한다. 오늘·최근 7일·최근 14일의 총합과
  공고별 횟수·마지막 이동 시각, 환경 배지를 보여 준다. 로그 없음·읽기 상한·조회 오류는 정상 0건과 구분한다.
  DEV·PROD 관리자에서 각각 집계하고 환경 간 합산은 하지 않는다. 원문 확인은 OTR로 직접 이동한다.
  지원서 삭제는 상세에서 대상을 다시 확인하고 별도 삭제 비밀번호를 매번 입력해야 실행된다. 비밀번호는 브라우저에 저장하지 않는다.
- `/admin/events`는 이벤트 글을 쓰고 고치고 공개·내리고 지우는 화면이다. 삭제는 확인 창을 거쳐 글과 이미지를 되돌릴 수 없게 지운다. 제목·요약·줄바꿈 본문·기간·신청 링크·대표 이미지와 메인 배너
  설정(노출 여부, PC 3.2:1·모바일 4:3 이미지, 대체 문구, 노출 종료일, 순서)을 한 폼에서 저장한다. 이미지는 줄이지 않고 원본을
  `safeUpload`(`EVENT_IMAGE`)로 올리며, 배너 비율이 칸과 10% 넘게 다르면 잘림을 안내하지만 막지는 않는다.
- `/admin/files`는 운영 대시보드에서 들어간다. 7일 미만을 포함한 미사용 파일을 상태별로 조회하고,
  현재 페이지에서 삭제 가능한 파일만 선택한다. 삭제 전 대상 ID를 다시 보여 주며 지원서 삭제와 같은 2차 비밀번호를
  한 번 입력받아 최대 100개를 요청한다. 파일별 성공·실패와 재시도 대상을 보여 주고 비밀번호는 화면에 보존하지 않는다.
- `/admin/logs`는 애플리케이션 로그를 읽기만 한다. 구조화 로그는 시각·레벨·이벤트·요약·처리 시간·축약 request ID로
  표시하고 펼친 행에서 전체 필드와 stack trace를 확인한다. 기존 문자열은 `LEGACY`로 표시한다. ERROR·1초 이상 HTTP 요청
  필터와 request ID·대소문자를 구분하지 않는 키워드 검색을 제공하며, 100·200·500건 중 하나를 조회 조건으로 보낸다.
  자동 새로고침은 5초 주기이며 끌 수 있다. 탭이 보이지 않거나 앞선 요청이 끝나지 않았으면 요청을 건너뛴다.
  로그아웃하면 화면에 남은 로그를 즉시 지운다. `ADMIN` 세션만 통과하고
  공개 서비스의 `AuthSessionProvider`는 운영자 세션을 비로그인으로 취급한다.
- 인증 전 지원서 Draft는 브라우저에 남고 소셜 로그인 완료 뒤 같은 `returnTo`로 복귀한다.
- 실제 제출 후 프로필 저장을 선택했다면 별도 프로필 PATCH를 시도한다. 프로필 저장 실패가 제출을 취소하지 않는다.
