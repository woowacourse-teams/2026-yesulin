## 추가 오류 탐색과 쿼리 개선

사용자 요청에 따라 p95 1초를 중단 조건에서 제외하고, 예열 이후 HTTP 오류·타임아웃·검증 오류가 한 건이라도 발생하면 중단하도록 변경했다. HTTP timeout은 **10초 그대로**다. 3초 UX timeout이나 서버 요청률 제한은 질문에 대한 설명만 했으며 구현하지 않았다.

전송 RPS는 시작 요청 수/부하 전송 시간, 완료 RPS는 그 시간 안에 끝난 요청 수/부하 전송 시간이다. 종료 후 유예 중 끝난 요청을 포함해 80 RPS로 처리했다고 계산하지 않는다. 지연 백분위는 해당 측정 구간에 시작해 완료된 요청 전체(유예 포함)를 대상으로 한다. 100 RPS는 첫 오류로 중단되어 미완료 691건을 백분위·오류율에 포함하지 않았다. 따라서 0.05%는 **완료된 2,002건 중 1건의 실패율**이며 계속 부하를 보냈을 때의 오류율이 아니다. k6 threshold abort는 설정한 gracefulStop을 기다리지 않고 남은 요청을 중단할 수 있다.

100 RPS의 첫 클라이언트 오류는 20:39:43 KST의 `error_code=1050`, 10초 요청 timeout이었다. HTTP 500 응답이 아니며 k6에서는 status 0이다. CloudWatch에는 전송한 2,693건이 모두 HTTP 200으로 완료됐고 서버 최대 처리 시간은 10,120ms였다. 클라이언트 취소가 서버 작업의 취소를 보장하지 않는 실제 사례다.

80 RPS에서 Tomcat busy 최대 200/200, Hikari pending 최대 191, GC 최대 34ms가 기록됐다. 100 RPS에서는 active 10/10, pending 191, busy 200/200, GC 최대 26ms였다. 이 인접 분 단위 표본들은 순간 최대 전체를 보장하지 않는다. 100 RPS 중 DB vmstat 1초 표본에서는 CPU가 약 100%, 실행 대기 프로세스 약 9~10개, I/O wait 0%였다. 처음의 부팅 이후 평균 표본은 제외했다. 80~100 RPS의 병목은 DB CPU 포화와 그 뒤의 pool/요청 대기라는 근거가 있다. 앞선 9.7초 GC와는 별도로 분석한다.

### 실행 중 비용이 큰 쿼리와 개선 코드

MySQL performance_schema의 누적 digest에서 공고 COUNT 3개가 각각 약 18,400회 실행되며, 각 실행이 공개 공고 약 2,801행을 읽었다. 세 SQL의 누적 실행 시간은 각각 358.39 / 358.09 / 340.38초였다. 이는 여러 시험·이전 호출을 합친 **경과 시간**이며 CPU 시간을 직접 계측한 값은 아니다. 목록 조회 자체의 첫 페이지 SELECT는 평균 0.54ms였다.

코드에서도 `Page`의 자동 countQuery, countOpen, countPublished를 확인했다. 필터·페이지네이션을 유지한 List 조회로 자동 COUNT를 없애고, 전체/모집 중 개수를 `COUNT + SUM(CASE)` 한 SQL로 집계하도록 변경했다. 페이지 totalElements/totalPages는 집계 결과를 재사용한다. 카운트 캐시·DB 설정·새 인덱스·외부 API 계약은 추가하지 않았다.

DEV MySQL 읽기 전용 검증은 기존 COUNT 3개가 각각 2,801행을 읽는 것을 확인했다. 단일 집계도 all=2,801 / open=481을 반환하며 2,801행을 한 번 읽는다. idle EXPLAIN ANALYZE에서 기존 3개 합계 약 19.8ms, 단일 약 6.17ms였다. 이 숫자는 API 부하 개선율이나 운영 처리량 개선율을 뜻하지 않는다.

개선 코드는 아직 DEV에 배포하지 않았다. 기존 모집 중/마감 포함/분야 필터 검사에 더해 마지막 페이지·범위 밖 페이지·빈 목록·빈 분야 결과의 건수와 totalPages를 검사한다. PR 병합·DEV 배포 이후 같은 데이터·발생기 조건으로 60/80/100 RPS를 재측정해야 실제 개선 효과를 판단할 수 있다.

**20:45 KST**의 최종 크레딧 표본은 앱 288 / DB 285.70이었다. 19:25 이후 조회한 CPUCreditUsage 합계는 앱 3.83 / DB 10.96으로 idle 사용도 포함하며, 인스턴스당 20 credit 예산 내였다. Standard 모드를 유지했고 현재 readiness는 앱·DB 모두 UP, 앱 PID는 배포 전과 같았다.
