# 공고 조회 개선 순서

현재 목표는 DEV 공고 목록의 같은 100 RPS를 처리할 때 응답 지연·오류·자원 포화가 줄어드는지 검증하는 것이다. 기준 자료는 개선 전 100 RPS/60초, 6,001건 중 3,512건 클라이언트 10초 timeout(58.524%), DB CPU 1초 표본 최대 100%, Hikari/Tomcat 포화와 이후 ASG 교체다. 이전 조기 중단 결과를 전체 오류율로 쓰지 않는다.

## 80 RPS부터 관측된 병목과 첫 개선

60 RPS는 p95 79ms였지만 80 RPS는 p95 5,604.2ms / p99 7,231.07ms로 증가했다. 80 RPS 전송 중 성공 완료는 73.65 RPS였고, 인접 분 표본에서 Tomcat busy 200/200·pool 대기 191개가 관측됐다. 최종 오류율은 0%여도 이미 대기가 누적된 단계다. 측정한 단계 중 80 RPS에서 병목을 관측했으며 정확한 임계점은 60~80 사이 추가 측정 없이 확정하지 않는다.

**목표는 100 RPS, 첫 변경은 중복 COUNT 3→1이다.** 첫 비교에서는 기존 10초 timeout을 유지해 쿼리 변경의 효과만 확인한다. UX timeout 변경은 이후 별도 조건으로 비교한다. 합격 확인 항목은 오류·미전송·미완료 0건, 지연·대기 감소, 헬스 실패/ASG 교체 미발생이다. 제품 p95/p99 응답 기한은 아직 확정하지 않았다. 보고서의 p95 1초는 지연 표시용 참고선이다.

건수 계산의 의미: 기존에는 페이지 계산용 건수와 화면에 표시할 모집 중/전체 건수를 따로 조회했다. 예를 들어 전체 100개·모집 중 20개라면 20·20·100을 세 번 계산했다. 한 SQL에서 전체 100개와 모집 중 20개를 함께 계산하고 페이지 수는 그 20개로 계산한다. 목록 조회는 별도로 유지하며 반환값은 같다. 건수 SQL이 3→1로 줄어도 전체 API 지연이 1/3이 된다는 보장은 없다.

## 한 번에 하나의 변경을 비교

| 순서 | 작업 | 확인할 근거와 다음 결정 |
| --- | --- | --- |
| 1 | 비교 조건 고정: 100 RPS·10초 timeout | 먼저 기존 10초 조건에서 COUNT 변경만 비교한다. UX 3초는 후보일 뿐 확정한 제품 기준이 아니다. timeout은 기다림의 한계이며 성능 개선 자체가 아니다. 개선 전후 같은 timeout·RPS·혼합·기간·데이터를 유지한다. |
| 2 | 중복 COUNT 3→1 개선을 단독 적용 | PR #303의 COUNT+조건부 SUM. 실제 MySQL SQL/EXPLAIN ANALYZE에서 호출 수·읽은 행·실행 계획·시간·응답 건수 확인. 단독 쿼리가 빨라졌다는 사실만으로 API 개선을 확정하지 않는다. |
| 3 | 같은 100 RPS/60초 + 종료 유예로 API 비교 | 성공 RPS·오류율·p95/p99·DB CPU·Hikari 대기·Tomcat busy·RAM/GC와 헬스 실패/ASG 교체 여부를 함께 비교. 단순 재시작으로 좋아진 결과와 구분한다. |
| 4 | 남은 DB 반복 작업이 크면 캐시 또는 추가 SQL/인덱스 검토 | 같은 조회의 반복 비율·DB CPU·쿼리 비용·허용 정보 지연을 확인한다. 캐시 없이 COUNT 통합의 효과를 먼저 측정한다. |
| 5 | DB에 여유가 있는데 pool 대기가 남으면 pool 크기 비교 | 증가가 정답이 아니다. 현 10개보다 작은/큰 후보를 한 번에 하나씩 비교한다. DB CPU가 이미 100%이면 연결을 늘려 동시 쿼리만 늘리지 않는다. |
| 6 | DB/pool이 정상인데 APP 실행 슬롯이 병목이면 thread/대기 제어 검토 | 현 Tomcat 200개가 찼다는 사실만으로 증가하지 않는다. DB 대기로 찼다면 쿼리 병목부터 해결한다. 수용·대기 상한과 초과 요청의 빠른 실패, health 경로의 자원 경쟁도 검토한다. |

현재는 계획이며 cache/pool/thread/timeout 설정을 변경하지 않았다. DB QPS는 초당 DB 질의 수이지 성공 API 처리량이 아니다. 요청당 SQL이 줄면 DB QPS가 줄어도 성공 RPS가 높아질 수 있다. 목표는 QPS 자체를 높이는 것이 아니라 **정확한 응답을 기한 안에 반환하는 성공 RPS**를 높이는 것이다.

## 캐시를 도입한다면

메모리가 남는다는 이유만으로 캐시를 추가하지 않는다. 반복 조회를 캐시로 줄였을 때의 CPU/지연 절감과 정보 갱신 지연, 메모리/GC 비용을 비교한다. 당시 APP 호스트 메모리 표본 최대 사용률은 84.553%, JVM 힙은 73.65%였다. 호스트 여유 메모리가 곧 Java 캐시에 전부 쓸 수 있는 공간은 아니다.

단일 APP에서 후보는 작은 로컬 캐시다. 우선 COUNT 집계처럼 키 수와 값이 작은 반복 결과를 검토하고, 필요하면 첫 페이지 DTO로 범위를 확장한다. 전체 JPA 엔티티나 모든 페이지를 무제한 보관하지 않는다. TTL와 최대 엔트리/가중치, 실제 점유·적중률·미스 시 DB 부하·GC를 기록한다. 동시 미스에서 중복 로딩이 발생하지 않는지도 확인한다. 허용 정보 지연은 제품 기준을 정한 뒤 TTL로 반영하며 현재 값은 확정하지 않는다.

현재 APP 한 개이므로 **서버 간 캐시 동기화는 필요하지 않다.** 하지만 DB 변경을 캐시에 반영하는 문제는 남는다. 등록/수정/공개/숨김·삭제·외부 import/직접 DB 변경과 마감일 날짜 전환을 고려해 TTL 또는 쓰기 후 무효화, 날짜 키를 정한다. COUNT 키는 category·today 등 실제 집계 조건을 포함하고, 페이지 DTO라면 page/size/includeClosed/category/today 등 응답 조건을 포함한다. 교체된 APP의 캐시는 비어 있으므로 cold cache 구간도 따로 확인한다.

APP을 여러 개로 늘리면 각 캐시가 서로 다른 값을 가질 수 있다. 그때 허용 지연에 따른 TTL·무효화 전달·공유 캐시를 검토한다. 현재 규모에서 동기화 서버를 먼저 추가할 필요는 없다.

## 비교 조건과 중단 후 확인

- 새 APP의 CPU credit을 확인한다. 과거 APP의 288 credit을 신규 APP에 적용하지 않는다. 현재 Standard / 잔액 50 이상·표본 15분 이내·작업 예산 20/잔액 하한 30 조건을 유지한다.
- 같은 APP 프로세스의 연속 단계라면 최초 한 번 예열할 수 있다. APP 교체·재시작·재배포 시 예열 조건을 새로 맞춘다. 초수만 채우지 말고 응답 시간/CPU/대기가 안정됐는지 기록한다.
- timeout을 바꾸면 기존 10초 결과와 직접 같은 오류율 비교를 하지 않는다. 먼저 같은 timeout의 변경 전 기준을 확보하거나 10초 조건에서 쿼리 개선만 비교한다. 새 UX timeout의 합격 여부는 별도 비교 조건으로 남긴다.
- k6 결과 완료가 서버 작업 종료는 아니다. 측정 이후 CPU/대기/헬스와 ASG 활동을 확인한다. graceful 설정만으로 과부하나 health 실패가 예방되지 않는다.
- 한 번에 한 조건만 바꾸고 앞 단계의 밀린 요청이 정리된 뒤 다음 측정으로 간다. 이번 단계에서는 새 부하를 실행하지 않았다.
