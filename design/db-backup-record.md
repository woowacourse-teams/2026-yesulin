## 1. 왜 지금 필요했나

- **운영 DB에 백업이 하나도 없었다.** DEV DB는 8월부터 매일 S3 백업과 주간 스냅샷이 있었지만, 9/26에 분리한 PROD DB에는
  백업 스크립트·타이머·AWS CLI가 없었고 스냅샷도 0개였다(캡처 `02`, `01-precheck-prod-db.txt`).
- **DB는 되돌릴 수 없다는 것을 전날 겪었다.** 2026-10-21 무중단 배포 검증에서 #327로 롤백하려 했지만, #328이 컬럼을 지운 뒤라
  옛 버전이 켜지지 못했다([무중단 배포 검증 기록](zero-downtime-deployment-record.md) ④). 코드는 되돌릴 수 있어도
  DB를 되돌리는 방법은 백업 복원뿐인데 그 백업이 없었다.
- **처리방침과 실제가 달랐다.** 개인정보 처리방침은 "백업은 90일 순환 방식으로 만료"한다고 약속하는데, DEV 백업은 삭제 규칙이 없어
  계속 쌓이고 있었다(캡처 `01`).

## 3. 복구 연습

### 방법

`sudo yesulin-restore-drill`(`ops/backup/restore-drill.sh`)을 PROD DB 서버에서 실행했다.

- **어디서:** 같은 PROD DB 서버의 임시 MySQL 컨테이너. 운영 MySQL에는 쓰지 않는다. 개인정보가 다른 서버나 개인 PC로 복사되지 않게
  이 방법을 골랐다. 네트워크 없이(`--network none`) 띄우고 끝나면 컨테이너와 내려받은 파일을 지운다.
- **운영 보호:** swap이 없는 서버라 임시 컨테이너 메모리를 384MiB로 제한하고, 메모리가 모자라면 임시 컨테이너가 먼저 종료되게 했다.
  사용 가능한 메모리가 600MiB 미만이면 시작하지 않는다.
- **데이터가 맞는지 확인한 방법**
  1. 내려받은 파일의 SHA-256이 백업할 때 남긴 값과 같은지 (`sha256sum -c`)
  2. 압축이 깨지지 않았는지 (`gzip -t`)
  3. 복원이 오류 없이 끝났는지
  4. **표 85개 각각의 행 수가 백업 직후 운영 DB에서 센 값과 같은지**

## 4. 한계와 다음 일

- **DB가 아직 작다.** 4.5MiB라 복원이 4초였다. 데이터가 늘면 같은 스크립트로 다시 재서 걸린 시간을 갱신한다.
- **행 수는 내용까지 같다는 증명은 아니다.** 체크섬으로 파일이 그대로인 것은 확인했지만, 표 내용 비교(예: `CHECKSUM TABLE`)는 하지 않았다.
- **실패 알림이 없다.** 타이머가 실패하면 서버 journal에만 남는다. CloudWatch 알람이나 Slack 알림을 다음에 붙인다.
- **복구 연습은 손으로 월 1회 한다.** 자동화하지 않았다.
- **공용 버킷이다.** 다른 팀 역할이 우리 경로를 읽을 수 있는지는 권한이 없어 확인하지 못했다. 운영진에 접근 범위를 확인한다.
- **PROD DB 커널 업데이트 대기.** AWS CLI 설치 중 새 커널 재부팅 안내가 나왔다. 백업과 무관하며 점검 시간에 따로 재부팅한다.

## 5. 배운 점

- 백업이 "있다"와 "되살릴 수 있다"는 다르다. 복구를 직접 해 봐야 걸리는 시간과 필요한 것(AWS CLI, 메모리, 권한)이 보인다.
  PROD DB에는 AWS CLI조차 없어서, 장애가 난 뒤 처음 시도했다면 설치부터 해야 했다.
- 복원 결과를 숫자로 비교할 기준은 백업할 때 같이 남겨야 한다. 행 수를 백업과 함께 저장해 두니 복원 직후 표마다 바로 비교할 수 있었다.
- 보관 기간은 기술 선택이 아니라 약속이다. 처리방침의 90일을 기준으로 정하자, 그동안 DEV 백업이 무기한 쌓이며 약속을 어기고 있었다는 것도 드러났다.
