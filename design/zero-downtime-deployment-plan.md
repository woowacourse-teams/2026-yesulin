# PROD 무중단 배포와 롤백 작업 계획

2026-10-21 작성. 백엔드 요구사항 "무중단 배포와 롤백"을 PROD에 적용하기 위한 실행 전 계획이다. 정본이 아니며,
적용한 결과는 [배포 문서](../backend/docs/operations/deployment.md)와 [운영 비용 현황](../backend/docs/operations/cost.md)에
반영하고 이 문서에는 진행 상태와 측정 기록만 남긴다. 기록 규칙은 [작업 기록](operating-cost-work-log.md#기록-규칙)과 같다
(인스턴스 ID·IP·ARN·계정 ID는 적지 않는다).

## 한눈에 보기

> **2026-10-21 적용 완료.** PROD는 앱 2대, 배포 구성 `OneAtATime`으로 운영한다. 측정 결과와 캡처는
> [검증 기록](zero-downtime-deployment-record.md)에 있다. 아래 "현재 상태"의 로드 밸런서 연동 "꺼짐"은 잘못 본 것이고 실제로는 켜져 있었다.

- **요구사항**
  1. PROD에 배포하는 동안 외부에서 요청을 계속 보내, 실패한 요청 수와 끊긴 시간을 기록한다.
  2. 직전 버전으로 되돌리는 절차가 문서에 있고, 실제로 한 번 되돌린 기록(시작·완료 시각)이 있다.
- **지금 끊기는 이유:** PROD 앱이 한 대이고, 배포 그룹이 `AllAtOnce`이며 로드 밸런서 연동이 꺼져 있다.
  배포 중 앱을 멈추고 다시 띄우는 동안 요청을 받을 대상이 없다.
- **결정 (2026-10-21):** PROD 앱을 **평소에도 두 대**로 운영하고, CodeDeploy가 **한 대씩** 대상 그룹에서 빼고 배포한다.
- **선행 조건:** 두 대가 동시에 돌면 깨지는 코드 두 가지(스케줄러 중복 실행, 메모리 저장 비밀번호 재설정 토큰)를 먼저 고친다.
  관리자 삭제 잠금과 `/admin` OTR 경유 집계는 이번에 고치지 않고 "인스턴스별"이라는 한계를 문서에 남긴다.
- **비용:** micro 한 대 추가로 월 최대 약 +8.3. PROD 앱 micro 전환 뒤 예상 월 약 46.4가 최대 약 54.7이 되어 한도 70 안이다.

## 1. 배경: PROD 앱 t4g.micro 전환 (2026-10-19, 완료)

자세한 순서와 확인 결과는 [작업 기록의 PROD 앱 t4g.micro 전환](operating-cost-work-log.md)에 있다. 이 계획과 관련된 내용만 옮긴다.

- DEV micro 부하 테스트에서 80 RPS에서 막히던 서버가 400 RPS까지 처리했고, ALB·ASG로 바로 늘릴 수 있어 PROD 앱도 micro로 낮췄다.
- config `server/prod.env`의 `JAVA_TOOL_OPTIONS`를 `-Xmx384m`으로 고정했다. DEV와 같다.
- `yesulin-backend-prod-lt` 버전 2(t4g.micro, swap 512MiB, CodeDeploy 배포본 2개)로 ASG가 micro를 띄웠고, 옛 small은 ASG가 종료했다.
- 교체 중에도 두 대가 잠깐 함께 Healthy였고 `https://yesulin.art/api/v1/health`는 계속 200이었다.
  **ASG로 두 대를 띄우면 CodeDeploy 시작 후크가 마지막 성공 리비전을 자동 배포한다**는 것을 PROD에서도 확인했다.
  이번 계획은 이 경로를 그대로 쓴다.
- 새 인스턴스에서 CloudWatch Agent 설치가 dpkg 잠금으로 실패했던 문제는 `install_monitoring.sh`가 잠금을 최대 60초
  기다리도록 고쳐 `main`에 반영했다(#324, #325). 두 번째 인스턴스를 띄울 때 다시 확인한다.
- PROD DB(`yesulin-db-prod`)는 t4g.small을 유지한다. ASG 소속이 아니라 정지 권한 없이는 유형을 바꿀 수 없고 micro에서 OOM 이력이 있다.

현재 DEV와 PROD 앱은 사양·힙·swap·GC가 같다. DB만 DEV micro, PROD small이다.

## 3. 결정

### 3.1 PROD 앱 대수: 평소 두 대 (채택)

| 안 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| **A. 평소 두 대 (채택, 추천)** | ASG 2/2/2, CodeDeploy `OneAtATime` + 로드 밸런서 | 설정이 가장 단순하다. Pipeline을 바꾸지 않는다. 한 대가 죽어도 서비스가 유지된다 | 월 약 +8 |
| B. 배포할 때만 두 대 | 배포 전 ASG를 2로 올리고 끝나면 1로 내림 | 평소 비용은 그대로 | 매 배포마다 손 작업이 필요하다. 자동화하려면 Pipeline에 ASG 조작 단계를 붙여야 한다. 올리는 동안 옛 버전이 먼저 배포된다 |
| C. CodeDeploy Blue/Green | 배포마다 ASG를 복사해 새 대상 그룹으로 전환 | 롤백이 대상 전환만으로 끝난다 | 서비스 역할에 ASG 생성 권한이 필요하고, 복사된 ASG의 태그(`ProjectTeam`)·후크 관리가 늘어난다. 학생 계정 권한으로 될지 불확실하다 |

한 대에서 in-place로 배포하면 재시작 동안 요청을 받을 대상이 없으므로 무중단은 불가능하다. 최소 두 대가 필요하다.

### 3.2 두 대에서 깨지는 코드: 두 가지만 고친다 (채택, 추천)

| 항목 | 두 대일 때 문제 | 이번 조치 |
| --- | --- | --- |
| 스케줄러 (`AuditionImportScheduler`, 업로드 정리 2개, `NoticeScheduler`) | 두 서버가 같은 시각에 실행한다. OTR 공고를 두 번 가져오고 Slack 알림이 중복될 수 있다. 배포 문서에도 "여러 대로 늘리면 잠금을 먼저 추가한다"고 적혀 있다 | **고친다.** DB 기반 분산 잠금(ShedLock JDBC)을 추가한다 |
| 비밀번호 재설정 토큰 (`CollectionPasswordResetRepository`) | 서버 메모리에만 있다. 메일 링크를 연 요청이 다른 서버로 가면 약 50% 확률로 유효하지 않은 링크가 된다. 재시작·배포 때도 사라진다 | **고친다.** `email_verifications`처럼 DB 테이블에 저장한다 |
| 관리자 삭제 비밀번호 잠금 (`AdminDeletionConfirmation`) | 서버별로 센다. 10분 5회 제한이 두 대면 최대 10회가 된다 | **문서에 한계로 남긴다.** 관리자 로그인과 CSRF가 앞에 있다 |
| `/admin` OTR 경유 이동 집계 (`FileOtrRedirectLogReader`) | 서버 로컬 JSON 로그를 읽는다. 각 서버가 자기가 받은 요청만 보여준다. 인스턴스 교체 때 사라지는 것은 지금도 같다 | **문서에 한계로 남긴다.** 합계는 CloudWatch Logs Insights로 본다 |
| Caffeine 캐시, Slack 오류 알림 중복 억제 | 서버마다 따로 유지한다 | 영향이 작아 그대로 둔다 |

### 3.3 Flyway 규칙 (새로 지킬 것)

한 대씩 배포하므로 약 5분 동안 **새 버전과 옛 버전이 같은 DB를 함께 쓴다.** 롤백하면 옛 버전이 새 스키마 위에서 돈다.
Flyway는 롤백되지 않는다(`rollback-release.sh`도 JAR만 바꾼다).

- 한 번의 배포에서는 옛 코드가 계속 동작하는 변경만 한다: 테이블·nullable 컬럼 추가, 인덱스 추가.
- 컬럼 삭제·이름 변경·NOT NULL 추가는 두 배포로 나눈다. 먼저 코드가 새 구조를 쓰게 배포하고, 다음 배포에서 옛 구조를 지운다.
- 이 규칙을 [배포 문서](../backend/docs/operations/deployment.md)에 넣는다.

## 5. 측정 방법 (요구사항 1)

- 스크립트: `ops/loadtest/deploy-availability.sh` (단계 1에서 추가)
- 대상: `https://yesulin.art/api/v1/health` (공개, 인증 없음, DB 상태 포함). 필요하면 공개 공고 목록 API를 같이 보낸다.
- 방식: 로컬(학교·집 네트워크)에서 0.2초 간격으로 요청을 보내고 요청마다 시각·HTTP 상태·응답 시간을 CSV로 남긴다.
  연결 실패·타임아웃(2초)은 상태 `000`으로 기록한다.
- 집계: 총 요청 수, 실패 수(200이 아닌 응답), 실패율, **가장 길게 이어진 실패 구간의 길이(끊긴 시간)**, 첫·마지막 실패 시각.
- 측정 구간: CodeDeploy 배포 시작 1분 전부터 배포 성공 1분 뒤까지. CodeDeploy 배포 ID·시작·종료 시각을 같이 적는다.
- 비교용으로 지금 구성(한 대, `AllAtOnce`)에서도 단계 2의 배포 때 한 번 측정해 둔다.

## 6. 롤백 절차 (요구사항 2)

두 대 운영에서는 **CodeDeploy로 되돌린다.** 서버 안에서 `rollback-release.sh`로 바꾸면 한 대만 바뀌고, CodeDeploy의
"마지막 성공 리비전"은 그대로라서 ASG가 새로 띄우는 인스턴스에는 잘못된 버전이 다시 깔린다.

1. CodeDeploy → 애플리케이션 `yesulin-backend` → 배포 그룹 `yesulin-backend-prod` → 배포 내역에서 되돌아갈 **직전 성공 배포**를 연다.
2. 그 배포의 개정 위치(S3 번들)를 확인하고 "배포 재시도"로 같은 리비전을 다시 배포한다.
   배포 구성이 `OneAtATime`이고 로드 밸런서가 켜져 있으므로 롤백도 한 대씩 무중단으로 진행된다.
3. 두 대 모두 Healthy이고 `https://yesulin.art/api/v1/health`가 200이면 완료다.
4. 되돌린 이유가 해결되면 Pipeline으로 다시 최신 버전을 배포한다.

주의

- 배포가 실패하면 배포 그룹의 자동 롤백이 마지막 성공 리비전을 다시 배포한다. 위 절차는 **배포는 성공했지만 동작이 잘못된 경우**다.
- Flyway는 되돌리지 않는다. 3.3의 규칙을 지켰다면 옛 버전이 새 스키마 위에서 동작한다.
- 세션 직렬화 방식이 바뀐 버전으로 되돌릴 때는 배포 문서의 세션 롤백 주의(`DELETE FROM SPRING_SESSION;`)를 따른다.
- 실제 롤백 연습은 Flyway 마이그레이션 차이가 없는 두 리비전 사이에서 한다.

## 8. 비용

- micro 한 대 추가: 인스턴스 정가 약 7.6 + 루트 EBS 8GiB gp3 약 0.7 = **월 최대 약 +8.3**.
  지금 micro는 다른 계정 소유 RI로 0원이다. RI는 작은 크기부터 덮으므로 micro가 늘면 small(PROD DB)을 덮던 몫이 줄어
  실제 증가분은 0~7.6 사이가 된다.
- 예상 월 비용(RI 유지): DEV 앱 micro 59.2 + PROD 백업 1 − PROD 앱 micro 13.8 = 약 46.4 → 두 대 운영 후 **최대 약 54.7**. 한도 70 안이다.
- RI가 모두 사라지면 약 70.5 → 약 78.8로 한도를 넘는다. 이 경우는 [비용 절감 계획](operating-cost-reduction-plan.md)의
  DEV 야간 정지와 함께 다시 판단한다.
- micro 두 대는 옛 PROD small 한 대와 비슷한 비용이다. 대신 한 대가 죽어도 서비스가 유지된다.
- 1주 뒤 Cost Explorer(`ProjectTeam = yesulin`)로 확인한다.

## 9. 남는 한계

- 두 대 모두 `ap-northeast-2a` 한 서브넷에 있다. 가용 영역 장애에는 대비하지 못한다. 다른 영역 서브넷 추가는 이번 범위가 아니다.
- DB는 한 대다. DB 재시작·장애는 이번 계획으로 막지 못한다.
- 관리자 삭제 잠금과 `/admin` OTR 경유 집계는 인스턴스별이다(3.2).
- DB 연결 수가 두 배가 된다(HikariCP 기본 10 × 2). PROD DB small의 `max_connections` 안이지만 단계 4에서 연결 수를 확인한다.
