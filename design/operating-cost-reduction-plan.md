2026-10-08 작성, 2026-10-09 0단계 조회 결과로 갱신, 2026-10-10 1순위 적용 결과 반영. 현재 상태와 계산 근거는 [운영 비용 현황](../backend/docs/operations/cost.md),
실제로 본 것과 바꾼 것은 [작업 기록](operating-cost-work-log.md)을 따른다.

금액은 모두 **USD/월**이고 `ProjectTeam = yesulin` 태그로 거른 Cost Explorer 비혼합 비용 기준이다.

## 1순위. DEV 앱 t4g.micro 전환 · −13.8 (RI 없음 −7.6) · 완료 (2026-10-10)

- **근거**
  - DEV DB(t4g.micro)는 하루 종일 켜져 있지만 13일 내내 0원이다. 다른 계정 소유 t4g.nano RI가 작은 크기부터 적용되기 때문이다.
  - 계정 전체에서 남는 RI가 하루 small 100시간 이상을 덮고 있어, micro 1대가 늘어도 덮일 여유가 있다.
  - DEV 앱(small)은 지금 월 약 13.8이다. micro가 RI로 덮이면 13.8, 덮이지 않아도 정가 차이 7.6이 줄어든다.
- **선행 측정 결과:** Java RSS 501 + CodeDeploy 72 + SSM 25 = 598MiB로 기준(700MiB)을 통과했다.
- **실제 적용 (2026-10-09~10)**
  - 처음 계획은 "정지 → 유형 변경 → 시작"이었지만 `ec2:StopInstances`가 계정 정책으로 막혀 있어 **ASG 교체 방식**으로 바꿨다.
  1. 힙 상한: config `server/dev.env`에 `JAVA_TOOL_OPTIONS=-Xmx384m`, `prod.env`에 같은 이름 빈 값을 넣고 PR #281로 DEV에 배포했다.
  2. Launch Template `yesulin-backend-lt` 버전 4를 만들었다. t4g.micro이고, 사용자 데이터가 swap 512MiB와 CodeDeploy 배포본 2개 보관을 설정한다.
     루트 디스크 여유가 1.5G뿐이라 swap은 1GiB가 아니라 512MiB로 했다.
  3. ASG 원하는 용량을 1 → 2로 올려 micro 새 인스턴스를 띄웠다. CodeDeploy 시작 후크가 자동 배포했고(2분 20초), 두 인스턴스가 번갈아 요청을 받는 것을 확인했다.
  4. 원하는 용량을 2 → 1로 낮춰 ASG가 옛 small을 종료했다(축소 보호로 종료 대상을 지정).
  5. 작업 중 잠시 바꾼 ASG 일시 중지 프로세스와 축소 보호를 원래대로 돌렸다.
- **결과:** DEV 앱은 `yesulin-backend-dev2`(t4g.micro) 한 대다. 가용 메모리 249MiB, Java 402MiB, swap 512MiB, GC는 SerialGC.
- **관찰 (1주):** OOM 로그, swap 사용량, 배포 소요 시간, CPU 크레딧 잔량을 본다.
- **확인:** 2026-10-17쯤 Cost Explorer에서 `BoxUsage:t4g.small`이 small 2대분인 일 약 1.0 이하로 내려가고 `BoxUsage:t4g.micro`가 0인지 본다.
- **잃는 것**
  - DEV가 PROD와 같은 사양이 아니게 된다. 메모리·성능 문제를 DEV에서 재현하기 어려워진다.
  - 기동과 배포가 느려진다.
  - 관리자 로그 집계처럼 메모리를 많이 쓰는 기능에서 OOM이 날 수 있다.
  - CPU 기준 성능이 10%로 낮아 크레딧 초과 요금이 생길 수 있다.
- **위험:** RI는 다른 계정 소유라 만료되면 micro도 과금된다. 그래도 small보다 7.6 싸다.
- **되돌리기:** 정지가 막혀 있어 같은 ASG 교체 방식으로 한다. 최대 용량을 2로 올리고, ASG 시작 템플릿 버전을 2(t4g.small)로 바꾼 뒤
  원하는 용량 1 → 2(small 기동·배포 확인) → 1(micro 종료) 순서로 한다. 줄이기 전에 남길 small에 축소 보호를 걸면
  micro만 종료된다. 끝나면 보호를 해제한다. 약 10분 걸린다.

### DEV·PROD 사양 차이 (2026-10-09 검토)

1순위 후에는 DEV 앱이 t4g.micro, PROD 앱이 t4g.small이 된다. DB는 이미 DEV micro, PROD small로 다르다.

**기능에는 문제가 없다.** 두 환경은 아래가 모두 같다.

- CPU 아키텍처(arm64, Graviton)와 vCPU 수(2개)
- AMI·OS(Ubuntu 24.04)·Java(OpenJDK 25)·실행 JAR·systemd unit·배포 경로
- 환경 변수 이름. 값은 `JAVA_TOOL_OPTIONS` 하나만 일부러 다르다.

같은 JAR가 같은 OS·같은 CPU 계열에서 돌기 때문에 기능 동작은 같다. 크기만 다른 같은 계열이라 바이너리 호환 문제도 없다.

**달라지는 것과 대응**

| 항목 | DEV (micro) | PROD (small) | 영향 | 대응 |
| --- | --- | --- | --- | --- |
| 메모리 | 1GiB + swap 512MiB | 2GiB, swap 없음 | DEV가 먼저 메모리 부족을 겪는다 | DEV OOM은 경고로 보고 PROD 여유를 따로 확인한다 |
| JVM 최대 힙 | 384MiB (`-Xmx384m`) | 약 460MiB (기본값, 물리 메모리 1/4) | 큰 데이터를 다루는 기능은 DEV에서만 실패할 수 있다 | 메모리를 많이 쓰는 기능은 PROD 배포 전 영향을 따로 본다 |
| GC | SerialGC로 바뀔 가능성이 높다 | G1 | 메모리 1792MB 미만이면 JVM이 기본 GC로 SerialGC를 고른다. GC 동작이 같지 않다 | 전환 후 실제 GC를 확인한다. 같게 하려면 `dev.env`에 `-XX:+UseG1GC`를 더한다(메모리는 조금 더 쓴다) |
| CPU 기준 성능 | 10% (크레딧 시간당 12) | 20% (크레딧 시간당 24) | 긴 CPU 작업에서 DEV가 먼저 느려지고 Unlimited 초과 요금이 날 수 있다 | DEV 응답 시간·부하 결과를 PROD 성능 판단에 쓰지 않는다. CPU 크레딧 잔량을 본다 |
| 기동·배포 시간 | 조금 길어질 수 있다 | 지금과 같다 | readiness 대기 시간이 늘 수 있다 | CodeDeploy readiness 재시도(최대 60회) 안에 드는지 첫 배포에서 본다 |

**정리**

- DEV는 기능 확인과 배포 경로 확인용으로 쓴다. 성능·메모리 판단은 PROD 지표로 한다.
- CPU 계열을 바꾸지 않는다. DEV·PROD 중 하나만 x86으로 바꾸는 일은 하지 않는다.
- 메모리를 많이 쓰는 기능(예: 관리자 로그 집계)을 바꿀 때는 DEV에서 힙 부족이 나도 놀라지 말고 원인을 본다.
  같은 조건이 필요하면 DEV를 잠시 small로 되돌려 확인할 수 있다(1순위 "되돌리기"의 ASG 교체 방식, 약 10분).

### 경로 A. 우리 권한으로 할 수 있을 때

0단계에서 EventBridge 조회가 거부됐고, 2026-10-09에 `ec2:StopInstances`가 `ec2-restrict-student` 정책으로 명시적으로 거부되는 것을 확인했다.
우리 권한으로는 인스턴스를 정지할 수 없으므로 **경로 A는 불가능하다.** 아래 절차는 경로 B에서 운영진이 할 일의 참고로 남긴다.
앱 서버는 경로 C를, DB 서버는 경로 B를 쓴다.

1. **DB 재부팅 리허설**
   - DEV DB를 콘솔에서 수동으로 한 번 정지했다가 시작한다.
   - `/opt/yesulin-db/compose.yml`의 restart 정책, docker 자동 시작, 데이터 EBS 자동 마운트는 저장소에 기록이 없다. 그래서 실제로 꺼 보고 확인한다.
   - 확인 방법은 `sudo sh ops/monitor/database.sh` 통과다.
2. **ASG 자동 교체 중지:** `yesulin-backend-asg`의 고급 구성에서 `HealthCheck`, `ReplaceUnhealthy`, `AZRebalance` 프로세스를 일시 중지한다.
   이 설정은 우리 권한으로 할 수 있다(2026-10-09 확인). 1순위가 끝나 지금은 원래대로 재개된 상태다.
3. **앱 재부팅 리허설:** DEV 앱을 수동으로 정지했다가 시작한 뒤 TG가 Healthy로 돌아오는지, health가 UP인지 확인한다.
4. **IAM 역할 생성:** 이름은 `yesulin-dev-scheduler`로 한다. 신뢰 주체는 `scheduler.amazonaws.com`이다. 권한은 아래 세 가지만 준다.
   - DEV 앱·DB 두 인스턴스에 대한 `ec2:StartInstances`, `ec2:StopInstances`
   - DEV Pipeline에 대한 `codepipeline:StartPipelineExecution`
5. **EventBridge Scheduler 일정 생성:** 일정 그룹은 `yesulin-dev-hours`, 시간대는 `Asia/Seoul`이다. 월 1,400만 건까지 무료라 비용이 없다.

   | 시각 | 대상 | 동작 |
   | --- | --- | --- |
   | 20:00 | DEV 앱 | StopInstances |
   | 20:05 | DEV DB | StopInstances |
   | 08:30 | DEV DB | StartInstances |
   | 08:40 | DEV 앱 | StartInstances |
   | 08:50 | DEV Pipeline | StartPipelineExecution (밤사이 병합분 반영) |

   DB가 먼저 올라와야 앱 readiness가 통과한다. 그래서 앱은 10분 뒤에 켠다.
6. **1주 관찰**
   - 매일 아침 09:00에 `dev.yesulin.art/api/v1/health`를 확인한다.
   - 1주 뒤 Cost Explorer에서 EC2 사용 시간이 줄었는지 본다.
- **되돌리기:** 일정을 비활성화하고, ASG 프로세스를 재개한다.

### 경로 C. ASG 예약 작업 (앱 서버만, 2026-10-09 추가)

2026-10-09에 ASG로 micro 새 인스턴스를 띄워 CodeDeploy 자동 배포와 사용자 데이터 swap 생성까지 동작하는 것을 확인했다.
그래서 앱 서버는 인스턴스를 정지하는 대신 **밤에 ASG 원하는 용량을 0으로, 아침에 1로** 바꾸는 방식이 가능하다.

- 필요한 것: `yesulin-backend-asg` 최소 용량 0(지금 1/1/1), 예약 작업 두 개(`Asia/Seoul` 20:00 원하는 용량 0, 08:30 원하는 용량 1).
  `autoscaling:PutScheduledUpdateGroupAction` 권한은 아직 시도하지 않았다.
- 절감: RI가 없을 때 앱(micro) 한 대 B안 시간대 기준 월 약 4.0. 지금은 micro가 RI로 0원이라 절감이 거의 없다.
- 얻는 것: 정지 권한·IAM 역할·EventBridge 없이 우리 권한으로 할 수 있다.
- 잃는 것: 밤마다 인스턴스가 삭제되고 아침에 새로 만들어진다. DEV 서버 로그(관리자 이동 통계 포함)가 매일 초기화되고, 아침 기동에 3~4분 걸린다.
  밤사이 병합분은 아침 새 인스턴스가 마지막 성공 리비전을 받으므로, 밤에 실패한 배포는 다시 실행해야 한다.
- DB 서버는 ASG 소속이 아니라 이 방법을 쓸 수 없다. DB 야간 정지는 경로 B가 필요하다.

### 경로 B. 운영진에게 요청할 때

1. 우리는 정지·시작을 할 수 없으므로 리허설(경로 A의 1·3번)도 운영진에게 함께 부탁한다.
   DEV DB가 재부팅 뒤 스스로 올라오는지(`sudo sh ops/monitor/database.sh` 통과) 확인하는 것이 핵심이다.
2. [운영진 요청 범위](#운영진-요청-범위)의 2순위 항목을 한 번에 묶어 요청한다.
   - 역할과 일정 생성
   - 일정 표와 되돌리는 방법을 함께 전달한다.
   - 앱 서버를 정지 방식으로 끄려면 ASG 프로세스 일시 중지가 필요하다. 이것은 우리가 직접 한다.
3. 역할 생성이 무리한 요청이라고 하면 2순위는 앱 서버만 경로 C로 하고 DB는 켜 둔다.
   - 서버 안에서 `shutdown`으로 끄는 반자동 방식은 관리자가 막아 둔 정지 권한을 우회하는 것이라 쓰지 않는다.
   - 아침 시작(`StartInstances`)도 우리 권한으로는 할 수 없을 가능성이 높다.

### Pipeline 정리

#### 옛 staging Pipeline 삭제 · 완료 (2026-10-08)

- **배경:** `yesulin-backend-staging-pipeline`은 Deploy 전환만 막힌 채 main 병합마다 실행되어 `중지됨`이나 `실패`로 끝났다.
- **조치:** Pipeline을 삭제했다. 이제 백엔드 Pipeline은 DEV와 PROD 두 개다.
- **남은 확인:** 다음 main 병합 때 PROD Pipeline만 실행되는지 본다.
- **잃은 것:** staging Pipeline의 실행 이력과 설정. Deploy가 막혀 있어 아무것도 배포하지 않던 Pipeline이다.

#### V1 전환 · 보류 (절감 약 0)

- **보류 이유**
  - 0단계에서 V2 비용은 staging Pipeline을 포함해도 월 약 2.2였다. 남은 두 개만이면 이보다 낮다.
  - V1은 활성 Pipeline 하나당 월 1이라 두 개면 월 2다. 계정 무료 1개는 공유 계정이라 기대하기 어렵다.
  - 바꾸면 실행 모드가 QUEUED에서 SUPERSEDED로 바뀌어 연속 병합 때 중간 커밋 배포를 건너뛴다.
- **V2 경로 필터 대안도 지금은 불가:** 소스가 GitHub(OAuth 앱) 액션이라 트리거 필터를 쓰려면 소스를 CodeConnections로 바꿔야 한다.
- **다시 볼 때:** 병합이 크게 늘어 Pipeline 비용이 월 3을 넘을 때 V1 전환 절차를 다시 꺼낸다.
  - 각 Pipeline의 현재 JSON을 저장한다(저장소에는 넣지 않는다).
  - 유형을 V1으로 바꾸고 `ConfigSource`의 변경 감지를 기존 동작에 맞춘다.
  - dev 병합 시 DEV Pipeline이 자동 실행되고 health가 UP인지 확인한다.

### PROD DB t4g.micro 복귀 · 보류

- 절감은 13.8(RI 없음 7.6)이다. micro였을 때는 RI로 0원이었을 가능성이 높다.
- PROD DB는 micro에서 MySQL이 OOM으로 종료된 이력이 있다.
- 다시 꺼내려면 2주 메모리 측정, `performance_schema=OFF`·`innodb_buffer_pool_size` 조정, swap 추가, PROD 백업 선행, 점검 시간 공지가 필요하다.
  변경 중 PROD가 2~5분 중단된다.
- 1·2순위로 한도 안에 들어오면 하지 않는다.

### 2027년 대응 · 보류

- 원래 계획은 무료 체험 종료로 2027-01부터 월 15.2가 는다고 보고 2026-12-01까지 대응안을 정하는 것이었다.
- 0단계에서 무료 체험이 계정 전체에 거의 적용되지 않는 것을 확인했다. 2027년에 크게 늘 비용이 없어 결정 기한을 해제했다.
- 더 큰 위험은 다른 계정 소유 RI의 변동이다. 이 경우는 2순위로 대비한다.
- DEV ASG 경로 정비 + Spot(옛 6-c)은 비용 목적으로는 효과가 작다. ASG 자동 교체 경로 검증은 운영 안정성 과제로 따로 다룬다.

## 운영진 요청 범위

교육 운영진은 무리하지 않은 요청을 받아 준다. 삭제 요청은 가능하다고 확인했다.
우리 권한으로 직접 할 수 있는 것으로 확인된 항목은 요청하지 않는다. 변경 권한은 각 단계에서 실제로 시도해 보고 정한다.

| 순위 | 요청 내용 | 성격 | 요청 부담 | 거절되면 |
| --- | --- | --- | --- | --- |
| ~~1~~ | ~~`yesulin-backend-dev` 정지 → 유형 변경 → 시작~~ | | | 요청 불필요. 2026-10-10에 ASG 교체로 우리가 직접 끝냈다 |
| 2 | (경로 B를 고를 때) DEV DB 재부팅 리허설, `yesulin-dev-scheduler` 역할과 일정 생성. 권한은 DEV 인스턴스와 DEV Pipeline으로 한정 | 새 권한 생성 | **중간** | 앱 서버만 경로 C, DB는 켜 둠 |
| 문의 | 조직 t4g RI의 만료 예정일과 계속 공유되는지 | 문의 | 낮음 | 2순위를 서둘러 준비 |

요청할 때 지키는 것:

- 순위별로 묶어 한 번에 보낸다. 대상 리소스 이름, 바꿀 값, 되돌리는 방법, 월 절감 예상액을 함께 적는다.
- 권한 생성 요청은 대상 리소스를 이름으로 한정한다. 계정 전체 권한을 요청하지 않는다.
- 요청 결과(수락·거절·대안)는 이 문서의 진행 상태와 `cost.md`에 남긴다.

## 작업 원칙

- 비용은 항상 `ProjectTeam = yesulin` 필터로 본다. 필터 없이 보면 다른 팀 비용이 섞인다.
- 콘솔 설정을 바꾸기 전에 현재 설정을 캡처하거나 JSON으로 저장한다. 인스턴스 ID·ARN은 저장소에 기록하지 않는다.
- 한 번에 하나만 바꾸고, 확인을 통과한 뒤 다음 조치로 넘어간다.
- PROD에 영향을 주는 변경은 DEV에서 먼저 확인한다.
- 조치마다 바꾸기 전 값, 바꾼 값, 확인 결과를 [작업 기록](operating-cost-work-log.md)에 남긴다.
- 적용일과 실제 효과는 `cost.md`에 기록한다. 실제 효과는 1주 뒤 Cost Explorer로 확인한다.
